Kernel and Web Terminal Performance Plan

Simplify Chariox runtime updates so the web terminal feels immediate while idle kernels use almost no CPU. The system should send the minimum useful information at the minimum useful cadence. Humans do not need millisecond-level updates for values that change at human-scale speed.

Goal

The primary KPI is user experience per unit of work: prompt submissions, terminal output, permission prompts, and visible state changes should feel smooth, while idle kernels, waiting-room screens, and background sessions should consume minimal CPU, disk, and relay bandwidth.

Optimize for responsiveness where the user is looking, and for calm resource use everywhere else. A stale activity count for a second is acceptable. A delayed first token, a frozen terminal, or an 80% idle kernel is not.

Observed Problems

Kernel

Fixed 50ms Sweeps

run_kernel_websocket_server_with_bound_listener starts a background task that calls pump_transport_runtime every 50ms even when no provider process is running.

Subscriptions

Polling Instead of Waiting

Session subscriptions wake every 50ms, build terminal output, notices, workflow events, and sometimes full session snapshots. Most ticks do not produce user-visible changes.

Snapshots

Whole Objects for Small Changes

Regular updates clone and compare full RuntimeSession projections, including agents, workflows, prompt state, provider run state, and activity maps.

Web

Push Plus Refresh Loops

The browser receives pushed events, then also schedules GetSessionState, waiting-room refreshes, provider catalog reads, and slice-list reads after common actions.

Persistence

Large Command Result Writes

Read commands such as waiting-room snapshots, provider catalog, and slice list are serialized into persistent command-result JSONL. Redundant polling becomes disk and JSON work.

Waiting Room

Version Events Trigger Full Fetches

waiting_room_inventory_changed carries a version, so the browser often does another full public snapshot fetch to learn what actually changed.

Target Update Cadence

These cadences are defaults, not correctness boundaries. Direct user actions and provider output should still wake immediately through events.

Surface Current Pattern Target Pattern Reasoning
Provider terminal output for visible session 50ms subscription polling Event-driven wakeup, coalesce writes to 33-100ms while streaming Feels live without repainting or serializing more often than the display and reader need.
Prompt lifecycle and focused agent activity Snapshot refreshes and heartbeat-triggered reads Immediate narrow events for accepted, running, settling, completed, failed These states drive UX and controls, so they should be fast but small.
Visible session metadata Full snapshot every fourth 50ms tick when changed Patch events immediately; full snapshot only on attach, replay gap, manual refresh, or 30s reconciliation Most metadata changes are small and do not need full session transfer.
Background session activity Events plus background state refreshes Activity summary events, at most 1s coalescing while active and 10-30s fallback Sidebar badges can be slightly coarse; visible terminal output cannot.
Waiting-room inventory Version event followed by full snapshot fetch Changed rows in event, coalesced to 250-1000ms; full snapshot on first load or explicit refresh Session rows do not need millisecond precision, but the list should not feel stuck.
Provider catalog Repeated reads during waiting-room refresh Cache by version, refresh on provider auth/config change, startup, manual refresh, or 5 minute TTL Catalogs rarely change during normal interaction and are relatively expensive.
Slice list Repeated reads during waiting-room refresh Event-driven changes, manual refresh, or 15-30s fallback while slice panel is open Slice lifecycle is important but does not require continuous polling outside the slice UI.
Relay and kernel discovery Periodic refresh mixed with waiting-room refresh Heartbeat freshness events and 10-30s discovery fallback Freshness matters, but not at terminal-output cadence.
Idle kernel maintenance 50ms pump No pump when no dirty work exists; 5-10s safety sweep An idle kernel should sleep.

Design Principles

Push facts, not guesses

Runtime mutations should emit typed events from the kernel authority. Clients should not poll to discover facts the kernel already knows.

Patch first, snapshot rarely

Full snapshots are for bootstrap and recovery. Normal operation should send narrow, typed changes.

Visible work gets priority

The focused terminal can update quickly. Background sessions, waiting-room counters, and catalogs should be coalesced and cached.

Idleness should be real

No active provider, no due watchdog, and no dirty projection should mean no hot loop.

Implementation Plan

  1. Replace the unconditional 50ms kernel pump with dirty queues. Provider output, prompt lifecycle, workflow watchdogs, relay inventory, runtime notices, and slice/provider changes should wake the relevant task directly.
  2. Change session subscriptions from polling loops to wait-on-change loops. Use per-session and waiting-room notification channels. Keep a slow safety sweep only to recover missed signals.
  3. Introduce narrow kernel events for the normal path: PromptAccepted, PromptActivityChanged, AgentActivityChanged, ProviderRunChanged, SessionMetadataChanged, existing workflow_run_updated, WaitingRoomRowsChanged, ProviderCatalogChanged, and SlicesChanged.
  4. Keep full SessionSnapshot for attach, replay gap recovery, explicit refresh, and a slow reconciliation interval. Do not use it as the main live update vehicle.
  5. Simplify browser prompt submission. After SubmitPrompt, apply the response session or acknowledgement, update local optimistic UI, and rely on pushed events. Remove immediate waiting-room and session refreshes except for timeout recovery.
  6. Make waiting-room inventory events carry changed rows or compact row patches. A version-only invalidation can remain as a fallback, but it should not be the default path after every user action.
  7. Split provider catalog and slice state from the generic waiting-room refresh. Cache them by version and refresh only on their own change events, manual refresh, startup, or coarse TTL.
  8. Reduce command-result persistence. Persist idempotency metadata for large read commands, but avoid writing full waiting-room snapshots, provider catalogs, slice lists, and session snapshots into JSONL on every request.
  9. Add coalescing at the transport writer. Terminal output can flush quickly while streaming; inventory and background state should be batched to human-scale intervals.

Expected Outcome

<2% idle CPU

Open waiting room and connected relay should not keep the kernel hot.

Fast visible feedback

Prompt send, stop, permissions, and visible output should update from direct events.

Less relay traffic

Changed rows and small state patches replace repeated broad snapshots.

Less code complexity

One live update path replaces polling plus push plus post-action refreshes.
