Chariox implementation plan

Workflow Code Product Completion

This plan completes workflow-code as a professional product feature: unambiguous export families, source export from manually built workflows, source-directory export with JSON schema files, always-on metaagent guides, a documented canvas contract, human-facing commands in TUI/shell/web, and full end-to-end validation across local, web, TUI, real-provider, and second-kernel distribution paths.

Completion criterion: a workflow can be built manually or from JavaScript, exported as a portable workflow-code package, a generated single JavaScript source file, and a generated source directory with external JSON schemas, transferred to an isolated second kernel such as the Hetzner runner, imported or validated there, rendered in the product surfaces, and run successfully with the intended topology behavior.

Public Naming And Exports

Avoid the overloaded word export by making the object being exported explicit in every command, API helper, confirmation message, and UI label. Do not add another generic workflow export command.

User action Meaning Output
workflow publication export Existing deployable publication export. Publication package directory for deployment/runtime invocation.
workflow code package export Portable workflow-code artifact exchange. Single .workflow-code.json package containing source, compiled definition, hashes, and validation metadata.
workflow code source export Readable JavaScript generator export from a saved artifact or an existing workflow. One .js file with inline schemas by default.
workflow code source export-directory Readable JavaScript generator package-directory export with external JSON schema files. Directory containing workflow.js, schemas/*.json, and manifest.json.

The source-directory form is the human-editable package form. It is not a publication package and not the same as the single JSON workflow-code package. The shorter workflow code source export-dir spelling may remain as a compatibility alias, but docs and UI should prefer source export-directory.

Protocol And Meta Tools

  • Add explicit package-named request/tool aliases for workflow-code package export/import while preserving existing ExportWorkflowCodeArtifact compatibility.
  • Add source export requests for both saved artifact refs and existing workflow refs, including workflows originally built manually through slash commands or product UI.
  • Because serialized protocol shapes change, bump the local daemon protocol version and update protocol snapshot/hash tests.
  • Expose metaagent tools under chariox.meta.workflow_code.*: package_export, package_import, source_export, source_export_directory, and keep older export/import or source_export_dir as documented compatibility aliases.

Source Export From Existing Workflows

  • Implement a workflow-to-code serializer that walks the kernel WorkflowDefinition and emits canonical JavaScript builder code.
  • Include workflow settings, schemas, nodes, generated-agent definitions, edges, endpoints, queues, watchdogs, validation policies, edge sides, output schemas, and canvas coordinates.
  • Default to portable generated agents by emitting workflow.newAgent({ alias, provider, model, effort, accountProfile }).
  • Support a non-portable --existing-agents mode that emits workflow.existingAgent(agent_id).
  • For source export-directory, write schemas to schemas/<handle>.json and emit workflow.schemaFromFile(...) calls; this is the required non-inline schema option for distribution.
  • Every exported source file or source directory must compile and apply as a new workflow with fresh runtime ids, independent of the ids in the original workflow.
  • Hash the generated source and schema files in manifest.json so package-directory export can be validated before compilation.

Always-On Metaagent Guides

Guides are always available. There is no opt-in/out configuration. Distribution should copy built-in guide files into user-visible Chariox home while keeping embedded binary guides as a fallback.

  • On install or first kernel startup, seed built-in guides to ~/.chariox/metaagent-guides/builtin/....
  • Users can copy a built-in guide into <workspace>/.chariox/metaagent-guides/... and edit it for project-specific behavior.
  • Guide lookup order is workspace, then user-wide, then built-in copies, then embedded fallback.
  • If multiple guides share the same id, the higher-precedence guide replaces lower-precedence versions for read_guide; search_guides and list_guides return the effective guide plus source_scope.
  • Expose source_scope values: workspace, user, builtin_copy, and embedded.
  • Keep embedded guides in the binary so pnpm/binary distributions remain self-contained even before the user-wide copy is seeded.

Canvas Contract

Metaagents need explicit canvas dimensions so they can design readable workflow graphs without overlapping boxes. The web workflow canvas is the authoritative visual coordinate space.

Component Dimensions / placement
Coordinate space workflow-canvas-v1
Workflow node 232 x 96
Endpoint 180 x 78
Exit marker 120 x 72, positioned at node.x + 268, node.y + 28
Minimum gap 36 canvas units between boxes
Recommended node grid 320 horizontal step and 160 vertical step
Default endpoint offset node.x - 220, node.y
  • Add chariox.meta.workflow_code.canvas_contract so metaagents can retrieve the current dimensions programmatically.
  • Document the same dimensions in workflow-code authoring and pattern guides.
  • Add validation diagnostics for explicit canvas overlap between nodes, endpoints, and generated exit markers.
  • Keep omitted coordinates valid; kernel/web auto-layout can still assign positions.
  • Update all canonical workflow-code examples to satisfy the canvas contract.

Human And Web Product Commands

TUI And Shell Commands

/workflow code validate <file> [--provider-rebinding node=provider/model]
/workflow code apply <file> [--provider-rebinding ...]
/workflow code run <file> --endpoint <handle> [--queue <handle>] --prompt "..."
/workflow code save <name> <file>
/workflow code artifact list
/workflow code artifact get <name>
/workflow code artifact delete <name>
/workflow code artifact apply <name> [--provider-rebinding ...]
/workflow code artifact run <name> --endpoint <handle> [--queue <handle>] --prompt "..."
/workflow code package export <name> --out <file.workflow-code.json>
/workflow code package import <file.workflow-code.json> [--name <name>] [--overwrite]
/workflow code source export <workflow-ref|artifact-name> --out <file.js> [--existing-agents]
/workflow code source export-directory <workflow-ref|artifact-name> --out <directory> [--existing-agents]

source export-directory always writes external JSON schemas and a manifest. source export writes one JavaScript file and may inline schemas for portability in the single-file form.

Web Terminal And Workflow UI

  • Add the same workflow-code commands to the web terminal command parser and command center, including command help, completions, validation errors, and downloadable artifact handling.
  • Add workflow UI actions beside existing publish/distribute actions: Export source file, Export source directory, and Export workflow-code package.
  • Labels must distinguish package export, source export, source directory export, and publication export.
  • The publish/distribute menu must expose the new code/package actions without changing the existing publication export behavior.
  • The web export UI should download the returned file or directory archive and show the command-equivalent action in confirmation text.
  • For source directory export in web, download a zip containing workflow.js, schemas/*.json, and manifest.json; no inline-schema fallback is allowed for this mode.

Second-Kernel Distribution Validation

Workflow-code portability must be validated on an isolated second kernel, preferably the Hetzner runner used by existing remote/native drills.

  1. Create and run each topology locally from its source file.
  2. Export the applied workflow as a workflow-code package JSON.
  3. Export the same existing workflow as a single JavaScript source file generated from the live workflow graph.
  4. Export the same existing workflow as a source directory with external schema JSON files generated from the live workflow graph.
  5. Copy all three export forms to the Hetzner machine or another isolated second-kernel workspace, preferably through the same distribution channel a user would use rather than sharing local artifact state.
  6. Start a clean second kernel with its own CHARIOX_HOME, workspace, worktree, provider catalog, and relay/socket configuration.
  7. Import and run the package JSON on the second kernel.
  8. Validate, apply, and run the single JavaScript source on the second kernel.
  9. Validate, apply, and run the source directory on the second kernel, proving schemaFromFile works with package-relative schemas/*.json paths.
  10. Use provider/model rebindings where the second kernel lacks a provider/model from the source workflow.
  11. Assert every second-kernel run creates a new workflow with fresh workflow graph ids and expected generated agents, including exports generated from workflows originally built manually instead of from workflow-code.
The second-kernel drill must not reuse the local artifact registry, local session ids, local agent ids except in explicit non-portable negative tests, or local provider process state. The preferred target is the Hetzner machine because it proves package and source distribution under real machine isolation rather than another process on the same host.

Topology Validation Matrix

Validate every canonical workflow-code topology as a toy but relevant workflow, not merely as a compile/apply fixture.

Topology Runtime assertion
Prompt chaining Draft handoff reaches refiner; final output matches schema.
Routing Router selects exactly one specialist edge for each routed prompt.
Fan-out and synthesize Planner sends work to both workers; synthesizer waits for both and completes.
Parallelization Independent branches run and return comparable structured outputs.
Adversarial verification Proposer and critic exchange at least one critique before finalization.
Generate and filter Generator emits candidates; filter chooses accepted output and rejects weak candidates.
Tournament Contestants produce alternatives; judge selects one winner with rationale.
Loop until done Workflow loops until done condition, then completes without infinite dispatch.
Orchestrator-workers Orchestrator assigns worker tasks; worker outputs are consolidated.
Evaluator-optimizer Optimizer revises based on evaluator feedback, then emits accepted final output.
  • Deterministic CI lane may rebind all nodes to dev-stub and assert exact structured behavior.
  • Real-provider lane must run representative three-plus-node examples with Codex, OpenCode, and Claude when credentials are available.
  • If real-provider credentials are missing, the drill must fail as a prerequisite failure for release validation, not silently pass.
