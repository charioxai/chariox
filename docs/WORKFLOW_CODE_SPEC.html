Arroba kernel design spec

Workflow Code

Workflow code is a saved, portable artifact that lets users and authorized metaagents define complete Arroba workflows with code. The kernel compiles the artifact into the normal workflow definition model, allocates fresh workflow graph identifiers, optionally spawns agents, validates every reference and limit, and can then run the resulting workflow through existing runtime paths.

Final objective: a metaagent can write a self-contained workflow-code file, validate it, apply it in the current kernel, and export or share it so another user or kernel can apply the same workflow after rebinding unavailable generated-agent providers and models, while validating target-kernel agent and extension availability before mutation.

Goals

  • Make workflow generation expressible as JavaScript through a compiler IR that can support additional scripting front ends without changing kernel workflow semantics.
  • Cover the same design surface that workflow slash commands cover: workflows, nodes, edges, endpoints, queues, watchdogs, schemas, output capabilities, node limits, canvas layout, and extension grants.
  • Keep execution authority in the kernel. The script produces a design IR; it does not mutate runtime state directly.
  • Let each application of the same script create a new workflow with fresh workflow, node, edge, endpoint, queue, watchdog, and generated-agent ids.
  • Support generated agents for portable workflows and existing-agent bindings for local, non-portable workflows.
  • Make schemas first-class workflow objects instead of ad hoc filesystem path strings.
  • Give metaagents a safe authoring path even when they are in plan mode by exposing workflow-code artifact tools through runtime MCP.

Non-Goals

  • Do not add edge-level conditional expressions. Conditional routing is node behavior expressed through normal workflow output.
  • Do not let scripts execute provider runs, shell commands, or direct kernel mutations while compiling.
  • Do not make publication creation part of workflow-code. Publication/export remains a separate operation once a workflow exists.
  • Do not reuse graph ids across script applications. Workflow code is a generator, not a durable execution replay format.

Current Kernel Morphology

The script API must compile to the existing workflow shape unless this spec explicitly calls out a needed refactor. The core object is WorkflowDefinition. It contains graph and endpoint definitions, not pre-spawned runs.

Slash Command Parity

Workflow code should be able to define every persistent component that slash commands can define. Read-only commands, run inspection, cancellation, resume, and publication export stay outside the static design artifact.

Limits And Configuration

Kernel configuration should set large but bounded defaults so generated workflows can fan out without making the runtime unbounded. 

[workflow]
session_default_max_agents = 1024
max_queues_per_workflow = 1024

[workflow.code]
max_concurrent = 32
max_nodes = 1024
max_agents = 1024
max_edges = 4096
max_queues = 1024
max_watchdogs = 1024
max_schema_bytes = 1048576
max_generated_prompt_bytes = 4194304
script_timeout_ms = 30000
script_memory_bytes = 268435456
  • The session agent cap is TOML-backed at workflow.session_default_max_agents with default 1024.
  • maxConcurrent defaults to 32 through workflow.code.max_concurrent and may be lowered or raised per workflow-code artifact up to the configured kernel limit.
  • Compile validation must enforce max nodes, generated agents, edges, endpoints, queues, watchdogs, concurrency, schemas, and generated prompt bytes before the workflow is accepted.

First-Class Schemas

Current workflows store schema references as strings such as handoff_schema_ref, run_output_schema_ref, and intermediate_output_schema_ref. Runtime validation reads those refs as JSON schema paths. That is not strong enough for portable workflow code.

The workflow schema refactor should introduce kernel-owned schema definitions: 

WorkflowSchemaDefinition {
  id: String,
  alias: Option<String>,
  description: Option<String>,
  schema: serde_json::Value,
  created_by_user_id: String,
  created_at_ms: u64,
  revision: u64
}
  • Workflow code defines schemas inline with workflow.schema({ alias, description, schema }).
  • Optional schemaFromFile(path) is authoring sugar only. The compiler embeds the JSON value into the workflow-code artifact or compiled IR.
  • Exported workflow-code packages include source_sha256 and definition_sha256; import verifies both hashes before saving the artifact.
  • Workflow, node, edge, and publication schema fields should migrate from *_schema_ref: String to schema ids or schema handles.
  • Compiled workflow snapshots should export schemas with the workflow so another kernel can import without local filesystem dependencies.
  • Validation tools should validate against schema definitions resolved by id, while preserving a compatibility shim for old path refs during migration.

Agents And Ownership

A workflow node has an agent. The script should express that directly instead of building a separate agent action list.

  • newAgent(...) means the apply step spawns a regular agent and attaches it to exactly one node.
  • existingAgent(ref) means the apply step binds an already-spawned regular agent. This is not portable.
  • A metaagent may only bind an existing agent it spawned or controls. It must not attach arbitrary session agents.
  • A user may bind agents according to normal session ownership policy.
  • The compiler must reject metaagents as workflow worker nodes and reject the same agent appearing in more than one node.
  • If a provider or model is unavailable in the target kernel, apply should produce a binding error with a provider/model replacement map.

Extensions

Workflow code may declare node extensions because extensions are part of what makes a worker node function. Applying a workflow-code artifact should translate extension declarations into the same kernel extension grants used outside workflows. 

extensions: [
  { kind: "mcp", name: "playwright" },
  { kind: "skill", name: "frontend-design" },
  { kind: "script", name: "schema-normalizer", environment: "node" },
]
  • Extension definitions are portability requirements, not hidden script execution privileges.
  • Apply-time validation checks that declared extensions already exist in the target kernel registry and rejects the workflow before mutation when a requirement is unavailable.
  • Credentialed connectors require target-kernel binding and must not be serialized with secrets.
  • Home-worker and slice-backed behavior must follow existing Arroba provider and skill/MCP transfer rules.

Routing Model

Conditional routing is a required node-driven capability. A node with multiple outgoing edges can either fan out to every outgoing edge or choose specific outgoing edges by producing a routed handoff object in output.message. The runtime already recognizes workflow_handoffs entries with edge_id or to_node_id. 

{
  "workflow_handoffs": [
    {
      "edge_id": "edge_abc",
      "summary": "Send implementation details to reviewer",
      "output": {
        "message": {
          "task": "review",
          "files": ["apps/kernel/src/session/service/turns.rs"]
        }
      }
    }
  ]
}
  • If workflow_handoffs is absent or empty, the runtime fans out the same output to all outgoing edges.
  • If workflow_handoffs is present, only matching edges receive output.
  • A handoff can target by edge_id or to_node_id.
  • A handoff with a null message suppresses output for that route.
  • Scripts never hard-code generated edge ids. The apply report maps script handles to concrete ids, and node runtime context lists outgoing edge contracts with the real edge_id, to_node_id, target label, target instruction excerpt, handoff schema ref, and validation policy.

Workflow Code API Shape

The JavaScript API should be small and builder-oriented. Handles are compile-time references only. They are not durable Arroba ids. 

workflow.define({
  alias: "triage-review-loop",
  prompt: "Triage, route, review, and synthesize the requested task.",
  flushAgentContextBeforeRun: true,
  maxConcurrent: 32,
});

// Define schemas, nodes, edges, endpoints, queues, and watchdogs here.

Mandatory components are a workflow alias, at least one node, at least one endpoint, and an entry node for every endpoint. Edges, queues, watchdogs, schemas, extensions, canvas layout, generated agents, existing-agent bindings, and apply-and-run actions are optional.

Example Script

This example defines a one-two-one workflow: an intake node fans out to two workers, both feed a synthesis node, and the synthesis node can loop back to intake for revision or complete the workflow. 

workflow.define({
  alias: "one-two-one-loop",
  prompt: "Coordinate a 1-2-1 workflow with a synthesis loop.",
  flushAgentContextBeforeRun: true,
  maxConcurrent: 32,
});

const partialOutput = workflow.schema({
  handle: "partial_output",
  alias: "partial-output",
  description: "Intermediate status visible to the endpoint while the run continues.",
  schema: {
    type: "object",
    additionalProperties: false,
    required: ["status", "summary"],
    properties: {
      status: { type: "string", enum: ["triaging", "working", "reviewing"] },
      summary: { type: "string" },
    },
  },
});

const finalOutput = workflow.schema({
  handle: "final_output",
  alias: "final-output",
  schema: {
    type: "object",
    additionalProperties: false,
    required: ["result", "evidence"],
    properties: {
      result: { type: "string", enum: ["complete", "needs_user_input"] },
      evidence: { type: "array", items: { type: "string" } },
    },
  },
});

const workerHandoff = workflow.schema({
  handle: "worker_handoff",
  alias: "worker-handoff",
  schema: {
    type: "object",
    additionalProperties: false,
    required: ["task", "constraints"],
    properties: {
      task: { type: "string" },
      constraints: { type: "array", items: { type: "string" } },
    },
  },
});

workflow.define({
  runOutputSchema: finalOutput,
  intermediateOutputSchema: partialOutput,
});

const intake = workflow.node({
  handle: "intake",
  publicLabel: "Intake",
  agent: workflow.newAgent({
    alias: "wf-intake",
    provider: "codex",
    model: "gpt-5",
    effort: "medium",
  }),
  instructions: `
Read the workflow-level prompt for the requested task.
Split the work between the two worker nodes.
When choosing a downstream route, use the outgoing edge contracts listed in the system prompt.
If the synthesis node asks for revision, incorporate its feedback and send updated tasks.
`,
  canEmitIntermediateRunOutput: true,
  intermediateOutputSchema: partialOutput,
  maxTurns: 4,
  extensions: [
    { kind: "skill", name: "openai-docs" },
  ],
  canvas: { x: 120, y: 240 },
});

const implementer = workflow.node({
  handle: "implementer",
  publicLabel: "Implementer",
  agent: workflow.newAgent({
    alias: "wf-implementer",
    provider: "codex",
    model: "gpt-5",
    effort: "high",
  }),
  instructions: "Implement or draft the requested change. Hand off concrete files, commands, and unresolved risks.",
  maxTurns: 3,
  extensions: [
    { kind: "mcp", name: "node_repl" },
  ],
  canvas: { x: 420, y: 120 },
});

const reviewer = workflow.node({
  handle: "reviewer",
  publicLabel: "Reviewer",
  agent: workflow.newAgent({
    alias: "wf-reviewer",
    provider: "codex",
    model: "gpt-5",
    effort: "medium",
  }),
  instructions: "Review independently. Hand off only findings, verification status, and recommended next action.",
  maxTurns: 3,
  canvas: { x: 420, y: 360 },
});

const synthesize = workflow.node({
  handle: "synthesize",
  publicLabel: "Synthesis",
  agent: workflow.newAgent({
    alias: "wf-synthesis",
    provider: "codex",
    model: "gpt-5",
    effort: "medium",
  }),
  instructions: `
Combine both incoming worker results.
If more work is required, route a revision request back to Intake using the outgoing edge whose target node is Intake.
If the work is complete, call validate_and_submit_workflow_run_output with the final-output schema.
`,
  waitForAllInputs: true,
  canCompleteWorkflowRun: true,
  canEmitIntermediateRunOutput: true,
  intermediateOutputSchema: partialOutput,
  maxTurns: 5,
  canvas: { x: 740, y: 240 },
});

workflow.edge(intake, implementer, {
  handle: "intake_to_implementer",
  handoffSchema: workerHandoff,
  validationPolicy: "halt",
  sourceSide: "right",
  targetSide: "left",
});

workflow.edge(intake, reviewer, {
  handle: "intake_to_reviewer",
  handoffSchema: workerHandoff,
  validationPolicy: "halt",
  sourceSide: "right",
  targetSide: "left",
});

workflow.edge(implementer, synthesize, {
  handle: "implementer_to_synthesize",
  sourceSide: "right",
  targetSide: "left",
});

workflow.edge(reviewer, synthesize, {
  handle: "reviewer_to_synthesize",
  sourceSide: "right",
  targetSide: "left",
});

workflow.edge(synthesize, intake, {
  handle: "revision_loop",
  validationPolicy: "warn",
  sourceSide: "left",
  targetSide: "right",
});

const start = workflow.endpoint(intake, {
  handle: "start",
  alias: "start",
});

const urgent = workflow.queue({
  handle: "urgent",
  alias: "urgent",
  priority: 10,
  enabled: true,
});

workflow.watchdog(start, {
  handle: "follow_up",
  queue: urgent,
  intervalSeconds: 3600,
  invocationPrompt: "Check whether queued work needs follow-up.",
  policy: "queue",
  maxWakeups: 24,
});

Edge handles such as revision_loop are compile-time references only. Apply/run returns the real edge id in edge_ids, and workflow node prompts list the real outgoing edge ids when an agent needs to route with workflow_handoffs.

Compilation And Validation

Applying workflow code should be an atomic kernel operation with explicit phases.

  1. Parse the artifact and execute it in a deterministic workflow-code runtime with no filesystem, shell, network, provider, or kernel mutation access except approved schema file imports.
  2. Collect a typed compiler IR containing schemas, nodes, agent specs, edges, endpoints, queues, watchdogs, extension requirements, and canvas layout.
  3. Validate shape: required fields, enum values, graph references, endpoint entry nodes, workflow/endpoint/queue aliases using the same lowercase alias rules as slash commands, no duplicate normalized queue aliases, no duplicate agent bindings, no metaagent worker nodes, no impossible queue/watchdog references.
  4. Validate policy: caller authority, metaagent ownership, provider/model availability or replacement bindings, extension availability, configured limits, and max generated prompt bytes.
  5. Allocate fresh kernel ids for workflow graph objects and generated agents.
  6. Expose outgoing edge contracts at run time with allocated edge_id, to_node_id, target label, bounded target_instructions, handoff schema ref, and validation policy.
  7. Validate schemas and prompt templates after id allocation.
  8. Apply state changes through the normal session and workflow services, not through a parallel mutation path.
  9. Return a compile report with created ids, warnings, binding requirements, and a graph summary.

Dry-run validation should return the same report without mutating state. A failed compile must leave no partial workflow, generated agent, extension grant, queue, or watchdog behind.

Handle To Kernel Id Translation

Scripts do not assign workflow graph ids. Every builder call returns an opaque compile-time handle. Handles let the script connect objects to each other, but they are not Arroba ids and are not persisted as ids in the workflow definition. 

const intake = workflow.node({ ... });
const reviewer = workflow.node({ ... });
const reviewEdge = workflow.edge(intake, reviewer, { ... });
const start = workflow.endpoint(intake, { alias: "start" });

The compiler turns those handles into an intermediate representation. The IR may name handles with compiler-local references such as node#1, edge#3, or endpoint#1, but those references only exist during validation and apply.

  1. The script runtime collects objects and references by handle, not by kernel id.
  2. The validator checks that every handle points to an object of the expected type.
  3. The apply phase creates the workflow and generated agents through normal kernel services.
  4. As each object is created, the kernel records an allocation map: schema handle to schema id, agent handle to agent id, node handle to node id, edge handle to edge id, endpoint handle to endpoint id, queue handle to queue id, and watchdog handle to watchdog id.
  5. References are resolved through that allocation map before calling existing workflow services. For example, an edge IR with from: node#1 and to: node#2 becomes add_workflow_edge(workflow_id, allocated_node_id_1, allocated_node_id_2, ...).
  6. Instruction templates that need allocated ids are rendered only after allocation, using the same map.
  7. The apply response returns a creation report mapping script handles, aliases, and public labels to the actual ids created in this kernel.

Workflow-code scripts do not execute runs while compiling. Run and queue side effects happen only after validation through arroba.meta.workflow_code.run, workflow_code.run, or normal endpoint invocation APIs, which receive the allocated endpoint and queue references from the apply report.

Existing agents are the exception. workflow.existingAgent("agent-12") carries an external kernel id or user-supplied binding. The compiler validates that the caller may use that agent, then records the existing id in the allocation map instead of spawning a new agent. Generated agents still receive fresh ids every time the script is applied.

This is what makes the same script reusable: applying it twice yields the same graph shape but different kernel ids. Subsequent operations should use the returned creation report, workflow aliases, endpoint aliases, node public labels, or normal resolve/list commands to inspect the concrete instance.

Metaagent Authoring

Metaagents are normally in plan mode, so they should not depend on direct file writes or shell access to author workflow code. The kernel exposes runtime MCP endpoints that create and manage workflow-code artifacts.

Runtime MCP endpoint Purpose
arroba.meta.workflow_code.create Create a saved workflow-code artifact from name, source, optional language, and optional Node.js path.
arroba.meta.workflow_code.update Update a saved artifact revision.
arroba.meta.workflow_code.list List saved workflow-code artifact metadata.
arroba.meta.workflow_code.read Read a saved artifact for review or iteration.
arroba.meta.workflow_code.delete Delete a saved artifact from the session/workspace registry.
arroba.meta.workflow_code.validate Compile in dry-run mode and return typed errors, warnings, and binding requirements.
arroba.meta.workflow_code.apply Compile and instantiate a workflow in the current session, using explicit provider/model rebinding for generated-agent nodes and strict validation for existing-agent and extension requirements.
arroba.meta.workflow_code.run Apply if needed and invoke an endpoint with a prompt, or run an already-applied artifact instance.
arroba.meta.workflow_code.export Export artifact source, embedded schemas, manifest, extension requirements, compatibility metadata, and source/definition hashes.
arroba.meta.workflow_code.import Import a portable artifact package from another user or kernel without trusting embedded credentials.

Metaagents receive compact workflow-code authoring guides through the built-in meta guide tools. Those guides include the DSL reference, current kernel limits, examples, routing rules, schema rules, and the required validate-before-apply loop.

Portability

Portable workflow code must separate stable intent from local bindings.

  • Source, schemas, graph topology, prompts, watchdog definitions, queue definitions, canvas hints, and extension requirements are portable.
  • Existing agent ids, local filesystem schema paths, credentials, provider login state, and connector secrets are not portable.
  • Provider/model replacement should be explicit at apply time, for example { "codex:gpt-5": "claude:opus-4.1" } when policy permits.
  • Imported artifacts should validate against the target kernel's feature version and list missing capabilities before any mutation.

Implementation Phases

  1. Extend workflow turn prompts and add drills for multi-edge routing with workflow_handoffs.
  2. Add TOML-backed defaults for session max agents and workflow max concurrency.
  3. Introduce first-class workflow schemas with compatibility support for existing *_schema_ref strings.
  4. Add the workflow-code artifact type and compiler IR.
  5. Add runtime MCP endpoints under the existing metaagent bundle: arroba.meta.workflow_code.create, arroba.meta.workflow_code.read, arroba.meta.workflow_code.list, arroba.meta.workflow_code.update, arroba.meta.workflow_code.delete, arroba.meta.workflow_code.validate, arroba.meta.workflow_code.apply, arroba.meta.workflow_code.run, arroba.meta.workflow_code.import, and arroba.meta.workflow_code.export.
  6. Compile nodes-first workflow scripts into existing workflow services atomically.
  7. Add the metaagent workflow-code skill/guide and make it available to metaagents by default.

Protocol Impact

Adding workflow schemas, workflow-code artifacts, compiler reports, or runtime MCP/local daemon request shapes changes serialized protocol. Each such change must bump the local daemon protocol version, update protocol shape/hash tests, update client minimum supported versions when required, and add a focused drill that exercises the new behavior.
