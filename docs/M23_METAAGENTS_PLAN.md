# M23 Metaagents Plan

## Objective

Add metaagents as session-level coordinator agents. A metaagent is a normal Arroba
agent from the provider perspective, but it receives a meta-only runtime MCP
surface that lets it observe the session, run allowed Arroba commands inside its
own session, prompt agents it owns, and supervise workflow and agent activity on
behalf of the user.

The kernel remains the runtime authority. Metaagents must not introduce a second
prompt path, permission authority, workflow engine, relay authority, or provider
execution mode.

## Core Semantics

- A session may have at most one metaagent per user/collaborator.
- A metaagent is an `AgentInstance` with a role such as `standard` or `meta`.
- Metaagents use the normal provider launch, prompt, MCP, permission, and
  transcript paths.
- Metaagents cannot create new sessions.
- Metaagents cannot be added as workflow nodes.
- Metaagents cannot be launched in slices.
- Metaagents may run on a remote worker kernel.
- Metaagents may save, reboot, shut down, or otherwise manage slices through
  normal Arroba commands and tools when policy allows.
- Metaagent prompts to other agents must route through the existing
  `SubmitPrompt` path.
- Metaagent runtime event prompts must be generated by the centralized prompt
  injection service.

## Collaboration Semantics

Each collaborator may create one metaagent in a shared session.

Authority is user-scoped:

- A user's metaagent may prompt and mutate only that user's agents, including
  agents spawned by that metaagent.
- A user's metaagent may observe all workflow-related events in the session,
  regardless of which collaborator or agent emitted them.
- A user's metaagent may observe only agent-turn events for that user's agents,
  except where those events are also workflow events.
- A user's metaagent may resolve runtime interactions only for that user's
  non-meta agents when policy allows.
- A metaagent can never resolve its own runtime interactions.

The relay remains transport only. Collaboration metadata must not cause the relay
to inspect prompts, workflow outputs, or event payloads.

## UX Surfaces

Every place that can create a session or agent should expose "create as
metaagent" when the current user does not already have a metaagent in that
session.

Required surfaces:

- TUI waiting room session/agent creation.
- TUI slash commands and completions.
- TUI agent pane footer.
- Arroba shell command docs and command parsing.
- Web side panel agent creation.
- Web Freeform session and agent creation.
- Web terminal/freeform command flows.

Display requirements:

- Show a clear `meta` indicator in the agent pane footer for metaagents.
- Show metaagent status anywhere agent identity/status is summarized.
- Disable or explain the option when the current user already has a metaagent.
- In the web workflow canvas, keep metaagents out of the selectable/listed agents
  for workflow nodes.

## Protocol And State Changes

This changes serialized agent/session protocol shape. Follow the protocol change
rule:

1. Increment the shared local daemon protocol version.
2. Update protocol snapshot/hash tests.
3. Update minimum supported client protocol versions only when needed by the
   client behavior.
4. Add focused drills that exercise the changed protocol behavior.

State additions:

- `AgentRole`: `standard` or `meta`.
- Session/user projection helpers for "current user's metaagent".
- Metaagent event inbox records.
- Metaagent event subscription records.
- Metaagent command and event audit/provenance records.

## Spawn And Placement Rules

Agent/session creation requests should accept an explicit metaagent intent, for
example `metaagent: true`.

Kernel enforcement:

- Reject creation when the same user already has a metaagent in the session.
- Reject metaagent placement in a slice.
- Allow metaagent placement on a remote worker kernel.
- Preserve normal provider/model/variant/profile behavior.
- Mark restored/imported agent state with the correct role.

Client behavior:

- Clients may hide disabled options, but the kernel is the authority.
- Clients should surface kernel rejection messages directly when a metaagent
  cannot be created.

## Runtime MCP Tool Surface

Meta runtime MCP tools are exposed only to the current user's metaagent.
Non-meta agents must not see these tools in runtime MCP spec generation.
Dispatch must also reject guessed calls from non-meta agents.

Tools:

- `arroba.meta.session_overview`
- `arroba.meta.search_commands`
- `arroba.meta.list_commands`
- `arroba.meta.command_docs`
- `arroba.meta.run_command`
- `arroba.meta.list_events`
- `arroba.meta.read_event`
- `arroba.meta.ack_event`
- `arroba.meta.turn_overview`
- `arroba.meta.turn_blob`
- `arroba.meta.subscribe_events`
- `arroba.meta.unsubscribe_events`
- `arroba.meta.list_subscriptions`
- `arroba.meta.resolve_runtime_interaction`

### `arroba.meta.session_overview`

Returns a compact, current session snapshot so the metaagent does not need to
remember all session structure across compaction or large multi-agent sessions.

Payload should include:

- session id/ref, owner, current user id, workspace/worktree summary.
- metaagent id/ref for the current user.
- number of agents by user and status.
- current user's agents with id, ref, alias, provider, model, status, placement,
  worktree, active/queued prompt state, workflow participation, and recent turn
  refs.
- workflow definitions and active runs with status and latest output refs.
- pending interactions visible to the metaagent.
- event inbox counts by kind and ack state.

### Command Discovery

Command discovery must be backed by a shared command registry, not handwritten
docs that can drift from enforcement.

Command metadata:

- name and aliases.
- usage.
- examples.
- tags.
- scope: `session`, `global`, or `external`.
- mutates: boolean.
- metaagent policy: `allow`, `approval`, or `deny`.
- user/collaboration authority requirements.

`search_commands` searches names, aliases, usage, examples, tags, and safety
metadata. `list_commands` supports filtering by tag, scope, mutation, and policy.
`command_docs` returns exact docs for one command.

### `arroba.meta.run_command`

Runs one allowed Arroba command within the metaagent's containing session and
current user's authority.

Rules:

- Bind command context to the containing session.
- Reject `session new`.
- Reject attach/use of another session.
- Reject deleting the containing session.
- Reject cross-session targeting flags.
- Reject commands that target another user's non-workflow agents.
- Reject adding a metaagent as a workflow node.
- Preserve normal command-specific permission behavior.
- Record provenance for every command and result.

The existing shell `prompt` command is the primary metaagent-to-agent
communication path:

```text
prompt agent-2 "Investigate this and report back" --wait
```

This must route through the same prompt submission path as TUI, web, and shell
prompts.

There is no metaagent-specific Arroba program runner. If an agent needs to run an
Arroba shell program, it can invoke the normal shell/CLI from its provider shell
tools.

## Command Mutation Audit

Before broad enablement, classify each command one by one.

Default classes:

- Allow: list, inspect, show, status, history, recall, session overview.
- Allow within owner scope: prompt, agent spawn/delete/focus/config for the
  current user's agents.
- Allow for workflows: workflow create/edit/run/cancel/resume/observe, subject to
  normal workflow policy.
- Approval or configured allow: publishing, deployment, external connector
  writes, credential/vault mutations, machine/relay changes.
- Deny: session creation, cross-session attach/use, containing session deletion,
  workflow node membership for metaagents, resolving own interactions.

The command registry's policy must drive both docs and `run_command`
enforcement.

## Events And Prompt Injection

Metaagent awareness is prompt-first.

Before implementing metaagent event steering, characterize current Arroba
midturn prompt behavior for Codex, OpenCode, and Claude. The implementation must
not assume provider steering semantics that the current Arroba adapters do not
actually provide.

Current provider matrix: see `docs/M23_METAAGENTS_PROVIDER_STEERING.md`.

Required provider characterization:

- Submit a second prompt to a running agent through Arroba for each provider.
- Record whether the provider steers the active turn, queues the prompt for the
  next turn, rejects it, or produces mixed behavior.
- Record whether the behavior differs for normal prompt submission, native TUI
  prompt submission, and provider-specific control APIs.
- Record what transcript/history shape Arroba observes for the midturn prompt.
- Record whether cancellation, permission prompts, and runtime MCP calls interact
  safely with midturn prompt delivery.
- Use the results to define the adapter behavior that metaagent event prompts
  can rely on for each provider.

For every matching event:

```text
kernel event
-> record metaagent event
-> centralized prompt injection creates a runtime-origin event prompt
-> provider receives it through normal prompt/steering input
```

If the metaagent is idle, the prompt starts a turn. If the metaagent is already
running, Arroba injects the event prompt through the provider behavior validated
for that adapter. The intended behavior is steering the active turn when the
provider supports it; if a provider only queues safely, the metaagent plan must
record that provider-specific limitation and adapt event ordering, transcript
projection, and drills accordingly.

Missing or failed provider runs are not a normal delivery mode. They are liveness
faults:

- record the event.
- attempt provider recovery/resume/launch.
- inject pending event prompts after recovery.
- surface failure if recovery cannot happen.

Event prompts must include enough inline content for deterministic awareness.

For small text events, include the actual summary/body inline. For large or
structured payloads, include:

- event kind.
- source refs.
- type/content type.
- title.
- short preview.
- event id.
- exact detail refs for `read_event`, `turn_overview`, or `turn_blob`.

Do not inject vague prompts such as "3 events are available" as the only
notification.

## Required And Optional Events

Non-removable required subscriptions:

- Completion of every turn by the current user's non-meta agents.
- Failure of every turn by the current user's non-meta agents.
- Popup/runtime requests from the current user's regular agents when policy lets
  the metaagent answer them.
- Permission requests from the current user's regular agents when those agents
  are not in yolo mode.

Optional subscriptions:

- workflow run started/completed/failed/cancelled.
- workflow intermediate output.
- workflow final output.
- runtime MCP/tool call events.
- extension grant changes.
- slice state changes.

Agent spawned/deleted notifications should be emitted only when the user or some
other non-meta actor performs the action. The metaagent does not need a prompt
notification for agent spawn/delete actions it initiated itself; the command
result is already its acknowledgement.

## Meta Event Inbox

The inbox is storage, replay, and detail retrieval. It is not the primary
awareness mechanism.

Event records:

- monotonically increasing sequence.
- event id.
- kind.
- source user/agent/workflow/tool/interaction refs.
- inline summary.
- content type and preview.
- detail refs.
- injected timestamp/status.
- read timestamp.
- ack timestamp.

Tools:

- `list_events`: list by status, kind, source, and sequence.
- `read_event`: read full event detail.
- `ack_event`: ack by event id or sequence range.

Ack is for bookkeeping and replay control. It must not be required for the
session to keep progressing.

## Trace Observability

The metaagent needs compact and drill-down views of other agents' turns.

### `arroba.meta.turn_overview`

Inputs should allow:

- `agent_ref` plus `turns_back`.
- explicit `turn_ref`.
- optional item limits.

Output should include ordered emitted items:

- assistant messages.
- reasoning/trace entries when available and allowed.
- tool calls.
- tool results.
- provider status/error entries.
- blob ids and titles.
- compact summaries/previews.

This is an overview of the whole turn trace, not only the final assistant
message.

### `arroba.meta.turn_blob`

Returns exact content for a selected blob when allowed by policy:

- assistant message text.
- tool call args.
- tool result output.
- provider error/status detail.
- reasoning trace if Arroba has it and policy allows it.

## Runtime Interactions, Permissions, And Popups

`arroba.meta.resolve_runtime_interaction` is for allowing a metaagent to answer
kernel-owned runtime interactions on behalf of the user for regular agents.

Examples:

- approve or deny a provider permission prompt for a regular agent.
- answer a popup/request from a regular agent that asks the user for input.
- resolve a runtime interaction created by an extension or provider tool call.

Rules:

- The metaagent may resolve interactions for the current user's regular agents
  when policy allows it.
- The metaagent can never resolve its own interactions.
- Human clients can always resolve interactions.
- If a regular agent is not in yolo mode, permission prompts remain mandatory;
  the metaagent may answer them if allowed, but the prompt must still exist as a
  kernel-owned `RuntimeInteraction`.
- Popup/request interactions from regular agents should also be mandatory and
  visible to the metaagent so it can answer as the user.
- Every metaagent resolution records provenance: resolver kind, metaagent id,
  target agent id, interaction id, decision/input, and timestamp.

No self-resolution API or config should exist. Users who want the metaagent to
operate without its own permission friction should run the metaagent in yolo
mode.

## Workflow Boundary

Metaagents supervise workflows from above.

Allowed:

- create workflows.
- edit workflow graphs.
- configure nodes/endpoints/watchdogs.
- run/cancel/resume workflow runs.
- observe workflow events and outputs.
- publish/deploy workflows when command policy allows it.

Denied:

- adding a metaagent as a workflow node.
- scheduling workflow turns to a metaagent.

Reason: workflows are structured execution graphs, while metaagents are
session-level coordinators with authority over commands, prompts, events, and
observability. Mixing those roles creates recursion and unclear completion
semantics.

## Slice And Remote Boundary

Metaagent placement:

- local non-slice provider run: allowed.
- remote worker kernel provider run: allowed.
- slice provider run: denied.

Metaagent slice management:

- may list and inspect slices.
- may save/reboot/shut down slices when policy allows.
- may manage agents running in slices through the normal kernel command path.
- must not become slice-local authority.

Remote behavior:

- home kernel remains session authority.
- worker kernel hosts execution only.
- meta tools must respect home-owned user/session authority.
- relay remains opaque transport.

## Prompt Injection Requirements

Add a metaagent event prompt template to the prompt registry.

The prompt assembly/injection service must own:

- event prompt text.
- hidden runtime instructions.
- event refs.
- selected compact inline event details.
- available meta MCP tool reminders.
- provider-specific hidden-context or steering delivery.

Do not build event prompts ad hoc inside event dispatchers.

Provider-local histories may store injected context in provider-native form, as
with other hidden context. Arroba UI/history must mark runtime-origin prompts
clearly and must not present them as human-typed prompts.

## Audit And Provenance

Record durable provenance for:

- metaagent creation.
- metaagent command execution.
- metaagent prompt submissions.
- metaagent event prompts.
- metaagent event reads/acks.
- metaagent runtime interaction resolutions.
- denied metaagent operations.

Records should include session id, user id, metaagent id, provider run id when
known, command/tool/event/interaction ids, causation id, correlation id, and
timestamp.

## Acceptance Criteria

- Metaagents are ordinary provider agents plus a role-scoped runtime MCP surface.
- One metaagent per collaborator per session is enforced by the kernel.
- Metaagents are visible and clearly marked in TUI/web agent UI.
- Metaagents are excluded from workflow node agent selection.
- Metaagents cannot run in slices but can run on remote worker kernels.
- Metaagents can observe session/workflow state, inspect turns, and prompt owned
  regular agents.
- Metaagents receive deterministic inline event prompt injection for required
  events and subscribed events.
- Metaagents can resolve other owned regular agents' interactions, never their
  own.
- Command docs, search, and enforcement use one command registry.
- Protocol/version tests and TUI/web product drills cover the feature end to
  end.
