Parameterized Workflow Templates Plan

Add first-class input parameters to workflow-code registry templates so built-in and user-registered workflow scripts can generate different graph shapes at creation and run time. The kernel remains the source of truth, and every client uses the same registry, compiler, protocol, and validation path.

Owner: OSS runtime plus Cloud web client Primary surface: workflow registry Requires protocol version bump Validation: TUI, web, runtime MCP
Decision: registry entries become parameterized workflow generators. Loading a template compiles the script with a validated parameter object, applies the generated workflow, and returns the normal session-bearing registry load response. This is the production implementation path, not a staged demo path: every supported surface should use the same kernel-backed behavior.

1. Product Behavior

Goal

A template such as tournament should not be fixed to one final round with two contestants. The same registry entry should be able to generate any supported power-of-two bracket by passing input parameters.

Implement tournament.bracket_size as an integer that must be a power of two, defaulting to 2. A bracket size of 16 generates 16 contestant nodes, 8 first-round judges, 4 second-round judges, 2 semifinal judges, 1 final judge, and 1 seeder. There should be no hard-coded finite enum of allowed bracket sizes. Any power-of-two value is valid as input as long as the generated graph stays within the kernel's normal workflow size and validation limits.

This is not limited to tournament. The implementation must analyze all 10 built-in workflow-code templates and define the minimum useful parameter set for each template that benefits from dynamic generation. Each existing template script must either be updated to generate its graph from inputs or be explicitly left static because the analysis shows no meaningful input variable is needed.

Success Criteria

  • Static workflow-code templates keep working without parameters.
  • Parameterized registry metadata is visible through list/get APIs.
  • CLI/TUI, web, and runtime MCP can all pass the same parameter bag.
  • Invalid input fails before the workflow is created or run.
  • Built-in and user-registered workflow scripts use the same mechanism.

2. Kernel And Protocol Changes

Workflow-code compiler API

  • Extend the compiler input with parameters: Record<string, JsonValue>.
  • Add workflow.parameters({ schema }) to the JavaScript builder. It registers the parameter schema and returns the resolved parameter values for script generation.
  • Support a small JSON Schema subset: top-level type: "object", properties, required, default, minimum, maximum, multipleOf, title, and description. Keep enum support for naturally enumerated options, and add a kernel-recognized integer validation extension for power-of-two values so tournament bracket size is not modeled as a fixed enum list.
  • Apply defaults and validate values inside the kernel/compiler path before emitting a workflow definition. Unsupported schema shapes fail clearly.

Registry metadata

  • Extend WorkflowRegistryEntryMetadata with parameters_schema?: JsonValue.
  • Build registry list/get summaries by compiling with default parameters.
  • Include parameter values in durable workflow-code apply/run audit events and metaagent registry events.

Serialized protocol

  • Extend LoadWorkflowRegistryEntryRequest with optional parameters.
  • Extend RunWorkflowRegistryEntryRequest with optional parameters.
  • Update the kernel-client request helpers and generated TypeScript types in OSS and Cloud web.
  • Increment LOCAL_DAEMON_PROTOCOL_VERSION and update protocol shape/hash tests per the repo protocol change rule. 
workflow.define({ alias: "pattern-tournament", maxConcurrent: 32 });

const params = workflow.parameters({
  schema: {
    type: "object",
    properties: {
      bracket_size: {
        type: "integer",
        minimum: 2,
        xPowerOfTwo: true,
        default: 2,
        title: "Bracket size"
      }
    }
  }
});

const bracketSize = params.bracket_size;

3. Client And Runtime MCP Changes

Surface Required behavior
CLI / TUI slash commands Add --input key=value and --inputs-json '{...}' to /workflow load and /workflow run. Parse booleans, numbers, and JSON literals; otherwise keep values as strings. Show parameters_schema in /workflow registry get.
Cloud web terminal Extend the new create-template dropdown. If a selected template has a parameter schema, open a compact modal/popover form before loading. Render enum, boolean, number/integer, and string controls. Submit passes parameters to LoadWorkflowRegistryEntry; validation errors stay inline.
Runtime MCP for metaagents Extend chariox.meta.workflow_registry.list/get responses with parameters_schema, and extend chariox.meta.workflow_registry.load/run tool schemas with parameters. Tool descriptions should instruct metaagents to inspect schemas and pass required parameters.
Command center suggestions Continue suggesting registry entries. Do not add a separate interactive parameter editor in TUI command center unless it can use the same schema contract as the slash commands. The typed flags are the source of truth for TUI.

4. Template Implementation

  • Convert examples/workflow-code/tournament.js to generate bracket rounds from bracket_size.
  • Use deterministic handles and labels, such as contestant_01, round_1_judge_01, and final_judge.
  • Keep canvas coordinates deterministic and readable for generated brackets.
  • Analyze all 10 built-in workflow-code templates: prompt-chaining, routing, fan-out-synthesize, parallelization, adversarial-verification, generate-filter, tournament, loop-until-done, orchestrator-workers, and evaluator-optimizer.
  • For each built-in, define the minimum useful set of variables needed to generate the workflow dynamically for realistic use cases. Update every script whose topology or node count should vary; only keep a script static when the analysis shows that no meaningful input variable is needed.
  • Treat tournament as the reference case, not the only case. Other templates may need variables such as worker count, branch count, retry limit, evaluator count, or loop limit depending on the existing script's pattern and realistic user needs.

5. Validation Plan

Kernel and protocol

  • Compile parameterized workflow-code with default and explicit parameters.
  • Reject missing required values and invalid enum values before session mutation.
  • Assert tournament bracket_size=4 produces 4 contestants, 2 semifinal judges, 1 final judge, 1 seeder, expected edges, and 1 endpoint.
  • Assert a larger power-of-two bracket such as bracket_size=16 produces the expected round counts without hard-coded enum handling.
  • Reject non-power-of-two and oversized bracket sizes before session mutation.
  • Assert registry list/get includes parameter schema metadata.
  • Update protocol snapshot/hash tests and version bump.

CLI / TUI e2e

  • Add shell executor tests for /workflow load tournament --input bracket_size=4.
  • Add shell executor tests for /workflow run tournament --input bracket_size=4 --endpoint entry --prompt "...".
  • Add or extend a real PTY TUI drill that launches a local kernel and TUI, runs the load command, waits for the workflow screen/session snapshot, and asserts generated workflow shape.

Web product frontend

  • Extend the Freeform and Workflow sidebar browser drills: select tournament, see the parameter form, choose bracket_size=4, and verify the created canvas node/edge/endpoint counts.
  • Add failure drill for invalid bracket_size=3: inline error appears and the current workflow route does not change.

Metaagent runtime MCP

  • Unit test runtime MCP tool schemas include parameters.
  • Dispatch test chariox.meta.workflow_registry.load with { "bracket_size": 4 } and assert the generated workflow shape.
  • E2E metaagent drill: metaagent lists registry entries, reads tournament schema, loads it with bracket_size=4, and final evidence confirms the workflow exists with the expected generated graph.

6. Assumptions And Boundaries

  • Parameterized registry load/run is required. Saving a filled-out parameter preset as a new registry entry is out of scope for this plan.
  • Parameters are JSON-compatible and non-secret. Do not use this path for credentials or private tokens.
  • Web uses simple schema-derived controls, not a general-purpose JSON Schema form engine.
  • Existing static templates and user registry entries remain compatible because parameters_schema and parameters are optional.
  • Core behavior belongs in the kernel and shared protocol; client-only parameter handling is not acceptable except as display logic.
