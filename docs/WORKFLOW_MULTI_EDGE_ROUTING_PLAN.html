Arroba kernel implementation plan

Workflow Multi-Edge Routing

This plan covers the immediate prompt and validation work needed before workflow-code generation depends on multi-edge nodes. It does not implement workflow-code artifacts, schema refactors, or metaagent workflow-code MCP endpoints.

Goal: make the existing runtime routing contract explicit to workflow nodes, then prove fan-out, conditional routing, loop routing, and schema validation with focused drills.

Current State

The runtime already supports conditional workflow routing. When a node's output.message is JSON with a non-empty workflow_handoffs array, downstream completion selects only matching edges. A route may match by edge_id or to_node_id. Without workflow_handoffs, the existing behavior fans out the same output to every outgoing edge.

The prompt layer is weaker than the runtime. It lists outgoing edge contracts and tells the agent to return one output.message, but it does not explain the workflow_handoffs routing shape. That makes conditional fan-out possible but under-taught.

Step 1: Extend Workflow Turn Prompt

Update the bundled workflow turn template in apps/kernel/src/prompt_assembly.rs. The new text should teach routing without introducing edge predicates.

Required Prompt Contract

  • If output.message is plain text or JSON without workflow_handoffs, the runtime sends the same handoff to every outgoing edge.
  • If output.message is JSON with a non-empty workflow_handoffs array, the runtime sends handoffs only to matching edges.
  • Each handoff may target one edge with edge_id or one target node with to_node_id.
  • Each routed handoff may provide summary and either output.message or top-level message.
  • A null routed message suppresses output for that route.
  • If a selected edge has a handoff_schema_ref, the routed message for that edge must pass validate_workflow_handoff before finalizing.

Prompt Example

{
  "summary": "Routed implementation task to reviewer",
  "output": {
    "message": {
      "workflow_handoffs": [
        {
          "edge_id": "edge_123",
          "summary": "Review implementation details",
          "output": {
            "message": {
              "task": "review",
              "files": ["apps/kernel/src/session/service/turns.rs"]
            }
          }
        }
      ]
    }
  }
}

Step 2: Improve Outgoing Edge Contracts

Update workflow_outgoing_edge_contracts_block in apps/kernel/src/scheduler/prompt_injection.rs so the prompt includes target labels when available. Keep ids authoritative; labels are only readability hints.

Before After
- edge edge_123 -> node_456, handoff_schema_ref: /tmp/review.json, validation_policy: halt - edge edge_123 -> node_456 (Reviewer), handoff_schema_ref: /tmp/review.json, validation_policy: halt

Mirror this in apps/kernel/src/runtime/state/workflow_turn_prompt_owned_state.rs if that state-owned prompt path remains active. The two prompt construction paths should not drift.

Step 3: Tests And Drills

Unit Tests For Routing Primitive

Add focused tests around the current edge-completion behavior in apps/kernel/src/session/service/turns.rs.

Case Expected result
No workflow_handoffs All outgoing edges receive the same output.
One handoff with edge_id Only the matching edge receives output.
One handoff with to_node_id Only edges targeting that node receive output.
Handoff message is null The route is suppressed and no downstream message is emitted for that edge.
Invalid JSON or plain text output.message Existing fan-out behavior is preserved.

Prompt Assembly Tests

  • Assert the hidden workflow prompt includes workflow_handoffs, edge_id, to_node_id, and fan-out fallback language.
  • Assert outgoing edge contracts still include edge ids, target node ids, handoff schema refs, and validation policy.
  • Assert target node public labels appear when configured.
  • Assert prompt registry overrides still work, so custom prompt templates are not broken by the new bundled default.

Drill: Two-Edge Conditional Route

Build a workflow with one router node and two downstream worker nodes. 

router
  |--> worker_a
  |--> worker_b
  1. Run with a dev-stub router that returns workflow_handoffs selecting only worker B by edge_id.
  2. Assert worker B receives a node run and worker A does not.
  3. Repeat selecting worker A by to_node_id.
  4. Repeat with no workflow_handoffs and assert both workers receive work.

Drill: Loop Edge

Build a loop workflow where synthesis can route back to intake when revision is needed. 

intake --> worker --> synthesis
  ^                       |
  |-----------------------|
  1. Run a prompt that makes synthesis request revision.
  2. Assert synthesis emits a routed handoff to the loop edge only.
  3. Assert intake receives the loop handoff and starts another node run.
  4. Assert no unrelated outgoing edge fires during the loop route.

Drill: Selected-Edge Schema Validation

Build a router with two outgoing edges that use different handoff schemas.

  1. Select edge A and emit payload valid for A but invalid for B.
  2. Assert validation only requires edge A's schema because edge B is not selected.
  3. With validation_policy: halt, assert an invalid selected payload blocks the turn.
  4. With validation_policy: warn, assert the warning is recorded and the runtime follows the existing warning policy.

Acceptance Criteria

  • Workflow nodes can read the prompt and know how to choose one outgoing edge, several outgoing edges, or all outgoing edges.
  • Conditional routing remains a node action via workflow_handoffs; no edge predicate system is introduced.
  • Edge contracts are readable enough for agents to choose routes without searching the workspace for workflow metadata.
  • Unit tests lock current fan-out fallback behavior and selected-route behavior.
  • Drills prove conditional route, fan-out, loop routing, and selected-edge schema validation end to end.
