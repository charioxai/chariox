Recovery Contract

Failure Expected Behavior Hard Failure Condition
Browser, TUI, or kernel websocket drops Reconnect with backoff, resubscribe from last event id, replay missed events, keep transcript and prompt state. Lost prompt, duplicated completion, stale pending state, or transcript reset.
Relay process drops and restarts Kernel, browser, TUI, and workers reconnect and re-register; stale relay subscriptions close and recover. Dead subscription socket, stale target selected, or active turn marooned.
Home kernel restarts Durable session, agents, grants, history, prompt delivery state, provider resume state, and remote bindings restore. State loss, wrong authority path, duplicate provider submission, or unreconciled active prompt.
Worker kernel or slice worker restarts Home detects stale lease, selects fresh worker presence, repairs binding, and continues through the kernel-owned prompt path. Old lease remains active, worker output disappears, or session forks into a parallel authority path.
Cloud API or web server restarts Browser keeps runtime transcript state, refreshes bootstrap/token when needed, and continues via relay after service returns. Cloud becomes hot-path proxy, browser loses session, or token refresh cannot recover cleanly.
Provider process exits or kernel dies mid-turn Resume provider thread when provider resume state supports it; otherwise surface a structured recoverable retry state. Silent corruption, duplicated prompt, hidden failed state, or stale active provider run.
Collaborator disconnects Other participants continue; reconnecting collaborator catches up without gaining extra authority or losing visibility. Authority widening, missing transcript, duplicate prompt, or private state leak.

Local And Hetzner Setup

Local Isolated Runtime

  • Use unused ports for relay, home kernel, worker kernel, Cloud API, web server, MCP, Codex, and OpenCode ports.
  • Use temporary HOME, XDG_CONFIG_HOME, XDG_STATE_HOME, daemon sockets, and history dirs per run.
  • Run local relay and kernels directly from the current checkout.
  • Do not disturb shared staging or developer-owned services during destructive local chaos tests.

Hetzner Remote Runtime

  • Use the configured Hetzner machine for remote worker and collaborator scenarios.
  • Prepare a run-id-scoped remote root, workspace, home, state, runtime, and session-history directories.
  • Verify remote checkout version, build artifacts, provider auth readiness, disk space, and free ports before running live provider turns.
  • Always delete run-owned remote roots and terminate run-id-tagged kernel/provider processes on success.
