Connectivity Reliability Plan

A plan for making Arroba stable when connected, graceful when disconnected, and self-healing across Cloud, relay, kernel, browser, TUI, worker, and provider boundaries without exposing the complexity to users.

Operating principle

Connectivity and efficiency come first. Cloud bootstraps. Relay routes. Kernel owns runtime truth. Clients recover quietly.

1

Runtime Authority

The kernel remains authoritative for sessions, prompts, provider runs, history, and recovery.

2

Transport Only

The relay admits scoped peers and forwards opaque encrypted packets. It does not inspect runtime payloads.

3

Recoverable Commands

Every user action that can cross a broken socket needs a stable command id and durable reconciliation.

4

Chaos Proof

CI and drills must kill each layer mid-turn and prove no duplicate prompts, lost turns, or stuck UI.

Target User Experience

The user should see a small number of states: Connected, Reconnecting, Resyncing, and Action needed. Drafts, selected session, pending prompt state, and visible transcript should survive ordinary disconnects. Users should not need to know whether Cloud, relay, kernel, worker, or the browser event socket caused the disruption unless the next action is different.

Reliability Gaps

State Recovery

  • In-flight browser control requests are rejected on socket close instead of reconciled automatically.
  • Kernel command result dedupe is in-memory and limited to 512 entries.
  • Event bodies are retained in a small in-memory window, so longer disconnects fall back to replay gaps and snapshots.
  • Relay registry, pending requests, and subscriptions are in-memory, so relay HA requires clean client and kernel rebootstrap.

Liveness Isolation

  • The kernel relay heartbeat loop also does token refresh checks, inventory refresh scheduling, leased projection pumping, and Cloud presence publishing.
  • Slow consumers are closed correctly, but control, ping, and terminal deltas still need clearer priority lanes.
  • Cloud presence relies on kernel writes plus freshness, but should be resilient when explicit offline writes fail.
  • Remote worker rebind and lease recovery need a first-class lifecycle, not ad hoc operator repair.

Landed Hardening Baseline

Relay And Endpoint Recovery

  • Relay liveness stays healthy during drain while readiness reports draining and exposes runtime load counters.
  • Draining relays refuse new runtime admissions with HTTP 503 and Retry-After in headers and JSON bodies while health checks keep returning drain status.
  • Relay endpoint configuration accepts explicit health states and rejects unsupported states at startup/readiness.
  • Cloud treats configured relay endpoint sets as authoritative and ranks them by health so healthy alternates precede draining or stale relay URLs.
  • Cloud readiness and browser bootstrap fail closed before token minting when configured endpoint sets have no relay that admits new runtime sockets.

Client And Authority Recovery

  • Browser bootstrap treats non-empty Cloud relay endpoint sets as authoritative instead of appending legacy URLs.
  • Browser bootstrap filters draining, stale, offline, and revoked relay endpoints out of reconnect candidates.
  • Browser reconnect skips cooling relay endpoints when any non-cooling alternate is available.
  • Browser relay handshake failures close their provisional WebSocket immediately so malformed relay frames cannot leave orphaned connections behind.
  • Browser event reconnect skips subscriptions removed during async resume so closed views do not receive stale recovery events.
  • Browser token refresh is best effort before actual expiry, so temporary Cloud outages do not block reconnect while the current relay token is still valid.
  • Browser control replay keeps stable command IDs and restores pending state when a replay send fails before leaving the socket.
  • Authority invariant summary gates cover Cloud and OSS runtime boundaries so relay and Cloud stay out of kernel-owned runtime truth.

Reference Architecture

Keep the existing authority boundary, but add durable recovery contracts and isolated liveness lanes around it.

Client Browser, local TUI, remote TUI, iOS, Android. Owns drafts and reconnect UI.
Cloud Auth, tokens, membership, relay endpoint set, target freshness.
Relay Scoped admission, opaque packet routing, drain and HA signals.
Kernel Durable command ledger, event log, sessions, agents, provider state.
Worker Remote or slice execution, leases, provider adapters, home rebind.

Implementation Plan

Phase 1

Durable Kernel Recovery

Add a persistent transport command ledger keyed by stable command id. Store fingerprint, status, response or error, first accepted time, settlement marker, session, attachment, and agent. Add command.status and make duplicate requests return the known result or an accepted-observe-events state.

  • Persist command ids for create, attach, launch, prompt, cancel, workflow, and mutation requests.
  • Make browser and TUI retry through command status, not blind resubmission.
  • Use protocol version and snapshot tests if serialized shapes change.
Phase 2

Durable Event Replay

Replace short in-memory event body retention with a bounded persistent event log per session and attachment. Keep event IDs monotonic across restarts and retain enough bodies for normal offline periods.

  • Retain by bytes and time, for example 24 hours or 50 MB per active session.
  • Keep replay gaps as a fallback, not the common path.
  • Rebuild terminal deltas from history where possible before falling back to snapshots.
Phase 3

Liveness Lane Split

Separate socket liveness from application work. Heartbeats, pings, pongs, close frames, and minimal registration updates must not wait on Cloud presence, provider pumping, inventory refresh, workspace sync, or long app locks.

  • Create dedicated actors or queues for socket liveness, presence, event projection, command dispatch, and inventory refresh.
  • Make Cloud presence publish best effort and jittered.
  • Prioritize ping, close, subscribe ack, and command response frames over terminal deltas.
Phase 4

Unified Client Supervisor

Browser and TUI clients need one supervisor that owns bootstrap, control socket, event socket, token refresh, pending command reconciliation, subscription resume, target drift, and user-facing status.

  • Persist pending command ids locally until resolved or reconciled.
  • Resubscribe before replaying pending command reconciliation.
  • Expose only connected, reconnecting, resyncing, and action-needed states to UI.
Phase 5

Relay HA And Drain

Cloud should return a relay endpoint set instead of a single URL. Relay nodes should publish healthy, degraded, and draining status. Tokens should remain scoped to a realm and be accepted across that realm's relay pool.

  • Add endpoint ranking by region, freshness, drain state, and failure history.
  • Make clients and kernels reconnect to another relay without user action.
  • Keep relay stateless with respect to runtime truth.
Phase 6

Remote Worker Rebind

Persist home-worker lease binding, active worker provider run id, prompt delivery state, last projected runtime state, and manifest sync state. On reconnect, rebind before accepting new prompts to that remote agent.

  • Mark remote agents degraded while worker state is unknown.
  • Block new prompts with a precise recovery action when rebind fails.
  • Automatically sync remote extension manifests after worker reconnect.

Test Layers

Unit And Contract Tests

  • Durable command ledger returns identical results for duplicate command ids.
  • Command id conflict rejects a reused id with a different fingerprint.
  • Event replay survives kernel restart and reports gap only outside retention.
  • Heartbeat loop keeps schedule when Cloud presence publish hangs.
  • Slow consumer close does not block ping, close, subscribe ack, or command responses.
  • Cloud target selection rejects stale, revoked, draining, and missing-heartbeat targets.
  • Browser supervisor coalesces reconnect attempts and refreshes bootstrap once.

End-To-End Drills

  • Local browser, local relay, local kernel, dev-stub provider, event socket kill.
  • Hosted Cloud bootstrap, hosted relay, local kernel, Cloud API outage after bootstrap.
  • Remote TUI through relay with relay restart and retained event replay.
  • Remote worker leased agent prompt with worker kill and rebind.
  • Slice-backed native TUI with relay interruption and extension manifest resync.
  • Two-user shared session with member token refresh and non-member denial during reconnect.
  • Relay HA endpoint rotation from draining relay to healthy relay.

Operational Metrics

Reconnect

Time from close to subscribed, attempts, selected relay endpoint, token refresh time, and failure reason.

Replay

Last cursor, replayed count, gap count, snapshot fallback count, retained bytes, and oldest retained event age.

Backpressure

Queue depth, overflow count, slow-consumer close count, dropped/coalesced snapshot count, and priority-lane latency.

Presence

Kernel heartbeat age, Cloud publish latency, relay endpoint health, drain status, and stale target selection denials.

Sequencing

  1. Land durable command ledger and command status, because it prevents duplicate user actions after any control-socket failure.
  2. Land durable event replay, because it turns most reconnects into exact replay instead of snapshot repair.
  3. Split liveness lanes, because heartbeat starvation is the fastest path to unnecessary WebSocket disconnects.
  4. Unify browser and TUI reconnect supervisors around the same recovery vocabulary.
  5. Add remote worker rebind and manifest resync recovery.
  6. Add relay endpoint sets, drain, and HA rotation after the single-relay chaos drills are green.

Scope note: this plan intentionally keeps Cloud as bootstrap and control plane only. Any protocol shape changes must follow the repository protocol change rule: version bump, snapshot/hash tests, client minimum version update where needed, and focused drills.
