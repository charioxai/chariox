# Customer-managed infrastructure provider research

Status: research note, 2026-09-01. Sources are first-party provider documentation and APIs.

## Recommendation

Build one provider-neutral machine contract, but ship providers in this order:

1. **DigitalOcean**. It has the smallest clean control plane, scoped API tokens, project roles, cloud-init, private-only machines, Cloud Firewalls, snapshots, and reserved IPs.
2. **Hetzner Cloud**. It is similarly small and inexpensive. Project-bound tokens give a useful isolation boundary, though a read/write token is broad inside that project.
3. **AWS EC2**. It has the best third-party delegation pattern through cross-account roles and the broadest customer demand. Its resource graph and IAM policy are much more work than the first two.
4. **Google Compute Engine**. Workload Identity Federation and service-account impersonation avoid static keys. The VM model is coherent once Chariox standardizes projects, zones, networks, and startup metadata.
5. **Azure Virtual Machines**. Azure RBAC can confine a Chariox service principal to one resource group. Provisioning and cleanup involve more separate resources than GCE or EC2.
6. **Scaleway Instances**. Good API, SDK, CLI, IAM application, policy, private networking, and cost behavior. It is a strong European option after the first five.
7. **Akamai Cloud, formerly Linode**. Capable and well documented, including OAuth for third-party applications. Region-dependent VPC and image behavior needs more testing than the providers above.
8. **Vultr**. The VM API is compact and now has granular IAM actions, but API-key IP allowlisting and account-user setup make hosted onboarding less smooth.
9. **OVHcloud Public Cloud**. It can do everything required through OpenStack and OVHcloud APIs. The split control planes, regional feature differences, and more involved credentials make it a later adapter.
10. **Oracle Cloud Infrastructure**. OCI has excellent IAM and complete APIs, but its tenancy, compartment, image, VCN, shape, and capacity rules create the largest integration and support burden here.

Treat **Hostinger VPS as experimental and separate**, not as tier 3 of the same abstraction. Its API is still beta, credentials inherit the owning user's permissions, networking is fixed, and a VPS is a prepaid subscription rather than an ephemeral usage-billed VM.

Suggested support tiers:

| Tier | Providers | Product promise |
| --- | --- | --- |
| Tier 1 | DigitalOcean, Hetzner Cloud, AWS EC2 | Supported provisioning, repair, snapshot, and deletion workflows with provider-specific least-privilege onboarding. |
| Tier 2 | Google Compute Engine, Azure VMs, Scaleway | Supported after end-to-end credential and orphan-cleanup drills. |
| Tier 3 | Akamai/Linode, Vultr, OVHcloud, OCI | Preview adapters. Expect region, quota, and account-setup limitations. |
| Separate experiment | Hostinger VPS | Manage a customer-purchased subscription. Do not promise elastic create/delete economics or network parity. |

## Common adapter contract

The practical shared contract is smaller than any provider API:

* Resolve an Ubuntu image compatible with the target architecture and first-boot mechanism.
* Create, inspect, start, stop or deallocate, reboot, and delete a machine.
* Inject one or more SSH public keys and a non-secret cloud-init or startup payload.
* Attach a deny-by-default network firewall, a private network when supported, and either no public address or one stable public address.
* Create and restore an image or snapshot, while recording whether the provider snapshots a disk, boot volume, or whole machine.
* Tag or label every owned resource with a Chariox deployment ID.
* Discover and delete the complete resource graph, including disks, NICs, public IPs, firewall objects, and snapshots that outlive the VM.

Do not put relay tokens, provider credentials, or other long-lived secrets in user data. Several providers expose user data through instance metadata or control-plane reads. Bootstrap with a short-lived, single-use Chariox enrollment token instead.

## Hostinger VPS, separate assessment

Hostinger now has more automation than its old hosting-panel reputation suggests. The beta API and official `hapi` CLI can list, start, stop, restart, recreate, and inspect VPS instances. The billing API can order a VPS product, after which the VPS setup endpoint selects the data center, OS template, SSH public key, firewall, and post-install script. It also exposes OS templates, public keys, one VPS snapshot with create, restore, and delete operations, network firewalls, assigned IP addresses, metrics, backups, and recovery mode. See the [API reference](https://developers.hostinger.com/), [official CLI guide](https://support.hostinger.com/en/articles/11679133-how-to-use-hostinger-api-cli), and [post-install scripts](https://support.hostinger.com/en/articles/11080657-using-post-install-scripts-with-hostinger-api).

The gaps matter for Chariox:

* The API is explicitly beta. A token has the same permissions as its owning user and can only add an expiry. There is no documented VPS-specific scope, project boundary, service principal, delegated application flow, or IP allowlist. See [API authentication](https://developers.hostinger.com/) and [beta status](https://support.hostinger.com/en/articles/10840865-what-is-hostinger-api).
* VPS plans expose one IPv4 and one IPv6. The API documents address inspection and reverse DNS, not customer VPCs, private-only machines, floating or reserved IPs, extra NICs, or subnet controls. See [VPS plan limits](https://support.hostinger.com/en/articles/6976044-parameters-and-limits-of-hosting-plans-in-hostinger).
* Post-install scripts provide a useful first-boot hook, but they are saved on the VM and run as root after OS installation. This is not the same lifecycle or metadata contract as generic cloud-init.
* A VPS is purchased as a subscription. KVM VPS billing periods are 1, 12, or 24 months, paid in advance. Stopping the VM does not create cloud-style usage savings. See [Hostinger renewal periods](https://www.hostinger.com/support/1583589-how-to-pay-for-hostinger-services-in-advance/).
* The order API can charge the customer's default payment method. That action needs an explicit purchase confirmation and should never be hidden inside an ordinary machine-create retry.

If supported at all, model Hostinger as `bring an existing Hostinger VPS subscription`, then automate setup and ongoing lifecycle. Do not include it in generic autoscaling, disposable worker, stop-to-save, private-network, or stable-IP guarantees until Hostinger exposes those contracts and scoped credentials.

## Implementation notes

1. Start with direct REST clients even when an SDK exists. Chariox only needs a small stable subset, and direct clients make request IDs, idempotency, retry policy, and protocol logging uniform across providers.
2. Store only a credential reference in Chariox. Prefer temporary federation for AWS and GCP, a federated or certificate-backed service principal for Azure, OAuth for Linode, and provider IAM application or project tokens elsewhere.
3. Require a dedicated customer project, resource group, VPC, or compartment where the provider supports it. Refuse account-root credentials.
4. Make create idempotent around a Chariox deployment tag. Provider APIs are asynchronous and a client timeout does not prove that creation failed.
5. Treat `ready` as successful Chariox enrollment, not merely provider state `running` or `provisioned`.
6. Keep a provider-specific ownership graph. On delete, report retained snapshots and customer-owned network resources instead of silently removing them.
7. Return provider-native price and quota information before creation. Do not normalize away IPv4 charges, stopped-instance rules, minimum billing units, monthly caps, or prepaid subscriptions.
