It folds in Miguel's answers of 11-06 15:23Z, the one-card steer of 15:36Z, the no-takeover decision of 15:48Z and his binding answers of ~16:05Z: a decision card is shown only by the room agent, sub-agents are hidden everywhere (also on another kernel), and the account-profile limit is dropped. Section 7.5 (11-08) answers his question on `agent spawn --room` to another kernel: planned for Landing 6 as slice P5, same owner only. Base: Landing 4 union head `cd799d2e60`, local protocol 999, relay peer 438. Code references are `apps/kernel/src/...:line` at that head. "(owner may overrule)" marks a reading the coordinator or I took.
Words: **top parent** = the room agent at the root of a tree; **sub-agent** = any descendant; **peer** = an agent that is neither ancestor nor descendant; **decision** = a permission or question card; **holder** = who must answer a decision right now; **authority limit** = the most a sub-agent may be given (section 5).

## 1. What we build

The first milestone is **one room agent per room, plus sub-agents** (section 10). In ten lines:

1. One edge, `parent_agent_id`, makes a tree. A room agent spawning in its own room creates a sub-agent; a sub-agent can only create sub-agents.
2. Sub-agents are never listed as normal agents, local or remote: not in a room's agent list or agents view, not in `max_agents`. The user sees them in a folded stripe at the bottom of the top parent's panel, in the card it opens (a hierarchy), and in a sub-view of the room that looks like the agents view and shows status only (section 8).
3. A sub-agent is an ordinary agent runtime. A remote one runs that way on the other kernel, in a hidden home that belongs to its parent edge: no lease, no room there, not listed (7.3).
4. Events reach an agent through its **inbox**: one very short prompt, then the agent reads the events (section 3). This ships first and helps every agent.
5. A sub-agent finishing or needing a decision **steers or wakes the parent at once**. No queued or timed wake.
6. A decision is **one card with one holder** that moves up the tree, parent to user. When it reaches the user, **only the room agent (the top parent) shows it**; a sub-agent's pane never shows a card (section 4).
7. A child never has more authority than its parent, the **authority limit**, checked at spawn and at every control command and answer under the action's lock (section 5). No usage budget.
8. A parent controls its whole subtree without /sudo (section 6).
9. Peers (any agent, any room of the same owner, any kernel) can **message**, **reply**, **subscribe**, **steer** and **cancel** (Miguel, 11-08); they never answer a decision card, read files, run in another's shell, act as the user, delete, set a deadline, list children or reparent. Only room agents create peers (7.2). A message to an agent on another kernel cannot ask for a reply yet: the kernel refuses `reply_requested` there before sending anything, and the agent there answers by messaging the sender back.
10. Everything is event-driven: a parent parks on `events.yield` and the kernel resumes it. Nothing polls.

Assistants are not designed here; the model leaves room for them (7.4). **Removed since round 1:** the lease path, the remote-spawn card, the hop timer, the usage budget, App grants, the history outline, batched completion wakes.

## 2. Data model

**Today.** `spawned_by_agent_id` is an immutable creator receipt (`agent/types.rs:212`, `assert!` at `:339`); `direct_child` gives destructive rights over one level (`runtime/room_tool_admission.rs:29`); Meta mode has an older edge `controlled_by_metaagent_id` (`agent/types.rs:209`).

### 2.1 One edge, hidden from the room
- `parent_agent_id: Option<AgentRef>` replaces `spawned_by_agent_id` and `controlled_by_metaagent_id`. `AgentRef` is `{agent_id}` locally and `{kernel_id, agent_id}` when the parent lives on another kernel. Depth and root are derived by walking up.
- Spawn sets the edge once, from the spawner's current provider run (`runtime/state/room_agent_admission.rs:36-70`). Only a user-only `SetAgentParent { agent, parent | none }` changes it later ("promote", "orphan"). Agents cannot adopt or reparent.
- A local sub-agent keeps the top parent's room id (it needs a worktree, history and interactions) but is filtered from `ListAgents`, the archived list and the snapshot (`runtime/session_read_control.rs:237-246`) and from the counts (`agent/service.rs:97,192`; a spawned agent already skips the `max_agents` check there). Requests by agent id (prompt, steer, cancel, state, streams) still work for hidden ids. A remote sub-agent is hidden the same way and also has no room on its kernel (7.3).
- Caps, all at spawn: depth 4, 16 unfinished children per parent (a child that has had its turn and is idle again, or failed, no longer counts; a deleted one is gone), 64 per tree, remote children included (the owner said ok).

### 2.2 Lifecycle
The edge is stored with the agent and in the `agent.created` event (`agent_lifecycle_owned_state.rs:34-45`), so it survives restart. A subtree ends with its parent: destroy, delete, room end or deadline cascade depth-first as a durable effect with a startup recovery pass (T3 idea). This reverses "Deletion never silently destroys descendants" (`room_agent_admission.rs:187-197`), written for visible workers. For a remote child the delete stays pending and retries until its kernel is reachable (7.3).

## 3. The agent inbox: a short wake, the events in the inbox

The owner asked: *the kernel prompts the agent with a very short message and the agent reads the message from its inbox. Do we have this shape?*

### 3.1 What exists, and what does not
- **Yes, the store and the tools.** Every agent has a durable inbox with sequence numbers (`InboxEvent`, `durable_state/agent_lifecycle/types.rs:107`). Tools: `chariox.events.inbox {after}` (up to 128 events), `ack {sequence, handled}`, `subscribe`, `yield`, `timer`, `blocked` (`tool_dispatch/agent_events.rs:133,205`).
- **No, the delivery.** `deliver_agent_inbox` takes the front event only (one per turn, `agent_lifecycle.rs:352-378`) and puts the **whole payload inline**: `"Kernel event inbox, untrusted data (sequence N, source S). ... {payload} ... Use chariox.events.ack ..."` (`agent_inbox_delivery.rs:187`). So agent-authored text rides inside a kernel prompt, prompts grow with the payload, and three events are three model turns (orchdrill: 0.8-2.7 M cache-read tokens per event).
- Only tools read the inbox (`agent_inbox(` is `#[cfg(test)]`), so no client protocol is involved.

### 3.2 Decision: one fixed short prompt (owner may overrule)
The prompt names counts and kinds only (a kernel enum), never agent-authored text:
- `Inbox: 3 new events (2 child finished, 1 decision) after sequence 37. Read them with chariox.events.inbox, then chariox.events.ack each one you handled.`
- Reply requested, always one message alone: `Inbox: 1 message with a reply requested (sequence 41). Read it with chariox.events.inbox after 40. Your final answer of this turn goes back to the sender; do not send a separate message.`
The "untrusted data" warning moves into the tool result and description.

### 3.3 What `chariox.events.inbox {after, limit}` returns
`limit` default 16, max 64; ordered by sequence; reading changes nothing; each payload is bounded to 16 KiB.
Each event: `sequence`, `kind`, `urgent`, `needs_answer`, `reply_requested`, `source {kind, id, alias, kernel_id}`, `summary` (kernel text, at most 160 characters), `payload`, `attachments`; the result also has `untrusted: true`, `next_after`, `more`.
Kinds this feature adds (ordinary `InboxEvent` rows):

| Kind | Source | Steers | `needs_answer` | Payload |
|---|---|---|---|---|
| `child_finished` | child | yes | no | `TurnOutcome` (with `deadline_reached`), answer reference |
| `child_decision` | child | yes | yes | interaction id, one-line question, the card's text as `detail` (and `detail_truncated` when cut) when it has more than its title, choices |
| `message` | peer, kernel-stamped | sender's choice, default no | no | text, attachments |
| `peer_event` | followed peer | no | no | turn ended, state changed, error |

`timer`, `process`, `workflow_run`, `interaction_resolved` and the rest keep their kinds.

### 3.4 Acks, steer versus queue, one wake drains many
- **Ack** stays `ack {sequence, handled}` and gains `through: N` (all delivered events up to N that are not `needs_answer`). A `needs_answer` event cannot be acked until its decision is answered or passed. Acking an event before its wake was sent expires the wake without a prompt (`Expire`, `agent_inbox_delivery.rs:69-110`).
- **Steer versus queue is unchanged**, set by the event: urgent steers the running turn (`:154`); non-urgent waits for the turn to end; a parked agent starts a turn; a refused steer is deferred to the next turn. Child finished and child decision are urgent.
- **One wake drains many, without waiting.** The wake covers what is pending when it is built: a steer wake every pending urgent event, an idle or queued wake every pending event. No window, no timer. A later event gets its own wake, or is read and acked in the same turn. `Attempt` gains `through`; the batch rows share one prompt id and one delivery receipt.

### 3.5 The two fences in `agent_inbox_delivery.rs`
- **Correlated reply** (`replies.rs`; the `reply` text at `:182`): the reply is this turn's final answer, so a `reply_requested` message is delivered **alone**; its short prompt carries the reply instruction.
- **Sudo window** (`sudo_work_task`, `:48-53`; `WORK_CORRELATED`, `agent_lifecycle.rs:1052`): in sudo-bound work only events correlated to that task are delivered and readable (`agent_events.rs:136`); the rest stay deferred with the existing notice; nothing steers an active sudo turn. The batch holds correlated rows only; child events carry the parent's delegate `task_id`.
- Unchanged: a stopped agent keeps messages held (`:137`); the Vault-unlock wait (`:5`).

### 3.6 Protocol, shipping, tests
- **No client protocol change, no number, no relay change.** Changes: the tool schema of `chariox.events.inbox` and `ack` (three provider tool views, snapshot tests); a batch end on the durable row (`serde(default)`, no migration); the prompt text in room history.
- **Ships alone as slice A1, first.** It needs no tree and benefits every agent today (timers, processes, workflow runs, answers, messages). Size M. If A1 slips, later slices use the old prompt with the same events.
- Pinned tests that stay green (text expectations updated): `provider_output_runtime_tests/completion_settlement.rs`, `agent_reply_tests.rs`, `sudo/window_tests.rs`, `router/tests/agent_messaging.rs`, `agent_triggers.rs`, `local_prompt_dispatch_runtime/tests/inbox_recovery.rs`, `leased_wakes.rs`. New red-first tests and the drill: `SUBAGENTS_SLICES.md`.

## 4. Decisions: one card, one holder

### 4.1 The model (coordinator steer, owner may overrule)
A decision is **one interaction that belongs to the child** (`RuntimeInteraction`, `session/runtime_interactions.rs:239-285`; held as a `PendingInteraction`, `runtime/state/pending_runtime_state.rs:70-89`). It is never copied. The kernel only moves its **holder**: the child's parent, then that parent's parent, ..., then the user. There is one object and, for the user, **one place that shows it: the room agent's panel**. The first valid answer wins under the interaction lock; the loser gets "no longer pending" (`runtime_interaction_owned_state.rs:553-600`).

### 4.2 Who sees what (Miguel, 16:05Z: "a card is shown to the user only by the room agent")
1. **A parent holds it.** No user sees a card. The parent gets `child_decision` in its inbox as a steer (3.3). The child's pane in the sub-view shows its status only ("waiting"), no card and no button. The user's only lever is the one they already have: steer or stop the parent (and, by the cascade, its subtree); there is no timer and no takeover. The parent answers with the room command `agent answer <interaction> <choice | text>` or moves it on with `agent pass <interaction>`. Only the current holder may answer; agents never call `RespondToInteraction` directly. This replaces `answers_own_room` (`runtime/router/reach_tools.rs:42-58`).
2. **The user holds it** (a user-only kind, or the climb reached the top). The card appears **in the top parent's panel and nowhere else**, as an ordinary pending card with its own id. The child's pane in the sub-view shows "waiting", never the card, and nobody answers a child's decision from the sub-view. There is no "same card in two places". The top parent's stripe shows "needs you".
3. **A parent that wants the user's own words** asks its ordinary question with its own card (unlinked), then answers the child itself with the user's answer. This is the documented pattern; the kernel does not link the two.
4. **An external agent or an assistant** (a client of the kernel, like a terminal) receives the pending decision as an `interaction` record of its event subscription (`SubscribeEvents`, `docs/EXTERNAL_AGENTS_V2_PLAN.md` section 14, reported under the top parent) and may show it and reply for the user with the existing `RespondToInteraction`; only routine approvals can be answered this way, passkey and secret decisions arrive as a pointer and stay with the person (EA2-33). Nothing new is built for this.

### 4.3 Where a decision starts
- **Raise.** The kernel sets the holder when the card is created: the user for the eight user-only kinds (below); otherwise the nearest ancestor that could approve it **for itself**. An ancestor is skipped (the holder moves up at once, no model turn) when its permission level is `Required` and it would itself ask the user for that tool (a parent passes on only authority it holds, section 5), or when it is ended, archived, errored, stopped by the user, past its deadline or blocked on a user decision.
- **Holder ends mid-way.** If the holder ends, errors or is cancelled while holding, the holder moves up immediately and the former holder's inbox event is withdrawn. A decision never waits on a dead agent.
- **No hop timer.** The card's own `timeout_sec` / `default_on_timeout` still applies across holders.

**Decisions that never leave the user** (eight; default deny: delegable only if the subject is a subtree agent, the kind is `Permission` or `Choice`, and none of these marks applies):

1. Secrets, Vault entries, credential prompts (`terminal_credential_owner`, `pending_runtime_state.rs:83`; `InputKind::Secret`, `runtime_interactions.rs:192`).
2. /sudo (`sudo:` ids, `critical_approval_passkey.rs:537`).
3. Passkey-gated approvals (`passkey_gate`, `runtime_interaction_owned_state.rs:79`).
4. Payments (payment-card value kind, `runtime/state/vault_use.rs`).
5. Sign-ins: provider login, pairing, relay and Cloud identity, human verification (`provider_login_is_human_only`, `runtime_interactions.rs:622`; `handoff-` ids).
6. Renting or starting a machine (`kernel_operation_owner`, `runtime_interaction_state.rs:337-350`).
7. Kernel access grants (`access-grant:`, `critical_approval_passkey.rs:535`).
8. User-domain browser decisions (`user_domain_interaction`, `runtime_interaction_state.rs:365-378`).

There are no App grants in this design; every installed App is available to every agent. A card some code path may still raise for an App behaves as an ordinary permission card.

### 4.4 Races and audit
- Two answers at once (the holder moved to the user while the parent's answer was in flight, or the user and an external agent): the first valid answer wins under the interaction lock. The late agent gets a typed "settled by user" tool result; a late click is dropped by the card; nobody sees error text.
- The answer rechecks the authority limit under the interaction lock (section 5), so an answer cannot raise authority.
- `EventResolutionVia` gains `ParentAgent` (audit). The holder is kernel state used for routing; it is **not projected**, because the only place a card shows is the top parent's panel.
- Remote child: the decision lives on the child's kernel; the parent answers with `AnswerChildDecision` over the peer link (7.3) and the same lock decides. When the user holds it, B tells A, the card shows in the top parent's panel on A only, and the user's answer goes to B over the same link; B's own clients never see it (7.3).

## 5. The authority limit

> **In plain words (for the owner).** A sub-agent can never be given more authority than the agent that started it. The kernel checks it when the sub-agent starts and again every time it acts, against the parent's *current* settings, so lowering the parent lowers the whole team at once. Each limited thing, with one example:
> - **Permission level and mode:** a parent that must ask you before it runs a shell command cannot start a child that runs commands freely; a parent in read-only Plan mode cannot start a child in Build mode.
> - **Folders it may touch:** a parent working in `~/work/app` can start a child in a worktree of that project, not one in `~/private`.
> - **Deadline:** a parent with two hours left gives a child at most two hours, and the child ends when the parent does.
> - **Where it runs:** a parent allowed only on this machine cannot start a child on another one; renting a machine stays your decision.
> - **Tools are not limited:** a sub-agent has the tools of the kernel it runs on, like any agent there; a child on another kernel may use a Vault that is open there, which is fine.

**Rule.** The kernel stores what the child asked for and computes `effective(agent) = min(own, effective(parent))` at the moment of use, so lowering a parent constrains the whole subtree at once (T3 idea). Spawn refuses a request above it.

**Lock rule.** The check repeats for every control command and every decision answer, in the same serialized unit as the action, so nothing changes between check and effect: room-actor commands already run one at a time (`runtime/session_actor.rs:18-72`) and the answer also holds the interaction lock. Deadline and cancel join the actor (slice A5). **Remote carrying rule:** every request from a parent's kernel to a child's kernel carries the parent's current authority limit (level, mode, deadline, depth); the child's kernel applies the same minimum. **Control is not a comparison:** a parent controls a child by subtree membership (section 6); the limit only bounds what the child may do, so raising a child never locks its parent out (T3 issue 30408).

| Dimension | Today | Rule | Status |
|---|---|---|---|
| Permission level (`Required` < `Yolo`) and mode (`Plan` < `Build`) | `provider/launch_contract.rs:601,636` | child ≤ parent | **keep**: the core safety bound; also the base of the skip rule (4.3) |
| MCP, skill, script and connector grants and Vault handles | `ExtensionGrant` (`extension.rs:280`) | none | **not limited** (Miguel, 11-06 16:13Z: "the agent is bound to the tools in its kernel"): a child has the tools of the kernel it runs on, an open Vault there included |
| Workspace and worktree | `worktree_id`, `workspace_id`, `ProviderWriteAccessMode` (`launch_contract.rs:671`) | a child's worktree lies inside the parent's workspace root | **keep**: file reach. Enforceable, but a new check: today an explicit `--dir` is only tested to exist (`prepare_local_agent_worktree_placement`, `session_lifecycle_runtime_state.rs:615-650`); A5 adds the root test |
| Deadline | `AgentDeadline`, shorten only (`docs/AGENT_DEADLINES.md`) | child ≤ parent; the parent's deadline ends the subtree | **keep**: makes the subtree end in time without a budget |
| Placement and renting | `MoveAgentToRemote`, `ControlPlane` acquire (`room_agent_admission.rs:127-148`) | placed only where the parent may; renting stays a user decision (4.3, row 6) | **keep** |
| Account profile | profiles belong to the owner (`runtime/agent_account_admission.rs:6`) | none | **dropped** (Miguel, "Q2 yes drop it"): a profile is cost, not authority |
| Usage | only observed | **none in v1**: the agent decides | dropped (owner: "nothing") |

Network and sandbox follow the level (`codex_client/permission.rs:307`). Caps (2.1) bound fan-out. Nothing else is limited: not tools or secrets, not Apps, not the account profile, not usage. The limit is four things: permission level and mode, folders, deadline and where it runs.

## 6. Parent control without /sudo

**One rule replaces `direct_child`:** a caller may control a target when `in_subtree(actor, target)` holds, at any depth; a remote target reaches the same code through the peer link. It is membership, never a comparison of modes.

Room commands for the parent, each refused for a sibling, a peer, another room and a non-agent caller, except `agent cancel` and `agent steer`, which a peer may also use under the authority rule of 7.2: `agent cancel <child>` (stop the active turn, keep the agent), `agent steer <agent> <text> [--reply-requested]` (an urgent message to the child, answered like a message when the child reads it; the room command is `chariox.send_agent_message` with `urgent` set, so it arrives as an agent-authored message with the kernel-stamped sender, never as a user prompt), `agent message <agent> <text> [--reply-requested]` (the same tool without `urgent`; open to every ordinary agent of the owner, it gives no authority), `agent deadline set|get`, `agent delete` (the whole subtree), `agent spawn --permission --deadline` (clamped by section 5; an account profile is chosen freely, it is not limited), `agent answer` and `agent pass` (4.2), `agent children` (the subtree with state). `agent steer`, `agent message` and `agent cancel` take `--room R [--kernel K | --machine M]` to reach a peer in another room or on another kernel of the same owner; they refuse with the typed `kernel_ambiguous`, `kernel_unreachable` and `room_unavailable` of `agent spawn`, and steer and cancel keep the lower-authority refusal ("send it a message instead"). `agent answer` and `agent pass` are never a peer path: with `--room`, `--kernel` or `--machine` they refuse with `peer_decision_refused` and settle nothing, and an id the caller was never offered answers `unknown_interaction` (a decision it was offered and that is settled still answers `settled_by_user`). A peer never answers, approves or denies a decision, permission or question card. Read-only `agent usage` and `agent profiles` are open to every room agent (owner may overrule). A parent reads a child's history with the ordinary history tools (7.4) and a local child's files with its own shell; only a remote child needs `agent files get|put` (M2).

Orchdrill gaps closed: ORCH-04 by section 4; ORCH-05 by `agent deadline` (`SetAgentDeadline` is admitted for direct children, `room_agent_admission.rs:107`, but is no room command); ORCH-06 and ORCH-16 by `TurnOutcome` and `deadline_reached` in `child_finished`; ORCH-07, 08, 09 by the commands above; ORCH-10 by own shell (local) or `agent files` (remote); ORCH-11 because a remote spawn failure is reported "uncertain" (`app/kernel_session.rs:322-330`, `dispatch_error(.., None)`) and never settles, so a definite refusal settles as rejected and spawn takes a command id (retry returns the same child); ORCH-15 because a restart must reach the child as `InterruptedByRestart` (`provider/turn_outcome.rs:22`), not "The user doesn't want to proceed" (`app/provider_output_claude_native/transcript.rs:348`). All in A2.

A parent **parks** on `events.yield` covering its children's obligations and is resumed by `child_finished` or `child_decision` (urgent, section 3).

A child whose turn ends while a `run_in_background` call still runs is not finished: its one task stays Working, the provider wakes it with a notification turn when the call ends, and the parent gets one `child_finished` whose `public_answer` includes that turn's text. The kernel releases the task when the notification turn completes, 60 s after the last call ended, when the child's `--deadline` fires, or after 30 minutes with no deadline; a release with a call still running says so in the `public_answer` excerpt. Only a plain child task waits this way (no goal, wait or open obligation).

## 7. Peers, remote sub-agents and the reshaped reach

### 7.1 Relations
- **User, clients, external agents (assistants later):** the user's authority within the grant; the human-only set and the eight user-only decisions stay human. They address any agent, including sub-agents by id.
- **Parent to its sub-agents:** delegated authority, bounded by the authority limit: control the subtree, answer the decisions it holds.
- **Peers** (not ancestor and descendant; same room, another room of the same owner, another kernel): no authority over the target's work beyond **message, reply, subscribe, steer and cancel** (Miguel, 11-08: "for same/cross room, agents can steer and cancel each other. They can't reply/approve cards permission"). Nothing else (7.2).

### 7.2 Peers
- **Message and reply.** `send_agent_message` (today same room only) gains an address `{kernel?, room?, agent}`. The kernel stamps the sender `{kernel, room, agent}`; the receiver gets an agent-authored `message` inbox event, never a user prompt. A reply uses the existing correlated-reply path (3.5). `command_id` makes a retry one delivery. `urgent` stays a delivery class of the message (owner may overrule).
- **Subscribe.** `chariox.events.subscribe` (today the source must be a live agent or workflow of the same room, `agent_events.rs:158-176`) accepts a peer address. The subscriber gets `peer_event` for turn end, state change and error. Decision events are not delivered to peers.
- **Steer and cancel** (Miguel, 11-08). A peer may `agent steer` (an urgent message to the target, the existing mechanism) and `agent cancel` (stop the active turn, keep the agent) another agent, in the same room or another room. The rule is membership-free and has two conditions, both checked by the kernel at use: the target belongs to the **same owner**, and the caller's authority is **at least** the target's (the authority-limit clamp of section 5, so a sub-agent cannot cancel or steer a more privileged peer). Both stay reversible: the target remains and can be steered or prompted again (owner may overrule the authority rule). A cancel from an agent (a peer or a parent, same kernel or another) ends the target's current task only: its task reads "Stopped by an agent", and a message sent afterwards runs as a new turn. Only the owner's own stop keeps the agent stopped and holds later messages until the owner prompts it. When the owner's stop and an agent's cancel meet on one turn, the owner's wins in either order.
- **No other control**: a peer can never answer, approve, deny or reply to a decision, permission or question card (the holder rules of 4.2 are unchanged), read files, run in the other's shell, act as the user, delete the target, set its deadline, list its children or reparent it. A refusal is a typed calm reason, never an error text from the kernel.
- **Who creates peers.** Only room agents, with `agent spawn --room <room> [--kernel <k>]`: an ordinary agent of that room (it counts in that room's `max_agents` and appears in its agent list) with no edge, in a room of the same owner, authority clamped to the spawner's at creation, the spawner subscribed to its events unless `--no-follow`. A sub-agent's `--room` is refused: a sub-agent can only create sub-agents of its own. `--room` names another room: in the caller's own room a spawn is a sub-agent, so `--room <own room>` is refused with the advice to omit it, and a parentless peer in the caller's own room is added by the user. A peer an agent creates in another room has no deadline and no parent, so it stays until that room's owner deletes it: the spawn answer says so (`lifetime`), `agent delete` for it is refused with the same reason, and `agent cancel` stops its turn. `room list` and `slice list` show what `--room` and `--slice` accept for the caller. Same kernel: built (peers3, `spawn_args.rs:245`, `room_agent_admission.rs:222`), and `--kernel/--machine` are refused there today (`spawn_args.rs:402`). Another kernel of the same owner: planned, section 7.5, slices in `PEERS_P5.md`. Without `--room`, `--kernel/--machine` places a sub-agent's run on that kernel (section 7.5, execution lease); a reference that names this kernel (by id, alias or machine name) keeps the sub-agent here, and one that names no reachable kernel is refused and no agent is created.
- **Retired**: the reach `request` passthrough, `ReachNeed`, `reach_sudo_turn`, `answers_own_room`, the agent-made `AutomationOnly` attachment and the `reach:<run>` identity (`runtime/router/reach_tools.rs`, `kernel_access/reach.rs:36-95`). Acting as the user stays with external agents; `/sudo` never reaches a subtree or a peer.

### 7.3 Remote sub-agents (M2): hidden on the other kernel too
Miguel (16:05Z): "Subagents are never listed as normal agents and are kept away from rooms." A sub-agent started on kernel B runs as **an ordinary agent runtime** there (same provider launch, worktree, history and tools as any agent; no lease path) but exists only as the far end of its parent edge.

**What the code requires.** An agent cannot exist without a session: `AgentInstance.session_id` is mandatory (`agent/types.rs:205`), about 340 call sites read it, and `create_agents` takes a session, refuses an ended one and checks `max_agents` and the alias there (`agent/service.rs:63-142`). The session also carries the worktree, the history, the interactions and the owner.

**Smallest honest mechanism: reuse the hidden Room that exists today.** A session can be created hidden (`CreateSessionRequest::with_hidden(true)`, `session/service/core.rs:45-90`). A hidden session is skipped by the room list, the session projection and `visible_non_ended_sessions` (`session/store.rs:80-90`, `runtime/projection/session_state_projection.rs:205-215`); the lease backing room and the Move backing room already use it, and a client cannot reach a hidden backing room (`ensure_not_leased_backing`, `runtime/session_membership.rs:163`). For a remote sub-agent:
- B creates **one hidden session per child edge** when it accepts the spawn, owned by the owner user, not ephemeral (so it survives a restart: ephemeral sessions are not persisted, `app/prompt_state_owner.rs:492`), and creates the agent in it with `parent_agent_id = {A, X}`. That is the whole home: no new record type.
- It is in no room list and no agent list, and no `max_agents` counts it (a spawned agent skips the check, and the hidden session holds one agent).
- It ends with the edge: `ControlChild delete`, the parent's cascade, unpair of A, or the inherited deadline ends the agent and then its hidden session. No timer is added.

**What B's owner sees: nothing on B.** No room, no agent, no card there. They see it through the parent on A: the stripe, the card and the sub-view show its status, `unreachable` included. A decision that reaches the user is shown in the top parent's panel on A (section 4). The only trace on B is what any process leaves (quota use, CPU, the worktree on disk); a kernel-wide view that lists provider processes or worktrees may still show it, to check in P2 (first test below).

**Requests.** `agent spawn --kernel B` sends `SpawnAgentWithParent { parent: {kernel A, agent X}, authority limit, command_id, ... }`. B checks the limit, creates the hidden session and the agent, and answers with the child id. B sends A `child_finished` and `child_decision`; A sends B `ControlChild` (cancel, steer, deadline, delete, read output) and `AnswerChildDecision`. Each carries the parent's current authority limit and a `command_id`. If B is unreachable, A shows the last known state and `unreachable`; cancel and delete stay pending and retry.

**Authentication.** Peer-link requests on the same-owner seam that workflow notifications already use (`same_owner_request`, `transport/relay_client/peer_requests.rs:350`), so one path serves Cloud and self-hosted, Cloud only lists kernels, and a paired kernel inherits no grants: narrow, agent-addressed, idempotent, never the owner passthrough. Read on 11-08 (7.5): the sender binding passes on any relay, but the owner step, `authenticated_owner_of` (`runtime/state/workflow_notification_peers.rs:77-91`), returns no owner without an active Cloud profile, so a self-hosted pair is refused today; the fix, if wanted, is in that shared seam (11.3). Today's `agent spawn --kernel` still runs as an execution lease (`app/remote_agent_binding.rs:713-1060`), not as this design.

**First tests of slice RS** (remote sub-agents; named RS so it does not clash with the peer slices P1-P5; the unknowns of this reading): no kernel-wide list on B (rooms, agents, snapshot, `session overview`, pending interactions pushed to clients, provider processes) names the hidden session or its agent; a client on B asking by the child id is refused like any hidden backing room; restart of B keeps the child and its edge.

**Retired for sub-agents**: the execution lease, `SpawnLeasedAgent`, the Cloud realm and user check for them, and the pinned-key design of round 1.

### 7.4 History, assistants (one line each)
A sub-agent and a peer get the tools every room agent has (`chariox.history.search` / `read`, `runtime/state/public_history.rs`, secrets masked), bounded to the root room; nobody reads another room's history; no new mechanism. Assistants will sit one level above room agents with user authority inside their grant, neither descendants nor peers; nothing here changes for them.

### 7.5 Peers across kernels (M2, slice P5)

Miguel (11-08): "Agent spawn --room should also be able to spawn an agent in any owner's kernel. Is that planned and will be built?" **Yes, planned and to be built in Landing 6 as slice P5** (`PEERS_P5.md`). Nothing of it exists today. This section is the target. Code references are at `d1891c4b3c` (peers3 head), plus peers1 `b837f5fc42` and peers2 `ff553df9cf` where named.

**"Any owner's kernel" means any kernel of the same owner.** That is the laptop, b3, an Omarchy box or a rented machine, if it is reachable through the existing same-owner peer link. Kernels of **other users are out of scope**: no sharing or grant model exists, and every peer path is fenced to one owner, at the sender and at the receiver. Letting another person's agents reach yours needs its own product decision (11). Today the same-owner seam needs one more thing: an owner asserted by Cloud. `authenticated_owner_of` (`runtime/state/workflow_notification_peers.rs:77-91`) returns no owner without an active Cloud profile ("a private relay asserts its own identities, never the Cloud owner"). Two self-hosted kernels on a private relay are therefore refused today (11).

**`agent spawn --room <room> --kernel <k> [--no-follow]`** (`--machine <m>` is the same thing: a machine names its kernel; it never rents or starts a machine).
- `k` resolves with the selector `agent spawn --kernel` uses (`select_remote_kernel_by_ref_with_config`, `app/remote_agent_binding.rs:1464`): daemon id, alias, or machine name from the owner's inventory. A selector naming this kernel is the same-kernel path (`normalize_local_kernel_ref`, `session_lifecycle_runtime_state.rs:636`).
- `<room>` must be a visible, non-ended room on `k` owned by the same owner. Kernel `k` resolves it by id or alias, as `resolve_session_ref_id` does for the local case (peers3 `dispatch.rs:691`). An unknown room, another owner's room and a hidden room (the lease or move backing room, `ensure_not_leased_backing`) all get one calm refusal, `room_unavailable`. **Recommended default: refuse.** No implicit room creation; `--new-room` is open question 11.1.
- **What the new agent is:** an ordinary agent of that room on `k`. It counts in that room's `max_agents`, appears in `k`'s room and agent lists like any agent created there, and runs with `k`'s provider accounts and tools (section 5, "the agent is bound to the tools in its kernel"). It has **no edge**: no `parent_agent_id`, as on peers3's `!is_peer` branch (`session_actor/store/agent.rs:318`). Its folder is the target room's own folder; `--dir`, `--worktree`, `--slice`, `--deadline` and `--command-id` stay refused as in the local case (`spawn_args.rs:396-414`), and the lane uses the retry key below instead of `--command-id`. Its authority is **clamped to the spawner's at creation**: the sending kernel carries the spawner's `EffectiveAgentExecutionConfig { mode, permission_level }` (peers3 `peer_spawn_limit`, `runtime_state_views.rs:180`), and `k` applies `child_authority` to it (`session_actor/store/agent.rs:20,284-305`). After creation, the new agent's authority belongs to its room, like any peer's.
- **How the spawner follows it:** unless `--no-follow`, `k` records a follower for the spawner, and the spawner's kernel records a peer `Registration`. This is the same pair as a cross-kernel subscribe (below). The follow is named by the spawn's `request_id` and the calling turn's task: a repeat in the same turn re-asks for the same follow, and the same spawn repeated in a later turn gets a follow of its own, which `k` records with its duplicate answer. A registration held by one task is never rebound to another. The spawner then gets `peer_event` in its inbox across the link.
- **How this differs from `agent spawn --kernel <k>`:** that one creates a **sub-agent**. It has a parent edge, is hidden, is controlled by subtree membership (section 6), and its decisions climb to the parent (section 4). Today it runs as an execution lease: the agent is created on the home kernel and only its run is leased to `k` (`remote_agent_binding.rs:713-1060`, `CreateExecutionLease`, then `SpawnLeasedAgent`, `relay_peer.rs:919,930`). The hidden-session design of 7.3 is not built yet either. `--room --kernel` creates a **visible peer** on `k`. No edge, no lease, no hidden session: it does not depend on 7.3.

**The cross-kernel request set.** All of them are new `RelayPeerRequest` variants on the same-owner seam (`peer_requests.rs:350-438`, which carries workflow notifications today). The same `require_bound_managed_context_sender` + `same_owner_peer_user_id` admission applies. Every request is agent-addressed, and none is a `LocalDaemonRequest` passthrough. Exact shapes are in `PEERS_P5.md` section 3.

| Request (A -> B unless noted) | Effect on B | Response |
|---|---|---|
| `PeerAgentMessage` (message, reply-requested, `urgent` = steer) | a `message` inbox event for the target, never a user prompt (peers1 `agent_lifecycle_runtime.rs:554-561`); `urgent` runs `authorize_peer_control(.., Steer)` first (peers1 `peer_rooms.rs:58`) | `PeerAgentAccepted { outcome: delivered \| duplicate, target }` or `PeerAgentRefused { reason }` |
| `PeerAgentCancel` | stops the target's active turn and keeps the agent, after `authorize_peer_control(.., Cancel)` | same |
| `SubscribePeerAgent` / `UnsubscribePeerAgent` | records or ends a follower `{subscription_id, subscriber, generation}`; an older generation is ignored, as for workflow notifications (`relay_peer.rs:832-845`) | `PeerAgentSubscribed { subscription_id, generation }` or refused |
| `DeliverPeerAgentOutcome` (**B -> A**) | a `peer_event` (turn ended, turn failed, source lost) or a reply outcome to a message A sent. A applies it through the existing `Operation::SourceOutcome` / `source_end` path (peers2 `transitions.rs:720`, peers1 `replies.rs:40-68`) | `PeerAgentOutcomeAck { accepted \| duplicate \| unknown_subscription }` |
| `SpawnRoomPeer` | creates the ordinary agent in the named room, clamped, follower recorded unless `no_follow` | `RoomPeerSpawned { room_id, agent_id, alias, duplicate }` or refused |

- **Sender stamp `{kernel_id, room_id, agent_id}`.** The sending kernel fills it from the calling agent's seat; an agent cannot type it. The receiving kernel refuses the request (`unauthorized`, as "peer sender kernel mismatch", `peer_requests.rs:381-394`) unless `kernel_id == stable_peer_daemon_id(from_daemon_id)` of the authenticated link. Then it stores the link's id. B cannot check `room_id` and `agent_id` itself: it trusts them because they come from an authenticated kernel of the same owner. This is the trust workflow notifications already rely on. The inbox payload gains `sender_kernel_id`, which fills the `source.kernel_id` that is always `null` today (`tool_dispatch/agent_inbox_read.rs:137`).
- **Owner on both ends.** A sends only to a kernel in its owner's inventory, under its own owner (`send_same_owner_peer_request`, `workflow_notification_peers.rs:107-140`). B derives the owner from the authenticated identity (`same_owner_peer_user_id`) and checks that the target room has that owner, as peers1 does locally (`peer_rooms.rs:35,84-88`).
- **Authority rule across kernels.** A computes the caller's current `effective_agent_execution_config_in_tree` at send time and carries it as `caller_authority { mode, permission_level }`. B compares it with the target's own effective config under the target room's actor lock, with the rule peers1 uses: `mine.permission_level.permits(theirs) && mine.mode.permits(theirs)` (`peer_rooms.rs:89-103`). B trusts A's statement of the caller's authority just as it trusts the stamp. This is section 5's remote carrying rule. Folders and deadline are not compared, as in the local rule.
- **Idempotency.** Every A -> B request carries `request_id`: the tool's `idempotency_key` when the agent gave one; for the room commands `agent message`, `agent steer` and `agent cancel` a key of the caller's turn and the call, so the same command again in that turn is the same request; for `agent spawn` the retry key of 7.5; otherwise one generated per tool call. B keeps `(sender kernel, request_id) -> response` and answers a repeat with the first response and `duplicate`. A cancel's record is its receipt, written before anything is cancelled: the turn B found running (or none). A repeat cancels only that turn, never a later one. B claims a spawn before it creates the agent, so a repeat that overlaps the first waits for its answer, and the new agent carries the request as its spawn key, so a repeat after a restart that lost the answer finds that agent instead of creating another. B -> A outcomes are keyed by `(room, agent, source_id, occurrence_id)`, which the inbox already deduplicates (peers2 `durable_state/agent_lifecycle.rs:1067-1080`).
- **Ordering.** Commands carry no cross-request ordering promise: each is one request and one answer. Outcomes from B are sent in outbox order (`ORDER BY next_attempt_at_ms, sequence`, `durable_state/workflow_notifications.rs:435`), and A orders them by its own inbox sequence.
- **Reconnect and duplicate delivery.** A command with an uncertain end (timeout, `target_disconnected`) returns `uncertain` to the agent, never "refused". The agent repeats it with the same `request_id`, and B's record makes the repeat one delivery (the ORCH-11 lesson, section 6). Outcomes B -> A go through the durable outbox the workflow notifications use (`app_outbox`, states `accepted` / `retryable`, `workflow_notifications.rs:416-440`) with a deadline. They are written in the same transaction as the event on B, retried after reconnect and acknowledged `duplicate` by A.
- **Offline target kernel. Recommended: a typed, calm refusal now, no queue for commands.** If the relay answers `target_not_connected` (`apps/relay/src/server/connection.rs:660`), the agent gets `kernel_unreachable { kernel }` ("kernel `b3` is not connected; try again when it is online, or message another agent"). Outcomes already accepted keep retrying from B's outbox until their deadline. A subscription stays live while B is offline, and only the unpair of B or the target's deletion or archive ends it, as `source_lost` (an archived agent takes no new follow; once unarchived it does). A bounded command queue is open question 11.2.
- **No card answers on the link.** No variant carries an interaction id, a choice or an answer. B maps each variant to exactly one of message, cancel, subscribe and spawn, and none of these reaches `RespondToInteraction` (peers1 fence `reach_tools.rs:43,189`, unchanged). An outcome carries no decision events and no answer text: peers2's `source_end` builds only `turn_ended` / `turn_failed` and leaves out `public_answer` for peers (`transitions.rs:734`); it names the ended turn (`turn.agent_id`, `turn.turn_ref`: the prompt that ended the task, which `chariox.history.turn` takes; a task keeps its id across corrections, its turns do not) when the peer runs on the same kernel, so its history is one read away. The only answer text that crosses is the reply to a message A itself sent, which is the reply path. A test asserts the variant list.
- **Attachments.** Text only in P5. A message with attachments to another kernel is refused with `attachments_local_only`; carrying files across kernels is a later slice.
- **What the user sees: nothing new.** A peer on `k` is an ordinary agent of a room on `k`, shown in that room on every client. The spawner's panel on A shows the ordinary tool result. No stripe, no card and no list change on either kernel (section 8 stays as it is).

## 8. What the user sees: the kernel projection (data only, not a mock)

**Gate.** The stripe, the hierarchical card and the sub-view need an **owner-approved mock** (PROPOSALS.md) before any UI slice. This section is the data they read. A decision card is not part of the tree: the user-held card is an ordinary pending card of the top parent's panel (4.2).

`ListDescendants { agent }` (read) and the notification `AgentTreeChanged { root, rev }` (clients re-read; changes coalesced). Everything is enums and ids; the kernel adds no error text.

```
AgentTree { root: agent_id, rev, totals: { live, running, needs_user },
  nodes: [ { agent_id, parent_agent_id, kernel_id | null, alias, provider, model, depth,
             state: starting | running | waiting | idle | ended | error | unreachable,
             outcome: TurnOutcome kind | null, deadline_ms | null, created_at_ms } ] }
```
`waiting` means the sub-agent is blocked on a decision held by an ancestor or the user; the node carries no card, no holder and no path.
- Order is creation order and stable; the client builds the hierarchy from `parent_agent_id`.
- **Stripe** reads `totals`. **Card** reads `nodes`. **Sub-view** shows one panel per node, using the same per-agent reads and streams as the room's agents view, addressed by `agent_id` (2.1), with the status of the node ("waiting" included) and **no decision card**. Clicking a card entry opens the sub-view if needed and focuses that node.
- The decision card the user answers is shown only in the top parent's panel (4.2). For that, the kernel lists a user-held decision of a sub-agent among the top parent's pending interactions, unchanged (same id, one new field `shown_in_agent_id` = the top parent, present only while the user holds it); clients render it like any card.
- **Who may see it:** any client allowed to see the top parent's room and its panel (owner, and room guests as today); external agents and assistants within their grant, which also receive the pending decision as an event (4.2). Peers never see another agent's tree and cannot list its children; a parent sees its own subtree through `agent children`. A remote sub-agent is visible only here, never on its own kernel.
- Sub-agents are never listed in a room's agent list, on any kernel, and never counted toward `max_agents`. A decision held by the user raises `needs_user` on the top parent's room entry (aggregate flag; T3 idea).

## 11. Open questions for the owner

Miguel's answers of 11-06 (16:05Z and 16:13Z) closed the earlier ones: no tool limit, no account-profile limit. Peers across kernels (7.5) open five, each with the default this design takes until he answers:
1. **Missing room on the other kernel.** `agent spawn --room r --kernel k` when `k` has no room `r`. Default: refuse with `room_unavailable`. Alternative: an explicit `--new-room <name>` that creates the room on `k` first.
2. **Target kernel offline.** Default: message, steer, cancel, subscribe and spawn are refused at once with `kernel_unreachable`, and the agent decides whether to retry. Outcomes already accepted keep retrying from the target's outbox. Alternative: a bounded queue (for example 15 minutes) for messages to an offline kernel.
3. **Self-hosted kernels on a private relay.** The same-owner seam needs an owner asserted by Cloud today (7.3, 7.5). Default: P5 works between Cloud-signed-in kernels; a self-hosted pair is refused with `owner_unverified`, and accepting a private relay's owner is a separate change of the shared seam. Alternative: do that change inside P5.
4. **Kernels of another user.** Default: out of scope; every peer path stays fenced to one owner. Alternative: design a sharing or grant model first; nothing exists for it.
5. **Finding rooms and agents on another kernel.** Default: no cross-kernel listing in P5; an agent addresses a room and agent by the names its brief or the user gives it, and an unknown name is refused. Alternative: a read-only `ListPeerRooms` request that lists the other kernel's visible rooms and their ordinary agents.
