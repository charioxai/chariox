TUI and Web Terminal UX Parity Plan

Plan to close the local TUI UX gap against the web terminal for Freeform agent panes, prompt queue and steering behavior, prompt chrome, screen footer, and Waiting Room. Workflow canvas behavior is intentionally out of scope because the TUI has no canvas.

Target outcome

The TUI should feel analogous to the web Freeform terminal where the medium allows it: assistant messages expanded, non-assistant activity blobs collapsed by default, historical turns auto-collapsed, queue/steering visible and actionable, footer state consistent, and Waiting Room rows/footers driven by the same runtime facts.

Current Remediation Plan

  1. Make the queue a single Web-like surface. Stop projecting queued prompts as normal freeform transcript entries when the dedicated queue strip is active. Add TUI notice filtering equivalent to Web Terminal so queued prompt lifecycle notices do not become permanent agent-pane scrollback.
  2. Normalize queue lifecycle rendering. On steer, render one intentional steering prompt entry with dedicated role metadata. On cancel, remove the queued item without leaving the old prompt text and a permanent cancel notice in the transcript. Keep status feedback transient in the footer or strip.
  3. Fix queue keyboard control. Add a focused queue selection/index so keyboard actions can target any queued prompt, not only the first item. Route queue actions through deterministic TUI input handling and automation controls, with PTY shortcut behavior covered by a live drill.
  4. Rebuild queue strip layout. Replace long inline action labels with stable fixed columns, compact focused controls, and prompt/meta truncation. The strip must not clip or overlap at 80 columns, and it must hide cleanly when the queue is empty.
  5. Upgrade collapsed blob presentation. Build a TUI blob component with a useful header, type/status metadata, compact summary, chevron, loading state, loaded state, and error state. Reuse the shared tool display model where practical so tool, reasoning, status, notice, and error blobs are visually distinct.
  6. Apply the same compact layout rules to Waiting Room and footer actions. Waiting Room rows already expose the right semantics, but action/footer text needs fixed-width formatting, predictable truncation, and snapshot coverage at 80x24 and wider widths.
  7. Add parity drills as invariants. Keep the seeded TUI/Web fixture and assert behavior, not pixels: queued prompt appears once, queued notices are excluded from transcript scrollback, steer/cancel removes stale rows, lazy blobs expand with visible loading, turn collapse still works, and Waiting Room rows/footer hints render without overlap.
  8. Keep this below clients where possible. Prefer shared projection helpers for runtime notice filtering, queued prompt lifecycle display state, and blob summaries. Do not introduce a parallel prompt, history, permission, attachment, or relay authority path. If any serialized protocol shape changes, bump the local daemon protocol version and update protocol snapshot/hash tests.

Manual visual checklist

  • Assistant messages remain expanded and readable.
  • Tool, reasoning, status, and history blobs start collapsed.
  • Old completed turns collapse while the active/latest turn stays expanded.
  • Loading older history does not lose blob or turn collapse state.
  • Queued prompt strip appears with prompt preview, status, attachment count, steer, and cancel.
  • Steer and cancel work through keyboard and mouse.
  • Steered prompt appears in the correct chronological position without creating a new active turn.
  • Pane footer shows the same runtime facts as web in TUI form: status, alias, provider, model, mode, permission, runtime placement, and slice/substitute hints.
  • Screen footer prioritizes fatal errors, active prompt, queue depth, status line, connection, and hotkeys consistently.
  • Waiting Room rows show working/done/idle sessions, remote and slice next actions, and footer hints matching web semantics where applicable.

Non-Goals

  • Do not add a workflow canvas to TUI.
  • Do not add web-only buttons under TUI agent panes.
  • Do not make the relay or web app the runtime authority for any of this behavior.
  • Do not create a separate prompt, permission, attachment, history, or relay path for native provider TUIs.
