Web Server Local/Staging Unification Plan

Unify the local web terminal and staging web app onto one API server implementation. Local mode should only shortcut authentication and swap in local backing adapters. Routes, response contracts, dashboard projection, waiting room projection, and relay bootstrap behavior should be shared.

Problem

The web UI is mostly shared, but the API path has diverged. Staging uses the normal Cloud API server, Cloud auth, Cloud repositories, and shared service code. Local web terminal currently runs a separate local-browser-terminal-server.ts path that reimplements enough auth, dashboard, waiting room, and relay bootstrap behavior to look like Cloud.

That duplicate local server path caused alias and relay target fixes to require two edits. It also makes local behavior sensitive to stale detached processes on port 4321, which can keep serving old compiled code after the developer restarts relay, kernel, or the browser.

Target Architecture

Goal: one web app, one API server, one set of route handlers, one JSON contract.

Hosted/staging and local should call the same server factory. The only differences should be injected dependencies: auth, repositories, and token issuance. 

createBrowserTerminalServer({
  auth,
  dashboardRepository,
  relayTargetRepository,
  waitingRoomRepository,
  relayTokenIssuer,
  staticWebRoot,
  mode,
})

Hosted/Staging Mode

  • Real browser auth.
  • Cloud DB-backed repositories.
  • Hosted relay token issuance.
  • Real account, realm, and user session state.

Local Mode

  • Shortcut auth with a synthetic local user/session.
  • Local repositories backed by kernel registry and live kernel status.
  • Local relay token/config adapter.
  • Same route handlers and response shapes as hosted mode.

Implementation Steps

  1. Extract or formalize a shared API server factory for browser terminal routes. Both hosted and local entrypoints should create the server through this same composition point.
  2. Move authentication behind an adapter. Hosted keeps the current auth provider. Local gets a shortcut adapter that returns a synthetic authenticated user, account, and realm without changing route code.
  3. Replace local route duplication with local implementations of the same repository and service contracts used by hosted mode.
  4. Move local relay target discovery into a local repository adapter. It may read the local kernel registry and probe live RelayStatus, but it should feed the same shared dashboard and bootstrap services.
  5. Share these routes completely across both modes: /dashboard, /browser/relay-kernel/bootstrap, /browser/waiting-room/public-snapshot-cache, /auth/session, and /auth/cloud-session.
  6. Shrink local-browser-terminal-server.ts into a launcher only. It should load local config, create local adapters, call the shared server factory, and listen on the configured host/port.
  7. Add route contract tests that run the same dashboard, bootstrap, and waiting-room assertions against hosted/mock dependencies and local adapters.
  8. Remove obsolete local JSON construction and stale duplicate helpers once parity tests pass.

Local Adapter Responsibilities

  • Auth adapter: return a local authenticated session and synthetic profile/account/realm.
  • Relay target repository: list local kernel targets from local config, registry, and live kernel RelayStatus.
  • Dashboard repository: expose machines, relay targets, clients, collaborators, and pending invites using the same hosted dashboard contract.
  • Waiting room repository: provide the same waiting-room snapshot/cache contract, with local/in-memory backing where needed.
  • Relay token issuer: issue or expose a local relay token with the same response shape as hosted relay bootstrap.

Runtime Boundary

The kernel remains the runtime authority. Local adapters may enrich display data from local kernel registry, live kernel status, and local relay configuration. They should not create a separate session, agent, provider run, prompt, permission, or relay authority path.

Validation

  • Automated: shared route contract tests for hosted/mock and local modes.
  • Automated: web and API builds.
  • Manual: local waiting room and pane footer screenshots from the live web app.
  • Operational: ensure stale local servers on 4321 are stopped before visual validation.

Expected Scope

This is a moderate refactor, not a rewrite. The frontend should need little or no change. Most work is in chariox-cloud/apps/api. The main risk is making sure local shortcut auth satisfies every route that currently expects hosted auth/session state.

The payoff is that future changes to aliases, waiting room display, bootstrap selection, footer metadata, and relay target behavior are implemented once and apply equally to local and staging.
