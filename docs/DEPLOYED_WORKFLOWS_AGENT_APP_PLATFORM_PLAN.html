01 / Product decision

Ship a customer-owned deployment product, not a larger sidebar.

Recommended thesis Arroba should become the managed host for provider-native agent apps. A builder publishes an immutable release; a customer claims a deployment into their organization, connects their own provider and integration credentials, controls who may use it, and operates it on an Arroba-managed URL or their own domain.

The differentiated product is a claimable agent app release. It is narrower and more defensible than trying to match every n8n workflow-building feature. Arroba can own the deployment, handoff, runtime, authentication, credential binding, and operational experience for developers and agencies that do not want custom infrastructure.

01

Immutable releases

Production changes move through explicit release promotion and rollback. Deployment controls cannot silently rewrite workflow semantics.

02

Customer ownership

The destination organization owns access, credentials, domains, billing, and production activation. Builder access is optional and revocable.

03

Runtime-held credentials

Provider credential bytes never enter publication packages or ordinary Cloud deployment records. Login uses provider-native harnesses in the runtime plane.

04

One shared authority

The kernel remains workflow and execution authority. Cloud is control plane; relay and ingress remain scoped transport and policy boundaries.

Initial product focus

  • Agencies and independent developers delivering an agent portal or agent API to a company.
  • Teams that want provider-native Codex, Claude, or OpenCode execution without operating application infrastructure.
  • Two deployment kinds on one foundation: browser-facing Agent App and programmatic Endpoint.
  • Managed hosted runtime as the default handoff; local runtime and export/self-host remain supported sovereignty options.

Explicit non-goals for the first release

  • Cloning n8n's full integration catalog, embedded editor, or generic no-code automation breadth.
  • Arbitrary customer frontend code, Kubernetes, marketplace economics, or multi-cloud orchestration.
  • Automatic unreviewed production updates from the builder's mutable workflow.
  • Using persistent workflow patches as a general-purpose customer database.

05 / Release contract

Make the package self-describing enough to drive setup.

Add a versioned deployment contract to the publication package. Prefer extending the existing requirements format when compatibility remains clear; otherwise add deployment-contract.json and retain old package readers behind an explicit package-version adapter.

Required contract sections

  • Identity: stable release/package IDs, digest, source provenance, creator, timestamps, minimum runtime and protocol versions.
  • Routes: path, transport, methods, input/output schema, required roles, session behavior, streaming, timeout, idempotency hints.
  • Provider requirements: provider, model constraints, allowed substitutions, capability needs, readiness test.
  • Credential slots: stable slot ID, kind, label, provider/integration, required/optional, scope, allowed hosts, uses, test method.
  • Typed configuration: stable key, scalar/enum/schema type, default, constraints, sensitivity flag, environment scope.
  • Capabilities: maximum actions, manipulation permissions, extension requirements, scripts, MCPs, skills, connectors, filesystem and network policy.
  • Resources: expected concurrency, memory class, replicas, storage, schedules, egress destinations, region/data sensitivity hints.
  • Presentation: app kind, assets manifest, immutable content hashes, entry route, display name and icon metadata.

Compatibility rules

  • A deployment may tighten route roles, network access, provider choice, replicas, limits, schedules, and capabilities; it may never broaden the release's declared maximum.
  • Workflow graph, prompts, endpoint routes, required roles, actions, assets, or capability maxima require a new immutable release.
  • Access policies, credential bindings, typed non-secret settings, domain, allowed runtime override, region, size, replicas, budgets and alerts are environment configuration.
  • Any serialized OSS protocol shape change follows the repository protocol rule: bump the shared version, update snapshot/hash tests, update dependent minimum versions, and add a focused drill.
Design constraint The package must describe what a customer needs to provide without containing what the builder provided. A credential slot says "GitHub installation with repository read scope"; it never contains a GitHub token or builder account reference.

06 / Security foundation

Repair the current control and ingress boundaries before adding exposure.

This is Phase 0 and blocks public product activation, not the rest of local development. Existing routes appear to accept caller-provided account and creator identifiers. Public route lookup is globally ambiguous because slugs are account-scoped in the database but resolved without account or host context.

The normative actor, asset, trust-boundary, abuse-case, residual-risk and verification baseline is maintained in Deployed Workflows Threat Model.

Control-plane requirements

  • Derive actor and account membership from the authenticated browser/API session; do not trust body/query identity fields.
  • Apply CSRF protection to browser mutations and explicit bearer/scoped credentials to machine APIs.
  • Define control roles: owner, admin, deployer, operator, viewer, billing. Enforce them in repository/service policy, not only React.
  • Scope every lookup and mutation by destination account and deployment ID. Add cross-account denial tests.
  • Hash claim and API-key tokens at rest, display secrets once, support expiry and revocation, and log security events without token content.
  • Move destructive or sensitive operations through auditable service methods with idempotency keys.

Public ingress requirements

  • Resolve a globally unique verified host to one deployment/environment; never select the latest matching slug.
  • Authenticate before HTTP, SSE, WebSocket, and MCP upgrade/stream creation.
  • Strip caller-supplied identity and internal Arroba headers, then inject a short-lived signed invocation envelope.
  • Include deployment_id, environment_id, sub, org, roles, aud, expiry, nonce, and invocation ID in trusted claims.
  • Verify claims again at the runtime boundary and enforce the package route's required_role.
  • Keep identity structured. Do not automatically splice identity claims into model-visible prompt text.
  • Apply per-deployment and per-caller request, concurrency, queue, body-size, duration and spending limits.
  • Validate CORS, CSRF, cookie scope, WebSocket Origin, forwarded headers, redirect and content-security policy behavior.
Persistent patch policy Keep persistent workflow patching unavailable for customer deployments until strong authentication, authorization, reviewable diffs, audit, rollback, expiry, concurrency handling, and capability limits are implemented. A deployment may not become a hidden workflow editor.

07 / Customer handoff

A claim flow should replace credential and ownership copying.

  1. Create release. Builder publishes an immutable release and selects "Deploy for customer." Arroba validates the package contract before issuing an invitation.
  2. Review invitation. Customer sees the app identity, builder, required providers and integrations, capabilities, data/egress implications, runtime mode, estimated cost and offered builder role.
  3. Claim ownership. Customer signs in, chooses or creates an organization, accepts terms, selects billing ownership, and creates the deployment project. The claim is single-use and expiring.
  4. Connect dependencies. Customer supplies typed configuration, provider credentials and integration credentials. Builder secrets are never transferred.
  5. Set audience. Customer selects public, invitation/allowlist, organization/domain, external IdP, or machine access and maps identities to published route roles.
  6. Choose address. Arroba assigns a stable default hostname. Customer may attach and verify a custom domain.
  7. Private preview. Arroba runs contract checks and a smoke invocation in preview. Activation stays blocked until all required checks are green.
  8. Activate. Customer promotes the verified release/configuration snapshot to production.
  9. Maintain. Builder proposes future releases. Customer reviews the release and config diff, then promotes or declines it. Rollback is always available.
  10. Revoke cleanly. Customer may remove builder access without breaking runtime ownership, credentials, domain, history, or production availability.

Ownership modes

Customer-owned

Default. Customer owns deployment, billing, credentials and activation. Builder may receive a revocable maintainer role.

Builder-managed

Agency remains operator and billing owner while customer controls audience membership. Ownership transfer remains available later.

Export / self-host

Customer receives the immutable package and declared requirements, then operates it outside managed hosting.

Internal team

No handoff. Source and deployment stay within one organization, but release, credentials and audience boundaries remain identical.

08 / Credentials

Connect accounts in the runtime plane and expose only readiness to Cloud.

Replace the current free-text credential profile field with a destination-owned credential catalog and a provider-specific "Connect" flow. Reuse official provider CLIs, provider-local servers, and documented hooks only.

Provider connection flow

  1. Customer selects a required provider slot during setup.
  2. Cloud authorizes a short-lived, single-purpose credential setup session for the destination account and runner.
  3. Runner starts an isolated setup container/profile and launches the official provider login command.
  4. Verification URL, device code, progress, and normalized status travel through a scoped direct runtime/relay path.
  5. Provider credential files remain in the runtime profile volume with strict ownership and permissions; setup output and logs are redacted.
  6. Runner performs a non-destructive provider-native auth/readiness check and reports provider, account label when available, readiness, expiry and stable error category.
  7. Cloud stores only metadata and an opaque runtime reference, then creates the environment binding.
  8. Replace/rotate uses a new profile version and rolling restart; revoke removes binding first, then securely purges runtime material after confirmation.

Credential classes that must stay distinct

  • Provider execution: Codex, Claude and OpenCode provider accounts.
  • Integration secrets: GitHub, Slack, databases, third-party APIs, MCPs and connectors.
  • Audience identity: end-user sessions, OIDC claims, API keys and webhook signatures.
  • Control-plane identity: customer administrators, builders and operators.
  • Billing identity: who pays Arroba and, separately, who pays the provider.

Credential operations

  • List by provider/account label, scope, environments, status, last check, expiry and last rotation.
  • Test without exposing content; normalize ready, expired, revoked, missing_cli, login_required, and unknown.
  • Bind one credential profile to explicit compatible slots and environments; do not silently grant it to every deployment.
  • Redact package, API, runner, process, container, shell, audit and support logs.
  • Detect expiry and notify before production failure; preserve an atomic replace path.
  • Recommend least-privileged service/API credentials for production where provider terms and capabilities permit them.

Allow lists are one mode, not the authentication architecture.

Session and data isolation

  • Define whether each route is stateless, per-subject, per-browser-session, per-organization, or explicitly shared.
  • Derive runtime caller keys from signed claims, not request headers supplied by the caller.
  • Never reuse prompt history, files, overlays, provider thread state, queue affinity or generated artifacts across unauthorized callers.
  • Audit administrative access changes with before/after policy metadata. Do not log sensitive identity tokens or prompt payloads by default.

11 / Domains and CDN

Route by verified host from the beginning.

Replace account-local slug lookup with a globally unambiguous hostname binding. A stable deployment ID should remain the routing authority even when the display slug or custom domain changes.

Default and custom host flow

  1. Assign a default hostname such as <slug>-<short-id>.apps.arroba.cloud.
  2. Customer enters agent.customer.com. Cloud rejects any hostname already bound or reserved.
  3. Cloud issues DNS ownership instructions, preferably CNAME plus TXT challenge when required.
  4. Verifier checks ownership and target independently; status records DNS and TLS separately.
  5. Only after verification may ingress and certificate automation serve the host.
  6. Customer chooses canonical domain and redirect policy. Removal revokes routing before releasing the hostname.

Transport correctness

  • Preserve HTTP methods, encoded paths, request bodies, SSE flush behavior, WebSocket close codes/reasons and MCP semantics.
  • Scope cookies to the effective host and use a centralized login callback strategy that safely returns to custom domains.
  • Validate CORS, CSRF, WebSocket Origin, redirect allowlists, forwarded host/proto, HSTS and certificate failure behavior.
  • Cache only immutable content-hashed static assets. Never CDN-cache invocation POSTs, auth, personalized HTML, SSE, WebSockets, MCP, traces or overlays.
Infrastructure default Start with direct Caddy origin routing and controlled on-demand TLS. Do not make a CDN or Cloudflare account a prerequisite. Add a custom-hostname platform only after real domain volume, WAF needs, certificate operations, or geographic asset delivery justify it.

12 / Runtime operations

Production hosting needs more than start, stop, and logs.

Release and configuration operations

  • Build once, verify digest/signature, promote the same immutable release across environments.
  • Snapshot environment configuration and credential binding versions with every promotion.
  • Use readiness gates and rolling activation; switch ingress only after the replacement is healthy.
  • Rollback release and configuration pointer atomically. State/database rollback is a separate explicit operation.
  • Keep prior runtime for a short bounded drain window, then clean it and preserve diagnostic metadata.

Resource, usage, and abuse controls

  • Per environment: replicas, max concurrency, queue depth/age, request body, timeout, runtime memory/CPU class, storage and egress policy.
  • Per caller: request rate, active sessions, token/cost estimate and daily/monthly budget.
  • Customer alerts: credentials expiring, health degraded, error/latency threshold, queue saturation, budget percentage and domain/TLS issue.
  • Emergency controls: deny new invocations, stop environment, revoke one audience key, unbind one credential, or disable one route without deleting history.

State and data

For the first release, support stateless apps and external customer databases/connectors. Define deployment-scoped ephemeral files explicitly. Plan a later managed KV/blob capability with per-caller isolation, quotas, backup, retention, export and deletion. Persistent workflow patches are configuration mutations, not application storage.

Observability and privacy

  • Correlate invocation, ingress, environment, runtime, workflow trace and provider run with non-secret request IDs.
  • Default to metadata-only logs. Prompt, output and attachment capture requires explicit customer policy and retention.
  • Expose redaction, retention, export and deletion controls before promising enterprise compliance.
  • Record resource measurements locally, on each slice/container and on the Hetzner host during drills.

Default and temporary custom domains serve HTTP, SSE, WebSocket and MCP correctly; invalid ownership cannot bind; domain removal revokes routing; no personalized or streaming response is cached.

Phase 6Limits, usage, reliability, and state contract

Deliver

  • Invocation/concurrency/queue/spend/storage limits and non-charging usage ledger.
  • Alerts, audit views, structured diagnostics and privacy/retention controls.
  • Runner/ingress/kernel restart reconciliation, rolling release activation and clear in-flight failure semantics.
  • Stateless/external-storage product contract and deployment-scoped ephemeral storage limits.

Exit

Limits fail predictably, usage reconciles, outages recover desired state, interrupted calls are explicit, and no orphaned container/profile/package/test account remains after drills.

Phase 7Launch validation and service decision

Deliver

  • Full provider, transport, runtime mode, role, handoff, domain and disruption matrix.
  • Web/TUI parity report with screenshots and command evidence.
  • Resource/cost measurements and capacity recommendation.
  • External-service registration report and production migration checklist.
  • Customer-facing runbooks for deployment, claim, credential rotation, domain, rollback, export and deletion.

Exit

All launch criteria below pass, required external services are either configured or explicitly accepted as the only remaining production gate, and both worktrees are clean and pushed.

15 / Validation program

Test the product as two people, not only as one API client.

Run a dedicated local Arroba stack for these drills: start this worktree's own relay, kernel, and server on dynamically verified unused ports. Do not reuse the user's active daemons, staging processes, or their state directories. Use the existing Hetzner machine for hosted runtime, remote machine/slice, and collaborator drills. Before remote work, review existing publication, resilience, and provider drills for exact credential transfer, process ownership, port, and cleanup guidance.

End-to-end requirement Every required product journey, authorization case, lifecycle operation, and failure/recovery case must be driven end to end from both the web terminal and the TUI terminal. Unit, API, repository, component, and browser-only tests supplement this evidence; they do not count as acceptance on their own. Both terminals must observe the same deployment state, release, access, credential readiness, interaction, progress, error, and recovery outcome with only bounded propagation delay.
Isolated drill infrastructure Each drill must create a run manifest containing allocated ports, PIDs/process groups, state directories, package/profile paths, containers, volumes, temporary accounts, and remote artifacts. Install teardown traps where practical, monitor resource headroom while the drill runs, and execute idempotent cleanup after each case and again at suite completion. Verify that ports are closed, processes and containers are gone, temporary state is removed, and local/Hetzner resource use returns to the pre-drill baseline.

16 / Delivery discipline

Keep both repositories reviewable and continuously recoverable.

Worktrees

Implement only in the dedicated `codex/deployed-workflows-platform` worktrees. Start every phase by fetching and reconciling current `main` without overwriting unrelated user work.

Commit and push

Commit and push every meaningful green increment in each affected repository. Use focused commits such as contract, migration, service, UI, drill, and docs. Do not accumulate a cross-repository implementation in one final commit.

Cross-repo order

When the serialized runtime contract changes: land OSS contract/version/tests first, update Cloud compatibility and fixtures second, then run mixed-version rejection/compatibility drills. Do not merge one side while the other depends on unpushed local state.

Progress record

After each phase update this plan or a companion progress document with commits, tests, screenshots, measurements, known failures, temporary infrastructure and cleanup evidence.

Technical issues

When a provider, relay, remote machine, slice, hosted runner or credential drill fails unexpectedly, compare with existing repository drills before inventing a new path. Preserve the kernel authority and provider-native contracts.

Quality gate

Run focused tests during development and the full affected OSS/Cloud suites before phase completion. Treat schema migrations, protocol changes, ingress policy and shared web projections as broad-blast-radius changes.

17 / Launch gate

Do not call it managed hosting until these statements are true.

  • A customer can claim and operate a deployment without source-workflow or builder-account dependency.
  • Every control mutation is authenticated, authorized, account-scoped, CSRF-safe where relevant, and audited.
  • Every public route has an explicit audience policy; package roles are enforced across HTTP, SSE, WebSocket and MCP.
  • Provider and integration credential bytes are absent from packages, ordinary Cloud records, URLs, logs, traces, screenshots and support bundles.
  • Codex, Claude and OpenCode connect, expire, rotate and revoke with clear customer-visible status.
  • Default hostname and at least one real custom hostname pass DNS, TLS, auth, streaming, canonical and removal drills.
  • Immutable release promotion and rollback work without silently rolling back customer data or credentials.
  • Caller state is isolated; cross-account, cross-deployment and cross-caller security tests pass.
  • Budgets, rate limits, concurrency limits and emergency stop prevent unbounded provider or host spend.
  • Runner, ingress, kernel and Cloud restarts reconcile automatically; interrupted calls fail explicitly and new calls recover.
  • Every required journey and disruption has end-to-end evidence from both web terminal and TUI terminal; usage, health, errors, release, access, interactions, and credential readiness remain consistent.
  • Resource measurements establish safe host capacity and every drill leaves no dedicated relay/kernel/server, listener, process, container, profile, package, volume, or remote artifact on local, slice, or Hetzner resources.
  • Privacy, retention, export and deletion behavior are documented for logs, prompts, files, identities and deployment metadata.
  • The final external-service report is accepted and any truly production-critical service is configured.
