Arroba workflow implementation plan

Workflow Schedule Rename and Cron Scheduler

Rename the runtime feature from watchdogs to workflow schedules, make WorkflowSchedule and WorkflowScheduleDefinition the canonical types across arroba and arroba-cloud, and replace interval-only scheduling with a production scheduler that supports interval triggers and Unix cron triggers with seconds and explicit IANA timezone storage.

Owner: kernel runtime plus Cloud web client Primary surfaces: TUI, web terminal, workflow-code Requires protocol version bump Validation: unit, protocol, UI, live drills
Decision: the shipped feature is workflow schedules only. Temporary watchdog aliases or mappers may exist on the development branch to keep intermediate builds working, but the landed state removes public watchdog commands, API variants, TypeScript types, UI labels, and docs. Legacy watchdog payloads are accepted only through explicit one-way migration readers.

1. Kernel and Runtime Model

Replace WorkflowWatchdogDefinition with WorkflowScheduleDefinition. The kernel remains the runtime authority for schedule identity, trigger validation, dispatch decisions, overlap handling, run bookkeeping, and persistence. 

type WorkflowScheduleTrigger =
  | { kind: "interval"; every_seconds: number }
  | { kind: "cron"; expression: string; timezone: string };
  • Rename policy to overlap_policy, with values skip and queue.
  • Rename max_wakeups and wakeups_executed to max_runs and runs_started.
  • Rename watchdog_id references in queued prompts and run bookkeeping to schedule_id.
  • Rename queued prompt source from watchdog to scheduled.
  • Store last_scheduled_for_ms, last_run_at_ms, next_run_at_ms, last_status, last_error, and last_workflow_run_id.
  • Use schedule identifiers in logs, terminal events, status payloads, workflow apply reports, and persisted run metadata.

2. Cron Behavior

Cron schedules support seconds. The accepted cron grammar must include a seconds field before minute, hour, day-of-month, month, and day-of-week fields. The scheduler should also support common macros such as @hourly, @daily, @weekly, and @monthly where the selected Rust dependency can normalize them deterministically.

Required Semantics

  • Store timezone separately as an IANA name such as America/New_York.
  • Web-created schedules default to the browser timezone from Intl.DateTimeFormat().resolvedOptions().timeZone.
  • CLI and TUI commands default to UTC unless --tz is provided.
  • DST policy: nonexistent local times are skipped; repeated local times run once per schedule occurrence.
  • No offline backfill. After kernel or cloud worker restart, recompute the next future occurrence from current time.
  • Use a Rust cron/timezone dependency instead of hand-rolling calendar math. Primary candidates are cronexpr for cron evaluation and chrono-tz for IANA timezone validation.
Seconds are part of the production contract: validation, preview, persistence, command parsing, UI help text, tests, and drills must all treat seconds-capable cron expressions as supported behavior, not as a later extension.

3. Public API and Protocol

Add canonical local daemon requests and responses for schedules, then remove the public watchdog protocol variants before landing.

  • CreateWorkflowSchedule
  • ListWorkflowSchedules
  • SetWorkflowScheduleEnabled
  • RemoveWorkflowSchedule
  • PreviewWorkflowSchedule

PreviewWorkflowSchedule validates the trigger and timezone, returns normalized trigger data, and returns the next three scheduled run times. It must accept and preview seconds-capable cron expressions.

  • Bump LOCAL_DAEMON_PROTOCOL_VERSION and update protocol shape/hash tests.
  • Update packages/kernel-client, CLI types, terminal command catalog, shell executor, and iOS protocol fixtures to the new names.
  • Remove final public watchdog request/response variants and command catalog entries before landing.

4. Workflow-Code and Exports

Add workflow.schedule(endpoint, options) to workflow-code. Definitions, apply reports, packages, and exported artifacts use schedules and schedule_ids.

  • Accept old watchdogs only in a narrow legacy import and migration path.
  • Write and export only schedules after migration.
  • Update publication snapshots and status payloads from watchdogs and watchdog_count to schedules and schedule_count.
  • Ensure exported cron schedule definitions preserve seconds and explicit timezone data.

5. Web Terminal UX

Add a schedule icon button next to the existing Run and Deploy workflow controls in the workflow route. It opens a Schedule workflow modal that follows existing workflow run and deploy modal patterns while staying dense and operational.

Schedule Workflow Modal

  • Endpoint selector.
  • Trigger segmented control: Interval, Daily, Weekly, Monthly, Custom cron.
  • Interval fields for Every <number> <unit>.
  • Cron expression field for custom seconds-capable cron expressions.
  • Timezone select or input defaulting to the browser timezone.
  • Queue selector, overlap policy selector, max runs field, enabled toggle, and invocation prompt field.
  • Read-only Next runs preview driven by PreviewWorkflowSchedule.

Workflow Inspector and Console

  • Show schedule count, enabled state, next run, last status, and last error.
  • Provide enable, disable, and remove actions.
  • Keep management available in the workflow inspector and console context instead of creating a separate marketing-style page.

6. Terminal Commands

Add /workflow schedule ... command support with command-center suggestions and dynamic completions for workflow, endpoint, and queue references. Remove /workflow watchdog ... from the final UX. 

/workflow schedule add [workflow-ref] <endpoint-ref> --every 5m --tz UTC --overlap skip --prompt "..."
/workflow schedule add [workflow-ref] <endpoint-ref> --cron "30 0 9 * * 1-5" --tz America/New_York --queue urgent --overlap queue
/workflow schedule list [workflow-ref]
/workflow schedule enable <schedule-ref>
/workflow schedule disable <schedule-ref>
/workflow schedule remove <schedule-ref>
/workflow schedule preview --cron "15 30 14 * * *" --tz Europe/Berlin

7. Test Plan

Kernel Unit Tests

  • Interval schedules preserve current skip, queue, and max-run behavior.
  • Cron schedules compute next runs in UTC from IANA timezone input.
  • Seconds-capable cron expressions validate, persist, preview, and dispatch at the expected second.
  • DST skip and dedup behavior.
  • Disabled, removed, exhausted, active-run skip, active-run queue, and hidden publication warmup paths.
  • Legacy watchdog snapshot and package migration into WorkflowScheduleDefinition.

Protocol and Client Tests

  • Protocol version and shape/hash tests updated.
  • packages/kernel-client request builders and shell executor tests for all /workflow schedule commands.
  • CLI command handler tests for parsing interval, seconds-capable cron, timezone, queue, overlap, max-runs, preview, and validation failures.
  • Workflow-code compile, apply, export, and import tests for workflow.schedule.

Cloud Web Tests

  • React modal tests for schedule creation, timezone default, preview rendering, validation errors, and remove, enable, and disable actions.
  • Command-center tests for /workflow schedule suggestions and dynamic workflow, endpoint, and queue completions.
  • Published workflow and sidebar tests updated to schedule naming.
  • Preview tests proving seconds in cron expressions are preserved in normalized trigger data and rendered next-run times.

E2E Drills

  • Rename or replace live-watchdog-drill.mjs with live-workflow-scheduler-drill.mjs.
  • Add cron mode to the live scheduler drill using a near-future seconds-capable cron expression and explicit UTC.
  • Add TUI e2e drill: create workflow, add cron schedule, list, observe scheduled run, disable, remove.
  • Add web terminal e2e drill in arroba-cloud: open product frontend in the in-app browser, create a schedule through the modal, verify preview and scheduled run, then manage it through /workflow schedule commands.
  • Add TUI/web parity drill: create in one surface, verify schedule and run state appears in the other.

8. Assumptions and Landing Criteria

  • Final shipped naming has no public watchdog aliases.
  • A narrow legacy migration reader is acceptable only for old persisted or exported data and tests.
  • Cron support includes seconds-capable expressions in the runtime, protocol, CLI, web UI, previews, tests, and drills.
  • Cloud deployments always store explicit timezone; web UX must not rely on cloud host local time.
  • Temporary migration code is isolated, named as legacy migration code, and does not leak into new public APIs.
