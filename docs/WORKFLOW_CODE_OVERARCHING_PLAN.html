Arroba kernel plan

Workflow Code Overarching Plan

This plan refactors Arroba workflows into an A-plus scriptable surface, adds kernel-validated workflow-code injection, and gives authorized metaagents the runtime tools and training context needed to create, validate, apply, and run portable workflow scripts.

Target outcome: a user or authorized metaagent can write a self-contained JS/TS workflow-code artifact, inject it into the kernel, have it validated against real Arroba workflow primitives, create or bind agents, see the workflow on the session canvas, run it, export it, and apply it in another kernel with explicit generated-agent provider/model rebinding and target-kernel validation of existing-agent and extension requirements.

Decisions

  • Workflow-code is JS/TS only for the first-class supported authoring surface.
  • Workflow-code is a saved artifact type separate from general script extensions.
  • Workflow-code generates workflows; applying the same script twice creates two distinct workflows with fresh runtime ids.
  • Scripts do not assign workflow, node, edge, endpoint, queue, watchdog, schema, or generated-agent ids.
  • Existing-agent bindings are optional and local; portable scripts should include generated-agent specs or explicit fallback creation specs.
  • Publication is not authored by workflow-code. Export/import and existing workflow publication mechanisms operate after workflow creation.
  • Conditional routing is supported through node-driven handoffs as a required workflow-code capability. Multi-edge node prompts must make edge choices explicit enough for agents to route reliably.
  • Metaagents retain both construction paths: structured workflow-code and the existing manual workflow-edit commands.

Phase 1: Refactor Workflow Foundations

Configuration and limits

  • Add TOML configuration for the default session agent cap, with default 1024.
  • Add TOML configuration for workflow scheduler concurrency, with default maxConcurrent = 32.
  • Add explicit hard limits for nodes, agents, edges, queues, watchdogs, schema bytes, generated prompt bytes, script runtime, and script memory.
  • Allow workflow-code to request per-workflow limits when they stay within kernel/admin caps.

First-class workflow schemas

  • Create kernel-managed workflow schema records for inline schemas and optional imported JSON schema files.
  • Use schema ids for final outputs, intermediate outputs, handoffs, endpoint inputs, queued prompts, and watchdog outputs.
  • Keep compatibility readers for existing schema refs while migrating workflow internals to schema ids.
  • Validate schema syntax, size, references, and output compatibility before accepting a workflow-code artifact.

Workflow primitive normalization

  • Document and stabilize the script mapping for workflows, nodes, agents, edges, endpoints, queues, watchdogs, schemas, canvas layout, output capabilities, node limits, and extension requirements.
  • Keep the existing morphology: workflows contain nodes and edges; nodes own agents; endpoints enter the graph; queues and watchdogs are optional workflow scheduling primitives.
  • If queues are omitted, create the standard single queue required by the endpoint/node shape.
  • If canvas coordinates are omitted, use the kernel auto-layout service for the web terminal canvas.

Multi-edge routing prompt support

  • Extend node-level system prompt assembly to enumerate outgoing edge options, target labels, edge ids, handoff schema names, and routing expectations.
  • Render script handles in prompts only after compile/apply allocates real kernel ids.
  • Add prompt assembly tests showing a node with multiple outgoing edges has enough information to select and emit the correct handoff.

Phase 2: Script Injection, Validation, And Execution

Workflow-code artifact and builder SDK

  • Add a saved workflow-code artifact with source, metadata, schema imports, extension requirements, provenance, and validation/apply history.
  • Provide a JS/TS builder SDK whose methods return opaque handles rather than ids.
  • Compile scripts into a declarative workflow IR; the script cannot mutate kernel state directly.
  • Support generated agents with provider/model preferences and optional extension requirements.
  • Support existing-agent bindings only after authorization checks prove the caller may use that agent.

Kernel compile and id allocation

  • Compile creates a handle graph such as node:planner, edge:planner_to_worker, and schema:handoff.
  • Validation resolves handles, verifies graph consistency, checks limits, validates schemas, resolves provider mappings, and checks extension availability.
  • Apply allocates fresh real ids for the workflow graph and any generated agents.
  • The apply response returns a creation report mapping script handles, labels, and aliases to actual kernel ids.

Provider and extension portability

  • Represent provider/model choices as preferences that can be rebound at apply time.
  • Require explicit provider remapping when a target kernel lacks a requested provider or model.
  • Represent extension requirements in workflow-code so generated and authorized existing agents can receive the same Arroba extension grants used outside workflows.
  • Reject apply when required providers, models, or extensions cannot be satisfied.

Kernel interfaces

  • Add local/runtime protocol endpoints for validate, apply, run, export, and import of workflow-code artifacts.
  • Return structured diagnostics with source spans, primitive handles, and kernel validation causes.
  • Return structured apply results with created workflow id, created agent ids, node/edge/endpoint ids, canvas placement status, schema ids, and warnings.
  • Increment the shared local daemon protocol version and update protocol snapshot/hash tests for every serialized shape change.

Phase 2 Drills: End-To-End Validation Before Metaagents

  • Script validate drill: write a workflow-code file, inject it, and confirm validation diagnostics are correct without mutating session state.
  • Generated-agent apply drill: apply a script with no existing agent ids and verify agents, workflow, schemas, endpoints, queues, and canvas nodes appear in the session.
  • Existing-agent binding drill: apply a script that binds one authorized pre-existing agent and creates the rest.
  • Authorization drill: prove binding an unauthorized existing agent is rejected.
  • Canvas drill: verify explicit coordinates render correctly and omitted coordinates trigger auto-layout.
  • Run drill: run the generated workflow and verify final output and partial outputs match schemas.
  • Queue/watchdog drill: define queues and watchdogs explicitly, then verify omitted queues default correctly.
  • Provider drill profile: deterministic CI uses dev-stub; release/local live drills mix Codex, OpenCode, and Claude where credentials exist.

Dynamic Workflow Pattern Examples

The example suite is based on Anthropic's dynamic workflow documentation and agent-pattern guidance: Claude Code workflows, dynamic workflows blog, and Building effective agents.

Pattern Minimum Arroba toy workflow Validation focus
Prompt chaining 2 nodes: drafter to refiner. Sequential handoff, final schema.
Classify and act / routing 3 nodes: classifier routes to one of two specialists. Multi-edge conditional handoff from one node.
Fan-out and synthesize 3 nodes: two workers feed one synthesizer. Parallel workers, wait-for-all-inputs, intermediate schemas.
Adversarial verification 3 nodes: proposer, critic, judge. Conflicting handoffs, evidence schema, final decision schema.
Generate and filter 3 nodes: generator, filter, finisher. Structured candidate list and filtered output.
Tournament 3 nodes: two competitors and one judge. Comparable outputs, judge selection, scalable fan-in.
Loop until done 2 nodes: worker and checker, with checker routing back or completing. Loop edge, max turns, completion edge behavior.
Orchestrator-workers 3 nodes: planner, worker, synthesizer. Planner decomposition and worker assignment.
Evaluator-optimizer 2 nodes: optimizer and evaluator. Evaluator routes back until acceptance, then final output.

Phase 3: Metaagent Infrastructure

Runtime MCP tools

  • Add workflow-code tools under the existing metaagent runtime MCP bundle, using the arroba.meta.workflow_code.* namespace: arroba.meta.workflow_code.create, arroba.meta.workflow_code.read, arroba.meta.workflow_code.list, arroba.meta.workflow_code.update, arroba.meta.workflow_code.delete, arroba.meta.workflow_code.validate, arroba.meta.workflow_code.apply, arroba.meta.workflow_code.run, arroba.meta.workflow_code.export, and arroba.meta.workflow_code.import.
  • Expose these tools only to users and authorized metaagents.
  • Keep existing manual workflow construction/editing commands available to metaagents.
  • Record provenance for metaagent-created workflow-code artifacts and applied workflows.

Metaagent authorization

  • Metaagents may bind only agents they spawned or agents explicitly authorized for their control scope.
  • Metaagents must pass the same kernel validation as users before workflow-code can be applied.
  • Metaagents may choose between workflow-code and existing manual workflow commands based on task fit; workflow-code validation does not remove or weaken their existing manual edit path.
  • All workflow-code apply/run operations emit auditable session events.

Teaching metaagents

  • Add an Arroba workflow-code skill/context pack automatically available to metaagents.
  • Include the exact builder API, primitive mapping, schema rules, provider remapping rules, extension requirements, limits, routing conventions, and validation examples.
  • Include canonical scripts for every dynamic workflow pattern in this plan.
  • Teach the contract that metaagents must not invent fields outside the Arroba workflow primitive mapping.

Metaagent Drills

  • Observed creation drill: operator gives only a workflow goal; the metaagent writes the workflow-code artifact, validates it, applies it, and runs it.
  • Observed generated-agent drill: metaagent creates a workflow with all-new agents and verifies they appear in the session and canvas.
  • Observed existing-agent drill: metaagent uses one authorized existing agent and generated agents for the rest.
  • Observed provider-remap drill: metaagent exports/imports a portable script and applies it with provider/model rebinding.
  • Observed pattern drill: metaagent independently creates at least one conditional-routing and one fan-out workflow from the pattern suite.

Test Plan

  • Unit tests for builder IR, schema records, handle resolution, id allocation, provider remapping, extension requirements, and limit enforcement.
  • Kernel integration tests for validate, apply, run, export, import, canvas visibility, queued prompts, watchdogs, partial outputs, and final outputs.
  • Protocol tests for new local/runtime shapes and protocol version bump.
  • Authorization tests for user, metaagent, generated-agent, existing-agent, and unauthorized-agent cases.
  • Prompt assembly tests for multi-edge routing.
  • Deterministic CI drills with dev-stub and live release drills with Codex, OpenCode, and Claude.
