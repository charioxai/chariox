Arroba · Cross-repository implementation plan

Event-based workflow publication

Make external events a first-class workflow publication surface, backed by scalable AEGS discovery, AEDS delivery, kernel-owned queueing, and equivalent product flows in the web terminal and PTY-based TUI.

Runtime: arroba Registry + web: arroba-cloud Protocol bump required No agent-owned subscriptions AEDS / AEGS host separation First wave in scope
01 · Decision

Build one vertical slice before building the marketplace.

Freeze the manifest, identity, subscription, and delivery contracts first. Then build AEDS, a dummy AEGS, and the kernel event-publication path as one end-to-end slice. Add the shared TUI/web management protocol next, followed by the paginated registry, product catalog, GitHub AEGS, SDK, conformance suite, and the remaining first-wave integrations.

AEDS is the canonical name.

AEGS means Arroba Event Generation Server. AEDS means Arroba Event Delivery Server. Event publication is kernel core behavior, not a new agent extension type.

Mandatory product validation.

No implementation milestone is complete until the real product frontend has been exercised through the web terminal and the real TUI has been exercised inside a PTY. Backend tests, component tests, and mocked clients are necessary but insufficient.

02 · Product and architecture invariants

What must remain true.

Workflow-owned

A published workflow endpoint owns event publications. Agents do not register subscriptions, and deleting an agent does not revoke a published workflow.

Queue-native

After durable insertion, an event is an ordinary queued workflow prompt. Existing queue ordering, idle dispatch, runtime interaction, and execution behavior apply.

Environment-exclusive

The same canonical event interest may have only one active route in an execution environment. This prevents two publications from acting on the same worktree.

Host-independent

A publication binds to a stable environment identity rather than a transient kernel process. Rebinding moves delivery without recreating the logical publication.

Runtime-independent registry

Registry discovery is on demand and never sits in the delivery path. Existing publications continue working while the registry is unavailable.

Shared product path

Web and TUI use the same kernel services and serialized protocol. Cloud must not fork runtime behavior or proxy event delivery.

Declarative catalog

Registry entries are signed data and schemas. Browsing a service never downloads or executes publisher code in the browser or kernel.

Endpoint-shaped input

An AEGS produces a prompt plus optional artifacts. AEDS carries routing and delivery metadata but does not invent workflow execution semantics.

Separate failure domains

Hosted AEDS and hosted AEGSs do not share a machine. Delivery remains available independently of a generator failure, and generator load cannot exhaust AEDS.

03 · System boundary

Discovery is control plane. Delivery is runtime.

External provider GitHub, Jira, Slack, or another source emits a native event.
AEGS Authenticates the provider, normalizes the event, and applies source filters.
AEDS Authenticates publication, stores pending delivery, and routes to the environment.
Kernel Maintains an outbound connection and durably enqueues the prompt once.
Workflow queue Uses the existing dispatch policy and invokes the published endpoint.

Separately, the web and TUI ask the kernel to search the registry, inspect an AEGS, authorize a connection, enumerate provider resources, and configure event bindings. The registry is not contacted for each event and is not required after activation.

AEDS routes and AEGS logical subscriptions are deliberately separate durable records. The kernel reconciles each AEGS through its operator endpoint using a distinct scoped management capability. That authoritative, revision-fenced reconciliation gives the AEGS the binding, opaque connection, provider scope, canonical event-interest key, event type, and filter it needs to manage upstream subscriptions and map incoming provider events. AEDS receives only normalized occurrences and never provider credentials or source-specific subscription state.

Responsibility split

Component Owns Must not own
Registry Search index, publisher identity, signed manifests, categories, ranking metadata Runtime event traffic, workflow state, provider credentials
AEGS Provider auth, upstream subscription strategy, normalization, source reconciliation Kernel execution state or workflow scheduling
AEDS Producer authentication, durable pending deliveries, environment routing, retry Prompt interpretation, workflow dispatch policy, agent state
Kernel Publication state, environment claims, durable queue insertion, dispatch, lifecycle Marketplace ranking or provider webhook semantics
Cloud web Product presentation and interaction through shared kernel protocol Alternate subscription, queue, or delivery authority
04 · Registry at scale

Search and browse pages—not catalog snapshots.

The catalog is expected to become large. Selecting Event-based notifications must not cause the kernel or browser to fetch every service or every event definition. The registry API returns small summaries, opaque cursors, and facet counts. Details and event schemas are loaded only when opened.

Public query surface

GET /v1/event-generators
    ?query=pull+request
    &category=developer-tools
    &publisher_trust=official,arroba
    &sort=recommended
    &cursor=<opaque>
    &limit=24

GET /v1/event-generators/{generator_id}
GET /v1/event-generators/{generator_id}/versions/{version}
GET /v1/event-generators/{generator_id}/events
    ?query=assigned
    &category=issues
    &cursor=<opaque>
    &limit=50
GET /v1/event-generators/{generator_id}/events/{event_type_id}

Landing request

Returns bounded sections such as featured, most connected, recently added, and category summaries. Each section has an independent continuation cursor.

Search request

Searches provider, publisher, service description, event names, and capability tags. Results are relevance-ranked and cursor-paginated.

Category request

Returns a page plus subcategory and trust facets. The client may prefetch only the next page after the current page becomes visible.

Service detail

Loads the selected version, authentication model, operator disclosure, and a separately paginated/searchable event list.

Scalability requirements

  • Use cursor pagination; do not expose offsets whose cost grows with catalog depth. Registry continuations are query-bound keyset cursors, not encoded numeric offsets.
  • Treat cursors as opaque and bind them to the query, filters, sort, and catalog revision.
  • Return summary projections in browse/search. Fetch full manifests and JSON schemas only for the selected implementation and version.
  • Add explicit limits, maximum page sizes, request timeouts, and response-size budgets.
  • Support ETags and cache-control for landing sections, query pages, service details, icons, and pinned manifests.
  • Keep a bounded kernel cache keyed by registry, query fingerprint, cursor, locale, and compatible protocol range. Eviction must not affect configured publications.
  • Debounce product search and cancel superseded requests. Never accumulate every result page in an unbounded client store.
  • Filter or clearly mark incompatible AEGS versions using the requesting kernel's protocol capabilities.
  • Return an explicit lifecycle state: available, development_preview, or coming_soon. Browse remains possible for every state, but clients must not create subscriptions for coming_soon entries.
  • Never seed fictional installation totals. “Most connected” ranking is enabled only after the registry has privacy-safe, measured usage; editorial recommendation and implementation availability remain separate fields.
  • Do not auto-subscribe users when a publisher adds a new event. Publications pin an event type and version until explicitly migrated.

Kernel-facing protocol

Web and TUI send bounded operations such as EventCatalogLanding, EventCatalogSearch, EventCatalogBrowseCategory, EventGeneratorGet, and EventTypesList. Responses preserve opaque cursors. There is deliberately no ListEntireEventCatalog request.

Failure behavior:

A registry outage disables new discovery but does not disable configured publications. The UI may display a clearly dated cached page, while authorization, subscription health, and event delivery continue through their existing endpoints.

05 · Identity and trust

Provider, publisher, and operator are separate facts.

Provider Publisher Operator Product presentation
GitHub Arroba Arroba GitHub by Arroba · Arroba-maintained
GitHub GitHub GitHub GitHub · Official
GitHub Acme User GitHub by Acme · Community · Self-hosted
  • Implementation IDs are publisher-scoped. Arroba-owned integrations use names such as dev.arroba.github; provider-owned namespaces remain reserved.
  • “Official” requires explicit registry verification that the provider published or endorsed the implementation. Domain control alone is not sufficient.
  • An official implementation may coexist with an Arroba-maintained implementation. It does not silently replace, migrate, or revoke existing publications.
  • The authorization screen prominently identifies the operator because the operator, not the catalog, may handle provider credentials and event data.
  • Registry records and version manifests are signed. The kernel verifies the registry record, publisher identity, content digest, and supported protocol range.
  • “Most connected” is based on privacy-preserving aggregates of successful active connections, not manifest downloads. Low-volume exact counts are not exposed.
06 · Product UX

One model, adapted to two interfaces.

Web workflow side panel

  1. Select Event-based notifications in the Publication tab.
  2. Open the catalog landing view: recommended, most connected, recently added, and category navigation, each independently paged.
  3. Search or browse, then select a provider implementation.
  4. Inspect its publisher/operator badges, permissions, supported event categories, and data-handling links.
  5. Search and select multiple event types. The event list may itself be paginated.
  6. Authorize once, then enumerate accessible repositories, projects, sites, mailboxes, workspaces, or channels.
  7. Configure event-specific filters, target queue, and optional prompt templates.
  8. Review combined scopes, duplicate conflicts, and resulting bindings.
  9. Activate and display health, last delivery, and test-event controls.

TUI and slash commands

The TUI presents the same pages as navigable lists with incremental loading. Slash commands use the same kernel requests rather than a reduced secondary implementation. 

/workflow publication event browse [category]
/workflow publication event search <query>
/workflow publication event show <generator-id>
/workflow publication event events <generator-id> [query]
/workflow publication event add
/workflow publication event status
/workflow publication event test
/workflow publication event remove

Search results expose a “load more” action tied to the returned cursor. Interactive authorization shows an external URL or device flow without requiring a graphical browser inside the TUI.

Duplicate conflict UX

Already routed in this environment.

If the canonical event interest already targets another publication, show that workflow, endpoint, and queue. The allowed actions are Open existing, Transfer route, or Cancel. There is no “subscribe anyway” path in the same environment.

07 · Runtime and data model

Separate catalog identity, event interest, route, and occurrence.

Record Purpose Stable identity
EventGeneratorVersion Pinned AEGS implementation, protocol version, and signed manifest digest Publisher-scoped generator ID + version
EventConnection Opaque authorized connection to one provider tenant/account AEGS-issued connection handle
EventBinding Event type, canonical filter, prompt configuration, endpoint, and queue Publication-owned binding ID
EventInterest Deduplication key for equivalent source event plus filter Hash of AEGS, event type/version, connection scope, canonical filter
EnvironmentRoute Maps one interest to one active workflow endpoint in an environment Environment ID + event-interest key
EventOccurrence One provider fact transformed into prompt plus optional artifacts AEGS occurrence ID and AEDS delivery ID

Enforce a unique active route on (execution_environment_id, event_interest_key). A single publication may hold many bindings, but each binding is independently versioned, reconciled, tested, paused, transferred, and deleted.

Delivery envelope

{
  "delivery_id": "opaque-aeds-id",
  "binding_id": "opaque-publication-binding-id",
  "event_type": "pull-request.opened",
  "event_type_version": 1,
  "occurred_at": "2026-07-27T09:45:00Z",
  "prompt": "Review pull request #482 in owner/repository.",
  "artifacts": [
    {
      "name": "pull-request.json",
      "media_type": "application/json",
      "reference": "opaque-artifact-reference"
    }
  ]
}

Prompt and artifact limits reuse the workflow endpoint contract. AEDS may enforce a defensive transport envelope ceiling, but it does not introduce a separate product payload model. Canonical event metadata stays inline. An AEGS includes an artifact only when the reference is durable and retrievable by the workflow; it must not advertise synthetic adapter-local references.

Connection and acknowledgement

  • The kernel opens one authenticated outbound persistent connection to AEDS.
  • On reconnect it presents stable kernel/environment identity, active route claims, and the last accepted delivery cursor.
  • The kernel acknowledges a delivery only after the durable, idempotent queue transaction succeeds.
  • A lost acknowledgement may cause network redelivery, but the existing delivery_id prevents a second queued prompt.
  • After insertion there are no special event semantics: ordinary workflow queue and dispatch rules apply.
08 · Publication and deployment lifecycle

The publication persists; the route can move.

Operation Required behavior
Republish in same environment Preserve binding identity and upstream subscription; update endpoint revision atomically.
Move environment to new kernel Rebind the route, fence the old kernel, and resume from the durable delivery cursor.
Deploy to a distinct environment Create an independent environment route and, when needed, an independent logical AEGS subscription.
Publish same interest twice in one environment Reject activation and expose the existing owner; permit an explicit atomic transfer.
Pause publication Stop new delivery for its route without deleting workflow definition or authorization.
Delete published workflow Tombstone routes, revoke delivery capabilities, reconcile AEGS state, and retain auditable status.
Kernel or computer reboot Reconnect automatically, reassert claims, reconcile subscriptions, and drain pending delivery.
AEGS manifest deprecation Keep the pinned version active where safe; surface migration health and require explicit migration.

10 · Hetzner deployment

Promote locally proven services into separate failure domains.

After the complete local product slice passes, deploy AEDS and the dummy AEGS to Hetzner and repeat the acceptance matrix over public TLS. During implementation, a new Hetzner machine will be reserved. The deployment design must keep AEDS and AEGSs on different machines and must not assume that the existing relay machine has spare capacity. If the new machine is not yet available, isolated containers on the local development machine provide a nonblocking deployment rehearsal.

Host-separation rule.

AEDS and AEGSs must never be co-located on the same host. The existing relay host is protected capacity: it may receive a bounded temporary staging role only after a fresh CPU, memory, disk, network, and port preflight. If the new reservation plus safely available capacity cannot provide distinct AEDS and AEGS hosts, provision another machine rather than weakening isolation.

Local-container fallback.

Machine procurement does not block implementation. Run AEDS and each AEGS as separately limited local containers with distinct networks, volumes, secrets, identities, and published loopback ports. Exercise the same images, configuration, persistence, restart, rollback, and product drills intended for Hetzner. This proves deployability but not physical failure-domain separation, public TLS, host reboot, or cross-machine recovery; those gates remain required on Hetzner.

Target host roles

Host role Services Isolation and persistence
Relay host Existing hosted relay and its Caddy edge Remains relay-first. It is not general event-runtime capacity and is not changed without a passing capacity and regression preflight.
AEDS host AEDS, loopback health/metrics, Caddy HTTPS/WSS edge Dedicated service identity, delivery database/volume, backup target, and producer/kernel credentials. No provider OAuth secrets.
AEGS host Dummy AEGS initially; GitHub and later first-wave AEGSs as isolated services Separate container, identity, secrets, limits, state, and logs per AEGS. No access to AEDS storage or another AEGS's provider credentials.
Additional AEGS hosts Generators moved out as traffic, privilege, or provider isolation requires Same deployment contract. Registry identity remains stable when the operator changes placement.
Local fallback One AEDS container plus separately isolated dummy and first-party AEGS containers Development-only deployment rehearsal. Separate networks, volumes, secrets, resource limits, and ports emulate host roles but do not satisfy Hetzner acceptance.

Deployment shape

  • Produce immutable Linux OCI images for AEDS and every Arroba-maintained AEGS. Deploy pinned digests tied to the exact revision of each owning service repository plus compatible OSS and Cloud revisions; do not deploy by pulling a mutable branch on the host.
  • Run persistent staging containers under systemd with restart limits, explicit service users, read-only roots where practical, bounded CPU/memory, and separately mounted data and secret paths.
  • Bind application ports to loopback. Caddy exposes distinct HTTPS/WSS hostnames for AEDS and for each externally reachable AEGS webhook/OAuth surface.
  • Permit only SSH and public HTTP/TLS at the host firewall. Cross-machine AEGS-to-AEDS traffic uses public or private TLS with scoped producer credentials; it never uses a shared filesystem.
  • Store AEDS pending deliveries and route state on a durable volume. The first single-node staging implementation may use SQLite/WAL behind a storage interface, but must prove restart and backup/restore before acceptance.
  • Give each AEGS its own durable connection/subscription store. Provider credentials and webhook secrets remain in that AEGS's protected secret boundary and never enter AEDS, the registry, publication packages, or workflow prompts.
  • Export readiness, structured logs, bounded metrics, build/version identity, storage health, connection counts, pending-delivery depth, retry age, and subscription reconciliation status without exposing prompts, artifacts, or credentials.
  • Keep the current image and one known-good rollback image. Upgrade one service at a time and verify delivery continuity before promoting the new version.

Promotion ladder

  1. Local fixtures: protocol, state-machine, retry, dedupe, lifecycle, and conformance tests.
  2. Local product: real web-terminal and PTY/TUI setup, delivery, conflict, health, test-event, and deletion flows.
  3. Local deployment rehearsal: run the immutable AEDS and AEGS images in isolated local containers with persistent volumes, restart policies, resource limits, upgrade/rollback, backup/restore, and product validation. Use this whenever the new Hetzner machine is not yet available.
  4. Ephemeral Hetzner: use the existing SSH preflight, artifact provenance, run ownership, resource safety lease, and cleanup machinery to stage temporary AEDS and AEGS services on their designated hosts.
  5. Persistent Hetzner staging: install systemd-managed pinned images, Caddy routes, durable volumes, secret files, backup, monitoring, and rollback.
  6. Failure validation: restart each service, reboot each host, interrupt the cross-host network, lose an acknowledgement, exhaust a bounded queue, rotate credentials, restore from backup, and verify recovery.
  7. Live provider: receive a real provider event and execute the target workflow exactly once through both product surfaces.
  8. Registry promotion: only then mark an Arroba-operated AEGS available or recommended. The dummy AEGS remains a development fixture.

Deployment artifacts and runbooks

  • OCI build definitions, digests, SBOM/provenance record, and version endpoint.
  • Systemd unit templates and least-privilege environment/secret-file contract.
  • Caddy host routing and TLS readiness checks without embedding credentials.
  • Install, upgrade, health-check, rollback, backup, restore, and removal commands.
  • Guarded Hetzner drill that targets exact configured hosts, refuses broad cleanup, labels every owned resource, and removes only run-owned temporary artifacts.
  • Retained evidence containing source revisions, image digests, host roles, service versions, restart/reboot timeline, queue/delivery results, web screenshots, and PTY/TUI transcripts.
11 · Implementation milestones

Executable scope ends with the first wave.

M0 · Contract

ADR, schemas, and fixtures

  • Finalize terminology, boundaries, identity, and environment uniqueness.
  • Establish the public/private repository boundary and extract production service runtimes before deployment: one private AEDS repository and one private repository per Arroba-maintained AEGS.

AEDS + dummy AEGS + kernel vertical slice

  • Implement kernel connection, heartbeat, reconnect, resume, and reconciliation.
  • Add event publication and binding persistence, environment claims, and idempotent queue insertion.

  • Prove test-event delivery through the real workflow endpoint queue.

Shared management surface and TUI

  • Add bounded catalog search/browse/detail/event-list requests with cursors.

M4 · Deployment

Local-container fallback and Hetzner gate

  • Build deployment images from the extracted private AEDS and per-provider AEGS repositories; OSS cross-repository Compose is only a local orchestrator and is not deployable production provenance.

  • Add immutable OCI builds, systemd units, Caddy routes, durable volumes, protected secrets, readiness/metrics, backup/restore, and rollback.
  • Run ephemeral remote validation before installing persistent staging services.
  • Connect a real local kernel to remote AEDS over WSS and deliver from the dummy AEGS running on its separate host.
  • Repeat web-terminal and PTY/TUI acceptance, then service restart, host reboot, cross-host partition, ACK loss, credential rotation, and restore drills.
M5 · GitHub

First production AEGS

  • Extract the implementation into the private arroba-aegs-github repository with independent CI, image, versioning, security scanning, deployment configuration, and catalog manifest.
  • Implement GitHub App authorization, installation/repository discovery, webhook verification, source deduplication, and event normalization.
  • Ship pull request opened first, then the approved GitHub event set through the same manifest and event-binding model.
  • Validate offline kernel delivery, reboot, retry, duplicate conflict, transfer, and publication deletion end to end locally.
  • Deploy the GitHub AEGS to its Hetzner AEGS host, receive a real GitHub webhook, publish across machines to AEDS, and repeat product and failure validation before registry promotion.
M6 · Platform

AEGS SDK and conformance suite

  • Provide manifest validation, auth helpers, AEDS client, event/artifact builders, signature/replay helpers, and a local test harness.
  • Add lifecycle, retry, schema compatibility, security, and registry publication conformance tests.
  • Document first-party, official-provider, community, and self-hosted paths.
M7 · First wave

Complete the initial integration set

  • Give every Arroba-maintained integration its own private repository, CI, immutable image, protected credential boundary, and publisher-scoped catalog identity.
  • Jira Cloud: OAuth 2.0 dynamic webhooks and renewal.
  • Linear: organization/team webhook subscriptions.
  • GitLab: project/group events and self-managed host support.
  • Sentry: alerts, issues, and project service hooks.
  • Slack: Events API, workspace auth, event filtering, and scopes.
  • Run the complete web-terminal, PTY/TUI, reconnect, deletion, and environment exclusivity matrix locally and against the separate Hetzner AEDS/AEGS hosts for every first-wave AEGS.

Mandatory runtime scenarios

  • Registry has millions of entries in the test index; first page remains bounded.
  • Rapid search replacement cancels stale requests and does not reorder results.
  • Category and event cursors remain stable within a catalog revision.
  • Registry unavailable while an existing publication continues receiving events.
  • Kernel offline when an event occurs; prompt appears after reboot and reconnect.
  • Connection drops between durable enqueue and ACK; only one prompt is visible.
  • Two workflows request the same event interest in one environment; second activation fails visibly.
  • Workflow moves to a different kernel; old kernel is fenced and pending delivery resumes.
  • Same workflow deploys to a distinct environment; independent routing is explicit.
  • Publication deletion revokes delivery and upstream subscription state reconciles.
  • AEDS and AEGS run on different Hetzner machines; stopping or saturating an AEGS does not make AEDS unavailable.
  • AEDS restarts and its host reboots while pending deliveries survive and resume from durable state.
  • The AEGS host restarts, reconnects to its providers and AEDS, and reconciles logical subscriptions without creating duplicate environment routes.
  • A cross-host partition recovers without lost accepted events or duplicate workflow prompts.
  • A pinned release is rolled back on one host without modifying the other host or the existing relay service.
13 · Definition of done

The first wave is complete only when all surfaces agree.

Architecture

  • Event-based is a first-class workflow publication surface.
  • Kernel remains workflow and queue authority.
  • Registry is paginated, searchable, cacheable, and absent from delivery.
  • AEDS and AEGS responsibilities remain distinct.
  • Production AEDS and AEGSs live only in their private owning repositories; OSS and Cloud contain no duplicate production implementation.

Safety

  • One active event interest per execution environment.
  • Signed manifests and clear publisher/operator identity.
  • Durable enqueue and delivery-ID dedupe.
  • Explicit transfer, deletion, and credential revocation.

Product

  • Large-catalog browse, search, categories, and paging work in web and TUI.
  • Multiple events can be configured in one publication flow.
  • Conflict and health states are understandable and actionable.
  • Real web-terminal screenshots and PTY/TUI transcripts are retained.

Integrations

  • GitHub, Jira, Linear, GitLab, Sentry, and Slack pass conformance.
  • Each passes live delivery, reboot, retry, transfer, and deletion drills.
  • SDK and documentation are sufficient for a non-Arroba publisher.
  • Second-phase integrations remain explicitly deferred.

Deployment

  • AEDS and AEGSs run on separate Hetzner machines.
  • The existing relay host remains within measured resource headroom.
  • Images are immutable and support a proven rollback.
