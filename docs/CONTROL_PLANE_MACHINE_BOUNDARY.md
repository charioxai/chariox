# Owned kernels and optional control-plane machines

MP-08 / MP-09 / MP-10 / MP-11. Design amendment, 2026-11-02; no protocol allocation or product implementation in this change.

A kernel can reach another kernel the user owns, transfer selected environment and accounts, and run ordinary Room commands there. A connected hosted control plane may additionally offer machine acquisition using the owner's session. Machine rental, its images, shutdown policies, provider selection and metering belong to Cloud. A self-hosted installation retains owned-kernel tools and exposes no rental or automatic-offload option.

Miguel's 2026-11-02 decisions replace the earlier separate managed-environment, disposable-worker and offload-machine designs with one managed-VM product. His ~12:10 Berlin answers bind this revision: every normal shutdown preserves the machine for a later Start with its state; internal retention may expire saved state only when keeping it costs Chariox money; users and agents see no prices, rates or quotes. The existing Cloud rental entry and admission stripe stay unchanged. The coordinator's 10:30Z clarification removes dedicated offload machinery: an agent rents/uses an ordinary managed VM, copies files with existing tools, runs commands and retrieves results itself. No job tool, `offload_job` purpose, files-back/conflict service, queued-command VM runner or leased-process runner is added. Generic execution leases remain useful for placing a home-owned agent on any owned kernel; they do not constitute another rental product.

The Cloud implementation/acceptance design is `chariox-cloud/docs/MANAGED_VM_RENTAL_PLAN.md` and its companion `MANAGED_VM_ACCEPTANCE_ROWS.md`. This note defines the OSS side and supersedes the old rental architecture/matrix in the managed-parity ledger. It preserves ordinary/managed runtime parity and narrowed semantic review of changed security-critical anchors. Historical evidence remains bound to its original source; this design grants no acceptance PASS.

Development is independently Empty or exact Project repository selection; provider accounts and Git credentials retain their existing separate selection. Source-backed layers use the same source. This is reuse, not a new design. The current [launch input](../packages/kernel-client/src/ipc-managed-environment-requests.ts) line 61 and [export request](../apps/kernel/src/managed_context/kernel.rs) line 23 expose no per-extension selector; the [exporter](../apps/kernel/src/managed_context/kernel/export.rs) line 156 enumerates all four kinds. ## Proposed neutral protocol surface

These are shape names, not assigned protocol numbers. Implementation must request the appropriate local/peer version from the coordinator and update snapshots, hashes and focused drills only when serialized contracts change.

- `ControlPlaneCapabilities`: issuer/account identity, revision, optional `machine_allocation` capability, action/catalog references. Authenticated transport/session binds the advertisement to its issuer/account. A capability descriptor is data, never executable client code or target-kernel authority.
- `RequestControlPlaneMachine`: idempotent request id, capability revision, generic CPU/memory/disk/architecture requirements, optional opaque class ref, policy ref and context selection ref. No quote or rate requirement. `GetControlPlaneMachine`, `StartControlPlaneMachine`, `StopControlPlaneMachine`, `DeleteControlPlaneMachine` and `UpdateControlPlaneMachinePolicy` use the same stable scoped allocation ref. Mutations carry request id and expected revision. Access uses the existing kernel request route, not a dedicated offload tool.
- `ControlPlaneMachine`: allocation ref, state/reason, canonical kernel/machine/realm/key binding when enrolled, access state, policy projection and available actions. Omit provider/image/snapshot/storage/retention internals, all prices/rates/quotes/costs and usage-ledger refs from user/tool projections. Never return an owner session, infrastructure credential or bootstrap secret. Clients show ordinary machine state/progress, without internal error strings or connection paths.
- `KernelActivityReport`: kernel id/generation, monotonic sequence, transition time and active agents/commands/transfers. `KernelQuiescence`: reservation id, expected sequence/generation and outcome. These extend the existing report/fence; Cloud interprets the facts against its policy.

Cloud's policy choices (time limit, last work finished with warning, manual), pricing tables, credit/quota checks, image refs and adapter details do not become OSS enums or constants. A generic kernel carries only opaque control-plane policy/action refs and validated projections. Generic activity can be useful to other control planes without introducing their business rules.

A self-hosted control plane advertises no Cloud allocation capability; rental actions, costs and rule choices are absent from clients and tool discovery. A forged/stale call is refused before resource dispatch. Cloud independently checks the owner session/account/entitlement on every mutation; advertising an invented capability cannot spend Chariox's money. Ordinary gateway/exec/files and leases between user-owned machines continue to work without Cloud rental entitlement.

## Authorization and access handoff

The kernel may acquire/start/stop/delete a machine using the owner's connected session when the effective caller already has authority for that action. This replaces the retired rental controls only. Room membership alone does not authorize spending or owner-level target access. The kernel keeps session credentials private and follows the product's session refresh/revocation path; an existing token field is not evidence that current enrollment supplies it. Implementation must verify that binding. Cloud checks owner/account/entitlement and internal budget on each mutation; there is no customer quote acceptance.

The new kernel enrolls to the owner, exposes its canonical identity through the normal inventory and attaches to the owner's gateway. The target still applies its ordinary access decision, including human-only operations and revocation. Reuse an existing grant/sudo window when applicable; where a decision is required, use the existing kernel-owned interaction visible to the owner's clients. Do not add SSH, an agent as an access proxy or a parallel rental grant. Rental readiness distinguishes enrolled, context-ready and access-ready rather than hiding an unusable machine behind provider “running.”

Runtime commands/files never pass through Cloud. The relay carries encrypted traffic. Cloud persists an accepted shutdown rule and may stop/preserve its machine after the source kernel disappears; it never schedules provider runs or decides Room state. The kernel's activity fence closes the race between accepting work and acknowledging idle shutdown. A hard user deadline/manual Stop can end active work; a last-work rule cannot treat a missing heartbeat as idle. Kernel shutdown/recovery flushes persistent state and truthfully marks interrupted work; it never silently replays commands or turns.

The same ManagedEnvironment owns each run generation, provider compute resource and private saved-state reference. Stop is complete only when current private state is verified and compute is stopped. Start restores one instance with the same kernel id/key, enrollment and canonical machine, preserving workspace, environment, selected product-transferred accounts, Vault state and history without reimport. The ordinary restore entry verifies the pinned installed release and target binding; it never redeems the initial bootstrap grant again. Old connection/activity generations are invalidated. If identity/state cannot be restored, Start remains incomplete for recovery; it cannot substitute a blank machine or silently enroll a new identity.

Start/Stop/Delete/retention use the same Cloud operation/revision fencing. A Start pins the saved state against cleanup; Delete is terminal; a stale operation cannot reclaim the next generation. Each accepted Start begins the selected time limit once for its new run; retries and process/API restarts do not reset it. Last-work arming also resets for a fresh run, so initial zero activity never immediately stops it. Private saved state is not a shared/base image or a credential-transfer route to another owner.

Cloud's provider-specific retention policy is internal. Free images do not expire just for age; charged images may expire after a few days. If a current viable free copy remains, collect redundant paid state rather than expire the machine. On permitted expiry, user history shows “No longer available,” Start is absent and the existing rental action remains available; there is no provider/image/cost wording, internal error text or blank-machine replacement. Explicit Delete removes the active machine and revokes its enrollment/grants. Operators retain deletion/usage reconciliation until all private resources are absent. Stopped state remains expected inventory, not orphan leakage.

## Install, preservation and deletion responsibilities

Base images hold slow preinstalls, a small trusted verifier/installer and public trust roots. They contain no runtime identity, account state, owner session, workspace or bootstrap grant. Routine kernel releases do not rebuild images. On each allocation Cloud delivers the same protected one-time envelope and immutable signed-release reference; the generic installer authenticates every executable before installing/starting the kernel/bootstrap. Reuse signature/hash verification in [release.rs](../apps/kernel/src/managed_bootstrap/release.rs) lines 90, 168 and exchange/supervision. A failed download/signature is terminal with cleanup, never a fallback to an older runtime. Reboot retains the allocation's pinned release/identity rather than re-enrolling or upgrading implicitly.

In BASE-IMAGE, kernel means the signed kernel software, not the user's kernel context. After fresh installation the M28 Empty/copied choice still applies; it never imports the source identity or history. Later Stop/Start preserves the target's own identity, context and subsequent history without another source copy.

Keep reusable bases clean. A per-machine private image intentionally retains the owner's installed kernel/identity, workspace and selected account/environment state; Cloud never reads its contents. Ordinary shutdown flushes and settles the product's persistent paths before provider save. Cold restore must prove those paths and keys survive the provider's exclusions and remain usable. A normal Start restores the pinned release, not an implicit upgrade or fresh enrollment.

Cloud keeps ManagedEnvironment and folds useful expiry/deletion-evidence logic into it. Delete rental-specific DisposableWorkerAllocation routes/handlers/bootstrap branches as their replacements land. The current [retirement gate](../apps/kernel/src/runtime/router/retired_cloud_controls.rs) line 5 rejects the old requests before routing; do not remove it wholesale and accidentally restore unrelated human-only controls. Retain generic execution leases, account transfer, installed release authenticity, gateway access, needed generation/operation fences and shared storage helpers. Remove replaced rental reimage/in-place A-B update/compatibility and mandatory volume paths. Explicit version replacement must preserve the prior machine until transfer succeeds; normal stopped machines retain their state.

One internal per-user ComputeUsage aggregate spans compute segments for each run/attempt and retained-storage segments. Stop settles compute, Start appends a segment, and Delete/charged retention expiry closes the aggregate after final census; failed create closes after compensation. Usage observations survive retries/restarts and cumulative counters are reconciled by delta. There is no ledger ref, price, quote, rate or consumption amount in the neutral user/tool projection. Cloud admin/operator surfaces alone expose metering for future pricing/tiering.

Acceptance belongs to the revised seventeen-row Cloud plan: actual signed install, current changed security-anchor review, owner access, real provider turns, ordinary agentless remote work, reconnect, three preserving shutdown rules, cold stop/relaunch, credential protection, internal compute/storage metering and separate retained-state/final-deletion censuses.
