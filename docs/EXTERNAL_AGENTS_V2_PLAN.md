# External Agents v2 Plan

**Status:** Approved by Miguel, 2026-10-20 (all eight questions answered, none open). Plan only, no code. Protocol numbers below are placeholders (`NEXT`, `NEXT+1`); the coordinator allocates them.

**Decisions taken on the open questions (Miguel, 2026-10-20):**

1. One local passkey grant reaches all of the user's machines; no per-machine narrowing. The popup says so and revoke is immediate.
2. The remote kernel also enforces the human-only set when a request carries `on_behalf_of` (section 5.3). One shared function; no Cloud and no link involved.
3. Machine file requests (`Read/Write/StatMachineFile`) are added, chunked, resumable, sha256-checked, 2 GiB cap (section 9.1).
4. b3 becomes a real signed kernel in Miguel's hosted account through a one-time ssh bootstrap. This is an interim step: it is replaced when b3 becomes a Path-1 Chariox-managed machine or a BYOM machine.
5. Verify first, then decide: Cloud already lists kernels for **user** sessions (waiting room, remote TUI picker). Step 1 checks whether a **kernel** credential can call that list. A kernel-scoped read-only variant is added only if it cannot (section 3.3).
6. Approval deep link (128-bit, single use, 10 min, account and kernel bound) ships as an extension after the core. Self-hosted uses a remote TUI until the native mobile client exists.
7. `apps-external-agents` is closed out as in section 10.
8. The popup default stays 8 h; "until the agent exits" is opt-in; a kernel restart still ends it.

**Extension added 2026-10-21, waiting for Miguel's review:** section 3.6 (several kernels on one machine: the target is a kernel, `--kernel`, `chariox kernels`, `kernel_*` codes) and section 14, events for external agents (one event subscription per grant following sessions or single agents on any kernel, filtered where the change happens, one cursor and one wait; it ends only with the grant or when the agent cancels it), with rows EA2-26..EA2-34.

## 1. Summary

Today an external agent (Claude Code, Codex, OpenCode started by the user, not by Chariox) can get one passkey-approved grant and then act as the user on **its own local kernel only**. v2 makes four changes:

1. A grant can last **until the agent process exits**.
2. The local kernel becomes a **gateway**: the agent names a target kernel and the local kernel forwards the request over the relay, exactly as a remote TUI would. The agent never talks to Cloud or the relay.
3. Kernels are **discovered by the local kernel**, like a terminal does it (a machine can run several kernels, section 3.6). The agent sees `chariox kernels` and `--kernel <name>`.
4. **Passkey approvals never pass through the agent.** The agent only receives a pointer; the user answers in a Chariox client. (Extension, after the core.)

The goal behind it: the coordinator (Claude Code on Miguel's Mac) works on the Mac and on b3 through this surface and drops ssh to b3, except as break-glass for a kernel that is down.

## 2. Goals and non-goals

### Goals

- One passkey grant on the local kernel gives an external agent the user's ordinary authority on every machine the user's own terminals can reach.
- Everything stays kernel-owned: the local kernel is the only thing the agent talks to; the remote kernel is the authority for its own sessions, agents, terminals and files (AGENTS.md rules 1, 3, 4).
- Every outcome is definitive: success, refusal with a reason, or "kernel offline/unreachable" with what to do next. No silent fallback to another kernel or to local.
- Revocable and visible from any Chariox client, on the machine that granted it.
- Nothing installed into the agent's harness. The agent learns the surface from `chariox guide`.

### Non-goals

- Cloud sign-in, tokens or Cloud calls by the agent. An external agent requires a local kernel (no kernel, no access; ssh is break-glass).
- Isolating agents from the user's own files or ssh keys (D12 stands). A same-user shell agent could already run `ssh`; v2 does not add power over that, it makes the access explicit, audited and revocable with one passkey.
- Agents answering passkey approvals, minting grants, reading secret values (D16, D3 stand).
- Kernel-to-kernel peer requests from agents. The gateway speaks the **client** protocol a terminal speaks, never the kernel peer protocol.
- Selkies/noVNC work, a root agent in Cloud (stratum 4), a native mobile client.
- Windows peer identity.

## 3. The five decisions and how each maps onto code

### 3.1 Grant lifetime "until the agent process exits" (decision 1)

**What exists.**
- `RequestKernelAccessRequest { holder_pid, lifetime_minutes }` (`apps/kernel/src/local/api/types/kernel_access.rs`). The grant record `Grant` (`runtime/kernel_access.rs`) has a `deadline: Instant`; `sweep_kernel_access` ends a grant when the deadline passes or `holder.alive()` is false.
- Holder = nearest ancestor that is a provider harness (`kernel_access/requester.rs::default_holder`), identified by PID + path + start time + exec version (`kernel_access/process.rs::ProcessIdentity`). Descendants are admitted; a new process with a reused PID is not (`access_ended_for`).
- Popup lifetime comes from the approve answer's numeric `custom_reply` (up to `grant_max_minutes` = 1440); an "ends in 5 minutes, extend?" popup follows.

**What changes.**
- A grant has a **term**: `Minutes(n)` or `UntilHolderExits`. One enum replaces `lifetime_minutes` on the request, on `KernelAccessGrant`, and in `Grant`; `deadline` and `expires_at_ms` exist only for `Minutes`. Asking for both is an error.
- The popup offers three choices: "until the agent exits", "8 hours" (default), "24 hours". The 8 h default and 24 h cap stay.
- `UntilHolderExits` grants have no extension popup. They end on holder exit, explicit revoke, passkey rotation or kernel restart (grants stay in kernel memory, so a kernel restart still means a new grant; this is the cost of "nothing on disk").
- **Exit detection (built in step 1, no new watcher).** Liveness is the existing identity check (PID + path + start time) in `sweep_kernel_access`. It already runs on every list, on every request admission, on the 100 ms tick of each open holder connection and on the kernel pump, so the grant and its subscriptions end as soon as anyone looks, without a pidfd/kqueue watcher. Measured on b3 with a real Claude Code harness killed by exact PID: grant list empty after 30 ms, orphaned former descendant refused after 32 ms (EA2-01/02, evidence `extagent/r3/green-impl-1`). macOS uses the same check; its drill is a Mac cell.
- Binding is unchanged: ProcessIdentity compare, descendants admitted, no inheritance by a new process.
- Grants stay listed (`ListKernelAccessGrants`) and revocable (`RevokeKernelAccessGrant`) from every Chariox client. The list shows the term.

**Deleted.** `lifetime_minutes` on the request and on the grant summary; `lifetime_minutes` stays on the popup shape (`PasskeyPrompt`) only as the minutes copy of a minutes term, for clients that predate the typed `term` (the hosted web popup in `chariox-cloud` reads it until it is updated), and for sudo windows. The `custom_reply` answer is one parser, `KernelAccessTerm::from_reply` (`until_exit` or minutes), checked once at the answer boundary.

### 3.2 Everything, but only through the local kernel (decision 2)

**What exists.**
- The Unix socket admits a request only for a bound grant holder (`runtime_transport/unix_access.rs`); every request passes `authorize_external_request` (`runtime/state/kernel_access/policy.rs`). Its refusal list contains the pairing, relay, Cloud identity and `ResolveKernelClientConnection` requests, and the docs say a grant cannot "attach to a REMOTE kernel or issue kernel-peer requests" (`docs/PROTOCOL.md`, Kernel access).
- A frame has no target kernel. A holder can already ask the local kernel for leased remote workers (`MoveAgentToRemote`, `ListRemoteMachines`), which is the local kernel's own business.
- A remote TUI gets a relay URL and a short-lived relay token from its kernel (`ResolveKernelClientConnection`, `IssueCloudRelayClientToken`; hosted) or a kernel-issued terminal grant (`TerminalPairingLinkJoined`, `terminal-grants.json`; self-hosted), then speaks the normal encrypted client protocol to the target kernel as a `RemoteClient`.

**What changes.** A new gateway inside the local kernel (section 5). The agent keeps one connection: the Unix socket. A frame may carry `kernel`; the local kernel authorises the request locally (same policy function), then forwards it as a terminal-class client of the target kernel and returns the response. No relay token, key or Cloud credential ever reaches the agent; `ResolveKernelClientConnection`, `IssueCloudRelayClientToken` and the pairing/relay requests stay refused.

**Deleted.** The "no remote kernel" rule in the access plan (D6 stratum 2 "only the local kernel", D9) and in `PROTOCOL.md`; the per-component "remote not supported" notes on the external path (section 4 lists them). What stays refused is the credential-bearing set, not "remote".

### 3.3 Discovery like terminals (decision 3)

- **Hosted.** The local kernel fetches its owner's kernel list from Cloud (heartbeat freshness), the same list the web waiting room and the remote TUI picker show. Relay target selection stays Cloud's job (AGENTS.md rule 4).
  - Cloud already lists kernels, but the open point was whether a **kernel** credential, the durable one that already renews terminal tokens, may call that list.
  - **Verified in step 1 (2026-10-20, `chariox-cloud` main `00658b85a`, OSS `landing/oss-r1`): yes, nothing is added to Cloud.** The list is `GET /relay/targets?accountId=&realmId=` (`apps/api/src/routes/relay.ts` → `relay/service.ts::listRelayTargets` → `relay/targets-repository.ts::listRelayTargetsForRealm`). Its auth takes a user session bearer **or** `x-chariox-kernel-credential` **or** a machine credential (`http/relay-directory-credential.ts`). With a kernel credential it requires that the credential's realm equals the requested realm and that its user is a member of the account. It returns every `DAEMON` target of the realm with `daemonId`, alias, `machineId`, machine alias, `status`, `lastHeartbeatAt` (freshness applied), providers and `acceptingLeases`. The kernel already calls it with the kernel credential: `get_cloud_kernel_directory` (`apps/kernel/src/runtime/cloud_api_client/http.rs`), used by relay discovery and the remote inventory behind `ListRemoteMachines`. So the hosted inventory source reuses the existing remote-inventory projection; the one limit is that it is realm-scoped (machines of the kernel's own realm), which is what "the user's machines" means today.
- **One source interface.** The gateway's kernel list sits behind a single inventory-source interface with one job: "give me the user's kernels with name, machine, status, last seen, protocol and how to reach them". Two sources implement it today, the hosted Cloud list and the paired kernels below. The gateway, the CLI and the agent guide only ever see the interface, so a future self-hosted registry or a kernel gossip mesh (Miguel's idea, a separate future area) can be added as a third source without changing the gateway or the CLI. No such source is built in v2.
- **Self-hosted.** The targets are the kernels this kernel paired with through terminal pairing links. A person runs `/kernel add <link>` (new, human-only) in a Chariox terminal on the local kernel; the kernel performs the terminal join (`JoinTerminalPairingLink` logic) with its gateway key and stores the machine in `gateway-kernels.json` (0600). No Cloud involved.
- **Agent-facing:** `chariox kernels`, `--kernel <name>` on CLI commands, `chariox guide`. Names are the user's local aliases (`/kernel rename`); ambiguity is an error that lists the candidates, never a guess. Only kernels the user's terminals could reach count; unapproved relay peers are not targets.

### 3.4 Approvals (decision 4)

- Routine approvals may be answered by the agent (unchanged, on any machine).
- Passkey approvals (grant, `/sudo`, critical) are never answered by the agent. A passkey field in a gateway request is refused locally and by the remote kernel (the existing `Refusal::HumanOnly`).
- The kernel raises the interaction; the agent receives a **pointer without secrets**; the user answers in an already-paired Chariox client (D1 popup). Details and extension scope are in section 8.

### 3.5 Dropping ssh (decision 5)

Section 9 lists what the coordinator needs and which area provides each piece.

### 3.6 Several kernels on one machine

A machine can run several kernels: a user-domain kernel and a system service, development kernels with their own `CHARIOX_HOME`, kernels of different OS users. Each has its own kernel id, state, passkey, sessions and agents. So the unit the gateway addresses is the **kernel**; the machine is an attribute for display and grouping. Where Miguel's decisions above say "machines", read "the user's kernels".

- `chariox kernels` lists the user's kernels grouped by machine: `{name, kernel_id, machine, label, os_user, status, last_seen, protocol, via}`.
- A kernel's name is its machine's name when it is the user's only kernel there, otherwise `<machine>/<label>` (label = the kernel's display name; `/kernel rename` changes the alias). `--kernel b3` while b3 runs two of the user's kernels is `kernel_ambiguous` with both candidates, never a guess.
- The agent talks to exactly one kernel: the one it holds its grant on, found as today (`CHARIOX_HOME` / default socket). Every other kernel, on the same machine or another, is a target. A target on the same machine is reached the way a Chariox terminal on that machine reaches it (local direct connection, the relay otherwise); the gateway never reads another kernel's state.
- Sessions, agents, terminals, files and events are always addressed through one kernel; files are read and written as that kernel's OS user.
- As built in r8: the code says `--kernel`, `chariox kernels`, `kernel_*` codes, frame field `kernel`, capability `kernel_gateway_v1`, `/kernel add|linked|unlink` and `gateway-kernels.json`. A name that fits two kernels is `kernel_ambiguous` and lists both as `<machine>/<label>` with their kernel ids; the kernel id and the aliases still work when they fit exactly one kernel. A self-hosted pairing takes the kernel's and the machine's alias from the kernel's own status answer (the link carries ids only). The hosted gateway row in the Cloud clients list is `Agent gateway of <machine>/<kernel alias>` when the kernel has an alias.
- As built in r9 (hardening after the r8 drills and the reviewer's P1s): a duplicate session alias answers `session_alias_conflict` naming the alias and the session that holds it (locally and through the gateway; `invalid_session_alias` likewise); `chariox kernels` renews the relay list when it is older than 1 s (the routing path still answers from a list up to 5 minutes old); a request whose grant ended while the link was being set up is not sent (`kernel_access_ended`, checked before resolving and again after the link opens); an open watch of a gateway the owner revoked ends within one 4 s probe with `kernel_unpaired`, a new stream from it is refused the same way, and a link that is cut because of a revoke says `kernel_unpaired` instead of a "retry" that could only fail; state-changing requests go only to targets that advertise `kernel_gateway_v1` (a legacy target is read-only for the gateway, 5.3); files uploaded to a kernel are written private (the unfinished upload is 0600, a new file stays 0600, a replaced file keeps its own permissions) and a download is private while it arrives and never replaces a file that appeared meanwhile unless `--overwrite` was given; the TUI waiting room focuses its prompt on `/` so the first typed `/kernel add` is not lost; the web popup of the next access request opens when the one that was open was answered on another client. Debug builds only: `CHARIOX_TEST_CRASH_BEFORE_RECEIPT` aborts the target right after a forwarded state-changing request took effect and before its receipt is written (EA2-09 e).
- Not built in r8: reaching a target on the same machine by the direct loopback lease a Chariox terminal uses (the lease is itself granted over the relay and needs the paired Cloud origin, so it only saves latency; the relay path serves same-machine targets today and never reads another kernel's state), and a `/kernel rename` command (the label is the kernel's alias set at install or with `CHARIOX_DAEMON_ALIAS`).

## 5. Gateway design

### 5.1 Parts (all in the local kernel, new module `runtime/kernel_gateway/`)

- **Directory.** Resolves a kernel name to `{kernel_id, machine_id, relay_url, target daemon id, protocol versions, freshness}` through the inventory-source interface (3.3): the hosted Cloud list or the paired kernels. Refreshed in the background (existing remote-inventory projection), never on the request path.
- **Gateway identity.** One key pair per local kernel, generated by the kernel on first use, stored privately in kernel state, never returned by any request. Hosted: it is registered as a terminal client named "Agent gateway of <machine>" so it appears in the paired-client list of every machine it reaches and can be revoked there. Self-hosted: it is the key the pairing link pinned.
- **Connections.** One connection per target kernel (relay, or the local direct connection when the target runs on the same machine, section 3.6), opened lazily on first use, shared by all grants, closed after 5 minutes idle and replaced after 4 minutes of age (hosted client tokens last 5 minutes). End-to-end encryption uses the same `relay_crypto` as a remote TUI; the relay sees ciphertext only. Hosted settings that break the rules fail loudly: a non-`wss://` non-loopback relay is refused with a clear message (AGENTS.md rule 6).
- **Forwarding.** The Unix socket handler (`unix_access.rs`) sees `kernel` on a frame, runs `authorize_external_request` locally, then hands the request to the gateway. Responses and subscription events come back on the same agent connection, tagged with the kernel. Subscriptions use the existing resumable event ids (they count on the target's stream, so a resume sends the last one seen with the machine); the gateway cancels the remote subscription when the grant ends or the agent unsubscribes, and renews the relay token in place so a subscription outlives the 5-minute token.
- **Attachments the gateway opened (decision of 10-20, built in r5).** An `AttachToSession` answered by a machine is kept alive by the origin kernel, not by the agent: while the grant is live and the machine answers, the origin sends `HeartbeatAttachments` for all such attachments every 10 s (one batched request, answered with the ids that no longer exist). They end when the grant ends, three beats are missed, or the agent sends `DetachFromSession`; the target sweeps a silent attachment after 30 s as always. The agent never re-attaches as a chore.
- **Recheck.** Every delivery rechecks that the grant is live (existing `delivery_live`), so revoke/expiry/holder exit stops forwarding at once.

### 5.2 Credentials the local kernel uses

| Mode | For the relay | For the remote kernel |
|---|---|---|
| Hosted | A 5-minute, key-bound relay client token minted from the kernel's durable Cloud credential through the existing terminal pivot path (`issue_cloud_terminal_client_token` with a kernel credential: `allow_unpaired_client_subject`, exact target, key thumbprint). Stays in kernel memory. The link is replaced before expiry instead of renewed. | The remote admits the gateway key as an owner terminal (relay `user_id` pin, as for any owner terminal). |
| Self-hosted | Operator transport token (shared or scoped CLIENT token) given by a human at `/kernel add`, stored 0600 in `gateway-kernels.json`, never printed, never returned by a request. | The terminal grant the pairing link created (`terminal-grants.json`); revocable on the remote. |

The agent holds nothing, so there is nothing to copy (D9 intact).

### 5.3 Permission handling on the remote kernel

The remote sees an owner terminal and handles requests exactly as for a remote TUI (ownership checks, session membership, D1 popups). Two additions:

- The forwarded request carries `on_behalf_of: { origin_kernel, grant_id, harness }` inside the encrypted request context. The remote kernel makes its own decision from it; no Cloud and no link are involved. The link between the machines is only used afterwards, when the user wants the action done and answers in a client.
- **Three checks, not one.** Today `authorize_external_request` does all of this in one call against the local grant map and the local `pending_interactions`. That cannot run on both ends: B has no record of A's grant, and A does not own B's interactions (for an interaction id A does not know, `external_interaction_requires_terminal` returns "not forbidden", so A cannot be the one to classify a remote answer). It is split into three functions:
  1. `grant_live(grant_id)`: **origin only.** A checks its own grant (live, holder covers the peer). B never sees or looks up a grant id; `on_behalf_of.grant_id` is audit text on B.
  2. `restricted_request(request)`: **shape only, shared.** The credential/pairing/relay/Cloud-identity/peer set, protected config paths, and any `RespondToInteraction` that carries a `passkey`. It reads no state, so both ends call the same function. A runs it before forwarding; B runs it again for every request that carries `on_behalf_of`.
  3. `interaction_requires_terminal(answer)`: **state, target only.** Whoever owns the interaction classifies it from its own `pending_interactions` (passkey prompt, terminal credential, critical level, choice requiring a passkey). For a request with `kernel`, A skips this step and B performs it with `on_behalf_of` present; routine approvals are admitted, anything else is refused with `kernel_access_human_only`. For a local request nothing changes.
- **Compatibility (built in step 2, 2026-10-20).** A target kernel advertises `kernel_gateway_v1` (in `RelayStatus.capabilities` and in relay presence) when it enforces `on_behalf_of`. The relay client envelope parser of an older kernel has `deny_unknown_fields`, so it *rejects* a request that carries `on_behalf_of` rather than ignoring it. The gateway therefore sends `on_behalf_of` only to targets that advertise the capability. To an older target it sends the plain envelope only for requests that may simply run again (reads, the attachment heartbeat, a file chunk that names its offset: `ledger::is_repeatable`); every state-changing request, `RespondToInteraction` included, is refused by A with `kernel_incompatible` ("update the Chariox kernel there"), because an older target keeps no durable receipt and a same-command-ID retry after its crash could run the request twice. (Built in r9; before, only `RespondToInteraction` was refused.) The planned "a newer target refuses a gateway caller that omits `on_behalf_of`" defence is **not built**: the hosted client subject is a hash, so the target cannot tell a gateway from another terminal of the same owner; a compromised gateway is a compromised kernel anyway.
- A popup for something that needs the **remote** kernel's passkey appears on the remote's connected clients (D1, per-kernel passkey). The agent gets the pointer (section 8) naming the kernel.

### 5.4 Failure and offline behaviour (definitive outcomes)

Each failure is a typed error with a code, one plain sentence and the next step. Codes (new, same style as `Refusal`):

| Code | When | Next step in the message |
|---|---|---|
| `kernel_unknown` / `kernel_ambiguous` | Name matches none / several | Run `chariox kernels`. |
| `kernel_offline` | No fresh heartbeat (hosted) or relay shows it gone | Start the kernel there; ssh is break-glass. |
| `kernel_unreachable` | Relay or connect timeout (10 s) | Retry; check the relay. |
| `kernel_unpaired` | Self-hosted: not paired, or pairing revoked there | Re-pair with a new link. |
| `kernel_incompatible` | Remote protocol below the minimum for this request | Update that kernel; names the minimum. |
| `kernel_request_timeout` | No answer within the request deadline (default 30 s, per request override) | For state-changing requests: retry once with the same `--command-id` (below). |
| `kernel_outcome_unknown` | Retry found a reservation without a receipt (target crashed mid-request) | Check the state before asking again; the request is not re-run. |
| `kernel_not_available` | The frame came from something that is not a grant holder | Use the local kernel's own connection. |
| `kernel_connection_lost` | Connection dropped with a request in flight, or a subscription's events stopped (the message names the last event id) | Same retry rule for requests; for a subscription, subscribe again with `resume_from_event_id`. |

- **Retries: at most once, with an explicit "unknown".** The existing `CommandResultCache` is not an exactly-once ledger: ordinary reservations live in memory only, results are written after completion, entries are bounded (512 entries, 24 h on disk), and several request kinds are excluded. After a crash on B between the side effect and the stored result, a retry with the same command id could run the mutation again. The plan therefore promises less and says so:
  - **Read-only requests** (list, stat, read, `read --since <cursor>`) are retried freely. **Chunk writes** (`WriteMachineFile` with offset and chunk sha256) are idempotent by construction: the same chunk at the same offset yields the same bytes.
  - **State-changing requests** go through a durable gateway ledger on the target, built on the at-most-once receipt path that app control already uses (`CommandResultCache::new_at_most_once`, `complete_at_most_once`): the reservation `(gateway caller, command_id, request fingerprint)` is appended and synced **before** the request is dispatched, and the final receipt after it. Receipts are kept 15 minutes (a retry comes within a minute) and up to 4096 fit; a full ledger refuses new mutations with a typed error instead of dropping entries, and an evicted command id stays fenced for good, so a late replay is refused, never run twice. (r8: the first build kept receipts 24 h with room for 512, and ~510 forwarded terminal inputs locked an agent out of every state-changing request on that kernel for a day.)
  - Outcomes of a retry with the same `command_id`: receipt present → the original result; reservation present but no receipt (B crashed or restarted mid-request) → `kernel_outcome_unknown`: "the request may or may not have run; check the state (for example `sessions list`) before asking again". The request is **never re-executed** from an interrupted reservation. A different fingerprint under the same id is a conflict error. Read-only is decided by one rule (a request variant that starts with List, Get, Search or Stat); every other request is on the ledger, so there is no "not retryable" kind. A request without a `command_id` is refused with `command_id_required` (the CLI always sends one).
  - The agent guide says: on `kernel_request_timeout` or `kernel_connection_lost`, retry once with the same `--command-id`; on `kernel_outcome_unknown`, look at the state first.
- **Never a hidden fallback.** A failed named kernel never routes to local or to another kernel.
- Revoking the grant stops new requests and subscriptions at once. Work already started on the remote (a running terminal command, a started agent turn) continues, as it does for a local grant; it is stopped with an explicit request.
- Local kernel down: no access at all (ssh is break-glass, recorded as a product issue).

### 5.5 Audit

Local: `kernel_access.forward` per request (request kind, target kernel id, outcome, latency; no payload), sampled like `kernel_access.denied` when looping. Remote: its ordinary command audit, with the gateway caller and `on_behalf_of`. No passkey or credential value in either.

## 6. Protocol changes

Per AGENTS.md: version bump, snapshot and hash tests, a focused drill. Numbers are allocated by the coordinator.

**Local protocol `NEXT` (core).**
- Access term: `RequestKernelAccessRequest.term` and `KernelAccessGrant.term` replace `lifetime_minutes`; `expires_at_ms` is optional.
- Unix-socket frames: `kernel` (optional) on request and subscribe frames; `kernel` echoed on `Response` frames (built, so a client can tell a forwarded answer from a local one); event frames carry it when they come from a forwarded subscription (built in r5; one subscription per connection); `HeartbeatAttachments` / `AttachmentsHeartbeated` keep gateway attachments alive; new error codes of 5.4 in `KernelTransportError`.
- Self-hosted kernel list: `JoinKernelLink { link, relay_token? }` (human-only), `ForgetGatewayKernel`, and `ListGatewayKernels`. Hosted needs no new request if step 1 confirms existing listing.
- Kernel view for agents: extend `RemoteMachinesListed` rows with `kernel_id`, `machine`, `label`, `status`, `last_seen`, `kernel_protocol_version`, `via` (hosted/self-hosted) if they are not already there.
- Relay client request context: `on_behalf_of` (5.3).
- Files (section 9): `ReadMachineFile`, `WriteMachineFile`, `StatMachineFile` with offset, length, sha256, mode.
- Client minimums: raised only for clients that show the grant list (term) and the popup choices; the web and TUI popups need the three-choice answer.

**Relay peer protocol.** Verified in step 1: the relay client envelope (`KernelIncomingFrame::Request { request_id, command_id, causation_id, correlation_id, request }`, `transport/kernel_protocol.rs`) is not peer-versioned and has no `deny_unknown_fields`: a kernel that predates a new optional field (`kernel`, `on_behalf_of`) ignores it silently, which is why 5.3 defines the compatibility rule on the origin side. The *relay peer* protocol versions kernel-to-kernel `RelayPeer` messages, which the gateway never sends. It is still bumped together with the local protocol in this repo, because the peer union embeds local response shapes (the term change touches `KernelAccessGrant`, which appears in `KernelSudoTurn.requester`); the relay binary itself does not change.

**Local protocol, events extension (section 14).** `SubscribeEvents { targets }`, `UnsubscribeEvents { targets | all }`, `GetEventSubscription`, `ListEvents { since, limit }`, `WaitEvents { since, timeout_ms, limit }`, `AckEvents { cursor }`, the `EventsListed` response `{ events, next_cursor, oldest_cursor, timed_out }`, the record of 14.5 (types `agent`, `interaction`, `terminal`, `session`; control records `gap`, `subscription_ended`), the `cursor_expired` code, and the `Outside` recipient kind in the agent-model ledger. External access path only, never in the session-agent or `/sudo` vocabulary. Allocated at the integration that ships it; it can share a number with `NEXT` or `NEXT+1`.

**Local protocol `NEXT+1` (approvals extension).** `ApprovalPending` frame to the waiting agent connection, `ListPendingApprovals` (read-only for agents), pointer record `{approval_id, kind, kernel, one_line, link?, expires_at}`; Cloud API `POST /v1/approval-pointers` (chariox-cloud).

Drills for these shapes: section 12 (EA2-01..EA2-34). Snapshot and hash tests next to `protocol_shapes/kernel_access.rs`.

## 7. CLI surface

All commands print one JSON document on stdout, errors as JSON on stderr (`{"error":{"code","message","kernel"}}`). Exit codes: 0 ok, 2 usage, 3 refused (human-only, not covered, ended), 4 kernel unavailable, 5 timeout/outcome unknown, 6 approval pending, 7 cursor expired (resync, section 14). Final numbers fixed at implementation.

```
chariox guide                                  # short agent guide (below)
chariox access request [--until-exit | --minutes N] [--no-wait]
chariox access status | list | revoke <id|--all>
chariox kernels                               # name, status, last_seen, kernel protocol, via
chariox request [--kernel M] [--command-id ID] < request.json   # one LocalDaemonRequest
chariox sessions|agent|terminal|files ... [--kernel M]          # thin verbs (below)
chariox sudo request --agent A --prompt P [--kernel M]
chariox approvals list | wait <id> [--timeout S]                 # extension
chariox events subscribe|unsubscribe|subscription|list|wait|watch|ack ...   # extension, section 14
```

- `chariox request` is the single generic door: any `LocalDaemonRequest` the grant allows, locally or on `--kernel`. It is the same shape as the sudo MCP `chariox_kernel_request`, so there is one request vocabulary.
- Thin verbs only where the raw request is awkward for an agent: `terminal open|send|read|wait|close`, `files get|put|stat`, `agent spawn|prompt|steer|read`, `sessions list|create`. Each is a one-screen mapping onto a request; none adds behaviour. `--kernel` is accepted by every verb and by the existing non-TUI commands that talk to a kernel (`context`, `app`). `chariox logs` reads local files today; remote logs are read with `terminal`/`files get` in the core.
- No "current kernel" state: every call names its kernel, or means the local one.
- `chariox guide` is static text compiled from the same command table the parser uses, so a test fails if the guide mentions a command or flag that does not exist. It tells the agent: request access once, list kernels, always pass `--kernel`, which things are human-only, and **what to do with an approval pointer: show it to the user verbatim and wait**.
- The default holder for `access request` stays the nearest provider harness. `--no-wait` exists because harness tool calls time out (minutes): it prints the pointer and exits 6, then `access status` polls.

Nothing is written into `~/.claude`, `~/.codex`, MCP config or hooks (checked by EA2-19).

## 8. Approvals extension

The core already has: popups on the kernel that owns the passkey (D1), `RequestKernelAccess`/`RequestKernelSudo` blocking with a one-line note on stderr ("Waiting for you to approve in your Chariox terminal on <kernel>").

The extension adds, when the user is not looking at a terminal of that kernel:

1. **Pointer.** When an external request raises a passkey interaction (local or remote), the kernel sends the waiting connection `ApprovalPending { approval_id, kind, kernel, one_line, link?, expires_at }`. The CLI prints it as the first line of output so the agent shows it in its chat. It contains no secret and no prompt body.
2. **Hosted answer.** If the kernel is Cloud-enrolled, it asks Cloud (kernel credential) for a one-time deep link: 128-bit code, single use, 10 minutes, bound to `(owner account, kernel id, interaction id)`. Cloud stores only that mapping and the kind label. Opening it serves the Chariox web app's approval view and authenticates the account as today. The web client then connects to the kernel through the relay (end-to-end encrypted) and shows the same popup the D1 popup shows; the passkey goes browser → relay → kernel. Cloud serves the page; the relay never serves pages or sees the passkey. A second open, a wrong account, an expired or answered link all show a plain "already answered / expired" page.
3. **Self-hosted answer.** No page. The pointer says which kernel to open; the user answers in a remote TUI paired to it (works from a phone SSH app). The native mobile client takes this role when it exists.
4. **Phishing note.** The agent prints the pointer, so a hostile agent could print a lookalike link. The real popup is also already shown on every connected client, and the page shows details from the kernel, not from the link. The guide tells agents to quote the pointer verbatim; the user is told in the pointer text to prefer opening Chariox itself if the domain is not the one they use.

The extension can ship after the core; the core's popups cover the Mac TUI, and `--no-wait` covers harness timeouts. Remote passkey prompts (a remote `/sudo` request, a remote critical approval) work in the core when someone has a client connected to that remote kernel; the extension makes them reachable from a phone.

### 9.1 Machine file requests: why and how

**Why.** The coordinator's day on b3 moves files in both directions: git bundles from b3 to the Mac so the Mac can publish them (b3 has no GitHub credentials by design), lane results and `LANE_STATUS.md`, evidence (screenshots, recordings, logs), and briefs or prompts going the other way. Pushing these through a terminal as base64 is slow, breaks on large files, cannot resume, and fills the agent's context with bytes. A terminal is also the wrong tool: it is a live shell, not a transfer.

**How.**
- They are ordinary kernel API requests (`ReadMachineFile`, `WriteMachineFile`, `StatMachineFile`), not terminal traffic. The gateway routes them to the target kernel like any other request with `kernel`; the target kernel does the file work and answers.
- Chunked: each request moves one bounded chunk (offset, length) of at most 256 KiB, so it fits the relay's 768 KiB request bound after base64 (found in the r5 drill: 1 MiB chunks were refused). A large file is a sequence of chunks.
- Resumable: `Stat` returns size and sha256 of what is already there; the client continues at the offset after an interruption (drill EA2-07 interrupts at 40 %).
- Verified: the final sha256 is compared by the receiving kernel; a mismatch is a typed error and the partial file is never presented as complete.
- Capped: 2 GiB per file; a larger file is refused with a typed error naming the cap.
- Authority: the user's, no wider. Files are read and written as the target kernel's OS user; a terminal of that kernel can already read and write any file that user can; the requests add convenience, not power. The bytes never reach the model unless the agent chooses to read them, and everything stays inside the relay's end-to-end encryption.
- CLI: `chariox files get|put|stat --kernel <name>`, JSON result with size, sha256 and elapsed time.

Every break-glass ssh during the dogfooding day (EA2-16) is logged as a product issue with the missing capability.

### 9.2 Terminal verbs on top of #1054 (built in r6, provisional protocol 569 with the Room terminal service)

Terminals are Room-scoped, owner-sent and survive client disconnects (term/r1, protocol 562 / peer 170). The verbs are one-screen mappings onto the single request `RoomTerminal { session_id, acting_agent?, operation }`; the gateway forwards it like any request with `--kernel`. The agent calls exactly these (no `acting_agent`, so the actor is the user and the gateway, an owner terminal on the target, may type):

| Verb | Request (`operation`) | Notes |
|---|---|---|
| `sessions create --kernel b --name ops --folder /root/work` | `CreateSession` (existing) | The ops Room per machine; its id is the `--session` of every terminal verb. |
| `terminal open --kernel b --session S [--cols 120 --rows 30] [--title T] [-- ARGV...]` | `open { cols, rows, title?, command? }` | `command` is an argv (no shell); without it the user's login shell. Answers the terminal summary (id, `host_agent`). |
| `terminal list --kernel b --session S` | `list` | Room-wide: this kernel's terminals plus workers'. |
| `terminal send --kernel b --session S --terminal T "make test\n"` | `snapshot`, then `input { data_base64 }` | `input` is written as one unit. The CLI first takes the terminal's current `output offset` from a `snapshot` and prints it as `after_offset` so the following `read`/`wait` sees only the new output. Whether `input` itself returns the offset is checked on the #1054 base; if it does, the `snapshot` goes away. As built (r8): `--wait-ms N` sends the `input` and a `read_output` long poll together and prints the output in the same call; with `--since OFFSET` (the `next_offset` of the last read) there is no `snapshot` either, so the whole echo is one round trip (about RTT + 20 ms; send then read was 2-3 round trips). |
| `terminal read --since OFFSET [--wait-ms N]` | `read_output { after_offset, wait_ms }` | `gap: true` means resync: the CLI then runs `snapshot` and says so. This long poll replaces a subscription for terminals. |
| `terminal wait --for finished\|output_contains=TEXT\|waiting_for_input --timeout S` | `wait` | One request waits at most 240 s; the CLI loops for longer waits and prints the exit code when the shell reports one. |
| `terminal close` | `close` | Ends the shell's whole session (background jobs too). |

- **As built (r6).** `terminal open|list|send|read|wait|close` in `apps/cli/src/terminal-verbs.ts`, JSON on stdout, `--kernel` optional (without it the local kernel answers). Differences from the table: `send` appends Enter (a carriage return; `--no-enter` types the text as it is), reads one `snapshot` first and prints its `output_offset` as `after_offset` (the `input` answer carries no offset); `read` prints the output as plain text (colour, title and cursor escapes removed) with `next_offset` and `gap`; `wait --timeout S` (default 60) asks in pieces of at most 240 s, each continuing from the offset the last piece saw, and a timeout is an answer (`fired: null` with the screen), not an error. The origin's wait for the machine's answer is the usual 30 s plus the request's own wait (`deadline_for` in `machine_gateway/ledger.rs`).
- **At-most-once (built).** The target's ledger treated a request as repeatable by the name of its variant (`List`, `Get`, `Search`, `Stat`, `Heartbeat`). `RoomTerminal` is classified by `operation`: `list`, `snapshot`, `read_output`, `wait` repeat; `open`, `input`, `resize`, `close` are state-changing and use the ledger, so a retried `input` never types twice.
- **Detached jobs.** The job belongs to the kernel-owned terminal, not to the agent or its grant: killing the agent ends the grant, not the job. A new grant (the same `--kernel`, the same `--session`) reads it with `read --since`. A terminal is not an attachment, so the gateway's attachment heartbeat is not involved.
- **No new fence.** Anything typed or read is the agent's own action on a machine the user connected to it; the response redaction applies as to every reply.

### 9.3 Remote `/sudo` (design only; EA2-11)

A sudo window is a *kernel-side* decision on the machine that owns the agent and the work, so the remote case is not a new kind of sudo; it is the same request arriving through the gateway.

- **Whose interaction:** the target's (B). `RequestKernelSudo { agent_id, prompt }` is forwarded with `--kernel b`; B raises its ordinary sudo popup (kind `sudo`, kernel-authored `SudoRequestPresentation` naming the requester as "<harness> via <origin kernel>") to its own connected host terminals, with B's passkey. The origin kernel only validates its grant and the request shape (it already refuses a sudo window itself as a gateway holder: "a sudo window does not reach other machines" stays).
- **Where the passkey is answered:** in any client already connected to B (TUI, web through the relay, a remote TUI over ssh). It never touches A, the gateway link, the agent or the model: `RespondToInteraction` with a passkey is human-only on both ends, and B classifies the interaction itself.
- **What B changes:** (1) the dispatch check "only a grant holder over ws+unix can request sudo" also admits a request that carries a valid `on_behalf_of` (authorized with `authorize_on_behalf_of_request`, not a local grant lookup); (2) the turn it starts is bound to B's named agent, provider run and prompt exactly as a local one (see Binding below), with `(origin_kernel, grant_id)` kept only as the audit attribution and as the pending request's liveness; (3) the presentation names the origin.
- **Binding stays B's.** The sudo window is bound exactly as `RequestKernelSudo { agent_id, prompt }` binds it today (`docs/KERNEL_SUDO.md`, protocol 484): to the named agent on B, its exact provider run and prompt (`sudo_for_auth_token`, `sudo_live`), with the window B's user chooses in B's popup (1, 2, 4 or 8 hours; 1 hour default) and B's monotonic deadline (`open_window_at`; `sudo_end_reason` expires a started window that lacks one). `on_behalf_of` does not become the execution identity: the external requester's calls are not the ones that run elevated, the named B agent's own tool calls are. The origin/grant attribution only (a) authorizes the request to be raised on B, (b) names the requester in B's popup, (c) is the pending request's liveness.
- **Ending:** exactly B's local rules. The window covers the authorized work: with Room agent tools the prompt's durable task, across waits and kernel-correlated continuations; without them the first turn. It ends at B's deadline, at the end of the work, on `/sudo` revoke or kernel restart, and a started window without its deadline counts as expired. As for a local external requester ("the window ends when the requester's grant ends"), the end of the origin grant ends the remote window too: the gateway tells B, and B ends it through the same path as a local grant end. A request still pending when the origin grant ends is cancelled on B. Nothing in the gateway adds a deadline or a turn limit of its own.
- **Agent-side result:** the forwarded request answers like a local one (pending, then approved or refused/expired); the agent is told "approve on <machine>" and nothing else. The deep-link pointer remains the approvals extension.
- **As built (r11, no protocol shape change; provisional 569/177).**
  - *Target (B).* A forwarded `RequestKernelSudo` that names its origin (`on_behalf_of`) is raised by `request_remote_kernel_sudo`: the requester is a synthetic grant `<origin kernel>:<origin grant id>` (owner = B's owner, no OS process), registered in B's `remote_requesters` for as long as the origin has not said its grant ended. `requester_grant_live` accepts it, so B's own sweep ends a pending request or a running window exactly as it does for a local grant. A request that does not name its origin keeps the old refusal ("only a grant holder over ws+unix").
  - *Popup.* The same sudo popup on B ("<Codex|Claude Code|OpenCode> via <origin name>", task, 1/2/4/8 h choice, B's passkey). The binding to B's named agent, provider run and prompt, the deadline and the task retention are unchanged B code.
  - *Origin (A).* The forward waits for the popup answer (`deadline_for`: 30 s + 10 min, the target's default access-answer wait), races the owner revoking the gateway like any long wait, and starts a per-(target, grant) watcher. When the origin grant ends (revoke, expiry, holder exit; polled every 500 ms) the watcher sends `RevokeKernelAccessGrant { grant_id: <that grant> }` with `on_behalf_of`; B reads a forwarded revoke of the grant id it names as "this origin's grant ended" (idempotent, no ledger), removes the requester and sweeps. Four attempts, 3 s apart; if B cannot be reached the window ends at its own deadline.
  - *Agent side.* `chariox request --kernel B --timeout 660 --command-id ID` with `{"RequestKernelSudo":{"agent_id":"AGENT_ID","prompt":"TASK"}}` (an example in `chariox guide`); the answer is `KernelSudoRequested` once B's user approved and the turn started, or a definitive refusal/expiry. The agent is told nothing else.
  - *Requester line.* The origin sends `on_behalf_of.harness` as the provider harness it recognised (`claude`, `codex`, `opencode`), else the executable file name; the file name alone (`2.1.296`, `node`) left B's popup at "An external agent". Both the launcher and the bare TypeScript CLI select the nearest installed provider harness in the caller’s OS ancestry, walking past intervening shells (r13). The kernel verifies PID, executable path, start identity and ancestry again before granting access.
  - *Long wait.* The forward renews the relay token on the open link when it starts and every 3.5 minutes (EA2-48): a person may take up to the target's 10-minute popup wait.
  - *Lease (r12; added shapes `RenewKernelSudoRequester {}` / `KernelSudoRequesterRenewed { renewed }`, still provisional 569/177).* B enforces the origin grant's liveness itself instead of waiting for a report. The synthetic requester carries a 45 s lease; the origin renews it every 10 s while its grant lives (silently, with `on_behalf_of`, no `command_id`), and every renewal restarts the 45 s. B checks the lease wherever it checks a local grant: `requester_grant_live` at approval, at dispatch of the elevated turn and in the sweep that ends a started window. An origin that is killed or restarted (a restart ends all grants), a partition, or a revoke while B is unreachable all end up the same way: the renewals stop and the pending popup (and a running window) ends on B within 45 s plus one sweep, with no report needed; a lapsed lease is never revived by a later renewal. The explicit report (four attempts, 3 s apart) stays as the fast path for the usual 1-4 s end. The origin stops renewing when B twice answers that it no longer knows the requester. Loss-of-contact bound: 45 s.
  - *What a revoke does to a running command (measured, r12 L5).* The window ends within about a second, as locally; a shell command already running is not interrupted, finishes normally and its result reaches the agent, and the next elevated call prompts again. This is B's local window contract, unchanged.
  - *Measured bound (r12 L1/L2).* With the origin kernel killed, a pending popup or a running window ends on B 36.6-45.3 s later (45 s lease, renewal phase, up to 1.4 s sweep); a base build without the lease keeps it until its own deadline. A revoke while B is merely unreachable is usually delivered when B returns (the relay buffers the end report), so only an origin that is gone needs the lease.

## 13. Risks and residual notes

- **The gateway on the target (r6).** The target records each gateway that sends a request carrying `on_behalf_of`, keyed by the relay's authenticated client key (`gateway-origins.json`, 0600), and lists it beside its paired clients as `Agent gateway of <origin kernel>` (client id `agent-gateway:<thumbprint>`). Revoking that id (`RevokePairedClient`) refuses the key at once, with or without `on_behalf_of` (`kernel_unpaired` at the origin). Self-hosted: a second pairing link for the same gateway key replaces the earlier grant (one grant per key; the replaced link cannot bring it back). **Hosted gateway in the Cloud clients list (built in r7).** The first time a hosted kernel opens a gateway link, it registers the gateway with `POST /kernels/gateway-client` (kernel credential in the body, as `/kernels/unlink`): Cloud adds one account client named `Agent gateway of <machine>` whose client id is the exact relay subject the gateway tokens carry (`kernel-client:<sha256(kernel id)>:<sha256("agent-gateway")>`), bound to the gateway key. It shows in the web clients list (`Signed-in terminals`) and revokes there with the ordinary client revoke: Cloud retires the gateway's live tokens and adds the subject to the relay denylist, so the link to every machine drops; token issue for a revoked row answers `identity_revoked`, the next forwarded request answers `kernel_unpaired` ("the agent gateway was revoked in the Cloud clients list and the agent access grants ended") and the origin kernel ends all its agent access grants. Registering again brings it back; the kernel registers only on first use after start and after such a revoke, i.e. only under an access grant the user approved (grants die with the kernel and with the revoke), so a revoke cannot be undone by the agent. A kernel may register only a subject that carries its own kernel hash and its own enrolled key; a second account cannot take the id. Cloud reaches no kernel: the end of the grants is the origin kernel noticing its own refused token.
- **Measured in r7 (release build, 8 Mbit/s up, RTT 60.4-61.2 ms, KVM guest, host load 22-144: a loaded-host number; the quiet-host run is still to do).** EA2-07 works end to end (200 MB bundle killed at 40.1 %, resumed from 80,478,208, sha256 equal, `git fetch` on B, 50 MB `files get`). Throughput: put 3.3 Mbit/s, get 3.7-4.1, plain TCP on the same link 7.1-7.5; unshaped put 18.8 / get 23.1 (r6 debug build: 4.5). The wire carries 1.86 bytes per file byte: the chunk is base64 inside the JSON request and the encrypted payload is base64 again in the relay envelope, so an 8 Mbit/s link carries at most 4.3 Mbit/s of file and the run reaches 77 % (put) to 95 % (get) of that. Pipelining chunks would gain at most 25 % on put and the target accepts only strictly sequential offsets, so it is not built; the real lever is binary frames for file chunks (a relay peer-protocol change, not v2). Latency (diagnostics off): forwarded requests on one persistent connection P95 64.9 / 66.2 / 69.5 ms against the gate RTT + 60 (about 121): PASS; the CLI adds 0.2-0.4 s of bun start-up (P95 308-523 ms), which is not the kernel path; a terminal echo measured as `send` then `read` is two round trips (P50 144-162 ms against 121), so a single send-and-wait request would be needed to meet the literal gate. After a 12 s pause the slowest request took 73 ms (r6: 5850 ms).
- **Slice cell (r7, EA2-13).** A hosted local-Docker slice (peer 177, provider sandbox compatibility on) runs agents and Room terminals on A and, through `--kernel`, on B. The first run failed at the terminal: the home kernel looked the slice worker up with the account-wide metadata grant, which lists only Cloud-online targets, and a slice worker never reports presence to Cloud. Peer requests and peer-event lookups for a `slice:` target now use the exact-target slice discovery grant (as the agent binding does). An unreachable worker now answers the public `terminal_refused` with one sentence the agent can act on (the transport detail stays in the kernel log). `watch` shows `--kernel/--session/--attachment` as required in its usage (it follows another machine; a local session is read with `request`).
- **Revoke timing on PR stacks (r7).** After a real click on Revoke in the web clients list the row leaves the list within 0.4-0.9 s and the first call afterwards answers `kernel_unpaired`; the live link was cut 119-190 s after the click. The own relay of a PR stack runs without revocation sync (no `CHARIOX_RELAY_REVOCATION_URL`, no `revocation_sync_enabled` line), so there the link ends when the gateway replaces it (at most 4 minutes) and token issue is refused; a production relay syncs every 30 s. Re-run the click on a stack whose relay syncs revocations before quoting a number.
- **Open web seam (r7).** The access popup is mounted only on the waiting-room page: a request that arrives while the person is on the account settings page (reached by in-app navigation) shows no popup until the waiting room is loaded. Not fixed; the popup's "Waiting for the kernel…" text is shown from the click until it closes (1.5-4 s on a loaded host) at DPR1 and DPR2.
- **Machine list (r7).** `chariox kernels` after more than about 20 s idle refreshes inline (1.8-5.4 s) and a killed machine shows offline only about 5 s after the kill (Cloud presence freshness), while a forwarded request answers `kernel_offline` within 0.2-0.6 s. Not changed.
- **No request waits for the machine list (r6).** The directory used to refresh the Cloud machine list inline when it was more than one heartbeat old, so any forwarded request after a pause of about 10 s stalled for 1-6 s. It now answers from a list that is at most 5 minutes old and renews it behind the request; only an unknown or offline name, or no list at all, waits for a fresh one. Persistent-connection max latency after a 12 s pause went from 5850 ms to 43-201 ms.
- **Web (r6).** An access request opens its popup by itself on the web (once per request; closing leaves the footer notice) and Settings > Security shows the live grants of the selected kernel with Revoke / Revoke all (`ListKernelAccessGrants` / `RevokeKernelAccessGrant`).

- **Blast radius.** One local passkey reaches all the user's kernels. This follows decision 2; the popup says so, the list shows it, the remote paired-client list shows the gateway, and revoke is immediate. Narrowing per kernel is not in v2.
- **Kernel restart ends grants.** By design (memory only). For the coordinator this means re-granting after a Mac kernel restart.
- **Remote passkeys are per kernel.** Remote prompts need the user at some client of that kernel; the extension makes that practical.
- **Dependency:** #1054 for terminals; a Cloud change only if step 1 finds that a kernel credential cannot read the owner's kernel list (3.3).
- **UX-first rule applied:** no new guard on what the agent reads or types; the only fences are the existing human-only set and the existing credential-literal response redaction.
- **Events extension.** Each kernel with a target keeps a durable part with a bounded inbox; a dropped range is always a `gap` record and an old cursor a definitive `cursor_expired`. The subscription itself has no expiry of its own: it ends only with its grant or when the agent cancels it.

## 14. Events for external agents (extension, discussed with Miguel 2026-10-21)

### 14.1 Why

An external agent needs to know when something it started has moved: an agent finished its turn, is waiting, is blocked on the user, is done; an approval is pending; a terminal job exited. Today the coordinator learns this by polling lane folders, PR reviews and the area check over ssh (`watch.sh`). The agent-model event core (OSS #1057, `docs/AGENT_WAKES.md`) produces exactly these changes, but only for agents inside a session. This extension gives them to recipients outside sessions, so an external agent can be woken, wait or poll through the `chariox` CLI, with nothing installed in its harness.

### 14.2 Session confinement (rule)

- A session is the confinement boundary for the agents in it. A session agent sees and is woken by changes of its own session only. The `chariox.events.*` tools stay session-scoped and unchanged.
- Observing several sessions belongs only to **outside principals**: an external agent through its grant (now) and the Chariox assistants (later, the in-product equivalent of an external agent, see the `chariox-assistants` area). Neither is a session member.
- The event subscription requests of this section are **not exposed** to Chariox session agents at all: they are absent from kernel MCP tool discovery, from `chariox.events.*`, and from the `/sudo` request vocabulary. There is nothing for a session agent to call, so there is nothing to refuse. They exist only on the external access path (the grant holder's Unix socket and the gateway) and, later, for assistants inside the kernel.
- Communication between session agents across sessions is a separate future mechanism. Nothing here provides it.

### 14.3 Terms

- **Kernel**: the target (section 3.6). A machine may run several.
- **Session** (a Room in the code): holds several agents, terminals and interactions.
- **Agent**: one provider thread in a session (`agent_id`). A coordinator lane is an agent.
- An agent has two states the kernel already keeps: its run state (`AgentState`: `idle`, `working`, `error`; a turn end is `working` → `idle`) and, with the event core, the state of its current task (`ExecutionState`: `working`, `waiting`, `blocked`, `done`, `cancelled`, with a reason).

### 14.4 What exists and what is missing

**Exists.**
- `Subscribe { session_id, attachment_id, subscription_scope, resume_from_event_id }` with two scopes: `Session` (the full live stream of one session, every agent, token by token) and `WaitingRoomInventory` (the kernel-wide session list the waiting room shows, a snapshot projection, not a resumable stream).
- The kernel event log keeps one stream per session with monotonic event ids, bounded retention and a `replay_gap` answer when a resume cursor is too old (`runtime/event_log.rs`, `runtime_transport/subscriptions.rs`).
- The event core ledger: tasks, obligations, registrations, wakes, inbox and receipts; delivery is a provider turn or a steer. Every recipient is an agent in a session.

**Missing for an outside recipient.**
1. **Choosing what to follow.** A live subscription is a whole session's full stream over one held connection. There is no way to follow one agent, or a few agents and sessions on several kernels, and receive only their state changes.
2. **Waiting from short command calls.** A CLI agent's tool calls are short; it needs a durable inbox and a wait.
3. **Being the recipient.** The ledger's recipients are session agents only, and the kernel cannot start a turn in a process it did not launch, so delivery to an external agent is pulled.

### 14.5 Design

**Authority versus interest.** A grant may see every session of the user on every kernel (section 3.2): that is what the agent is *allowed* to see. What actually flows is what it *asked for*: its **event subscription**. Nothing outside the subscription leaves the kernel that produces it.

**One subscription per grant.** It is a list of targets; each target is one of:
- `{ kernel, session }`: every agent of that session, including agents added later;
- `{ kernel, session, agent }`: that one agent (thread) only.

Sessions and agents the external agent creates through its grant are added to its subscription automatically (`--no-subscribe` opts out), so "follow what I started" needs no extra step.

**Four event types, one per thing that changes.** Only state changes travel, never token streams, prompt or output bodies:

| Type | About | Values |
|---|---|---|
| `agent` | one agent | new run state (`idle`, `working`, `error`) and, with the event core, task state (`working`, `waiting`, `blocked`, `done`, `cancelled`) with its reason |
| `interaction` | an approval or question raised by an agent | `pending` or `resolved`; a passkey approval only as the section 8 pointer |
| `terminal` | a Room terminal job in the session | `exited` with exit code |
| `session` | the session itself | `agent_added`, `agent_removed`, `ended` |

There is no kind filter: the target already says what the agent cares about, and a target produces a handful of changes per turn. Two control records complete the inbox: `gap` (see Bounded inbox below) and `subscription_ended` (with its reason, always the last record).

A record is `{ cursor, kernel, machine, session_id, agent_id?, type, value, summary, at_ms, refs: { task_id?, run_id?, interaction_id?, terminal_id? } }`. `summary` is one line (the task reason, the interaction title, the exit code). The agent reads details with the existing requests (session read, terminal read, task list).

**Where it lives (agent-model side).** The ledger gains a recipient kind next to `SessionAgent { session_id, agent_id }`: `Outside { subscription_id }`, whose delivery is **pull** and whose receipt is the ack. Each kernel that has a target holds one **part** of the subscription: an `Outside` registration with that kernel's targets and its own durable inbox, written by the producers the kernel already has (agent state, the event core's task updates, interactions, Room terminals, session changes). The agent's own kernel holds the subscription, owns the parts on other kernels through the gateway, and merges all parts into one inbox with **one cursor**, each record tagged with its kernel. Filtering happens where the change happens: a session or agent that is not a target never leaves its kernel, and a kernel without a target is never contacted. Answering Miguel's question: a kernel running 40 sessions where the agent follows one agent sends that agent's changes and nothing else.

**Lifetime.** The subscription ends only when its grant ends (expiry, revoke, holder exit, and a restart of the agent's own kernel, which ends grants) or when the external agent cancels it. Nothing else ends it: no expiry of its own, not a session ending (that target reports `session ended` and leaves the list), not a target kernel restarting (its part is durable there and keeps collecting), not a dropped relay link (the gateway resumes the part from its last cursor), not days without reads. When it ends, a running wait returns `subscription_ended { reason }` and the gateway removes the parts on the other kernels; a part whose owner kernel never comes back is removed when that kernel's gateway reconnects without it.

**Bounded inbox.** Unacknowledged records stay until acked. If more than 100 000 are pending (decided by Miguel, 2026-10-21), the oldest are dropped and replaced by one `gap { kernel, dropped, from, to }` record; the subscription continues. A cursor older than the oldest kept record is answered with `cursor_expired { oldest_cursor }`, never a silent jump.

**Requests (external access path only).**
- `SubscribeEvents { targets }` adds targets; `UnsubscribeEvents { targets | all }` removes them, and `all` cancels the subscription; `GetEventSubscription` lists targets and per-kernel health.
- `ListEvents { since?, limit }` returns records after `since`, oldest first.
- `WaitEvents { since?, timeout_ms, limit }` returns as soon as at least one record exists after `since`, with every record already pending (up to `limit`), or empty with `timed_out: true` at the timeout. The kernel caps `timeout_ms` at 15 min.
- `AckEvents { cursor }`. `since` omitted means "after the last ack".
- Response `EventsListed { events, next_cursor, oldest_cursor, timed_out }`.
- The gateway uses the same requests on the other kernels to manage their parts; there is no second protocol.

**Visibility.** Within what the grant may see, with the existing credential-literal redaction. A routine approval is an ordinary `interaction pending` record the agent may answer; a passkey approval is only the pointer.

**Assistants (later).** An assistant is an `Outside` recipient that the kernel itself runs, so its delivery is a turn, like a session agent's, while its reach is that of an outside principal. Nothing for assistants is built in v2; the recipient kind leaves room for it.

### 14.6 CLI

```
chariox events subscribe   --kernel K --session S [--agent A]      # add a target (agent omitted = the whole session)
chariox events unsubscribe --kernel K --session S [--agent A] | --all
chariox events subscription                                        # targets and per-kernel health
chariox events list  [--since C] [--limit L]
chariox events wait  [--since C] [--timeout S]
chariox events watch [--since C]          # one JSON line per record until interrupted or the subscription ends
chariox events ack <cursor>
```

- `wait` prints `{events, next_cursor}` and exits 0 as soon as something arrives; 5 on timeout (with `next_cursor`, so the next wait continues); 3 when the subscription ended (the reason is in the output); 7 on `cursor_expired`. An unreachable target kernel does not fail the wait; `subscription` shows it and its records arrive when it is back.
- Three ways to use it, no custom tool needed:
  - **Synchronous:** `wait --timeout 540` in the foreground, looping on `next_cursor`. Works in any harness; the timeout stays under the harness's own cap for one command (about 10 min for Claude Code).
  - **Background:** the same command with the harness's background option (`run_in_background` in Claude Code). The agent stays free and the harness tells it when the command exits.
  - **Polling:** `list --since <cursor>` whenever the agent wants to look.
- `watch` is for harnesses that read a live output stream.
- `chariox guide` gains one paragraph: follow sessions or single agents, the three ways to wait, keep the cursor, resync on exit 7, show approval pointers to the user verbatim.

### 14.7 What it replaces

The coordinator's `watch.sh`, lane-folder and `LANE_STATUS.md` polling and the ssh round trips behind them. Each lane is an agent: "lane finished" is an `agent` record with task `done` or run state `idle`, "lane needs me" is task `blocked` or an `interaction pending`. The coordinator follows its lane agents on b3 and the Mac and runs one `chariox events wait` in the background. This is the dogfood target (EA2-34) and the reason this ships together with the agent-model work rather than after it.
