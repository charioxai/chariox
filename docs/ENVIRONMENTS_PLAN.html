1. Summary and approved decisions — MP-08 / MP-10 / MP-11

The Environment describes requirements. It is a Project object, with a project-wide section and one section for each folder. A machine holds observations about those requirements. A Room's browser or desktop remains a separate runtime object.

Miguel's approved decisions, quoted from the task

Every Project has ONE first-class Environment, opened from the project list in the web app (and equivalent in the TUI). It has a project-wide section plus one section per folder (a folder may be a git repo, but git is optional; a project can have several folders).

Items are requirements, grouped by general-purpose kinds so it works for any work, not only coding (e.g. a marketing campaign): Files (folder; git optional), Software (runtimes, CLIs, packages, desktop programs, fonts), Services (things that must run), Variables (non-secret), Secrets (names + Vault location, never values), Accounts (provider and service sign-ins via authorization links, never terminal commands), Connectors (MCP servers, skills, instruction files), Chariox Apps (+ grants), Setup & checks (install/build steps and quick health checks), Machine needs (OS, CPU, RAM, disk, GPU). Empty kinds are hidden. Each requirement records its origin (detected at file:line / added by the user), its status per machine (Ready, Missing, Outdated, Needs your input, Conflict) and last-checked time.

Lifecycle: Detect (the existing utility agent, widened; import from devcontainer.json, .tool-versions/.nvmrc/mise, package manifests, .env.example, docker-compose, .mcp.json, and file types/linked accounts for non-code folders) → Review/edit by the user (versioned) → Apply → Check at any moment (drift).

Storage: the kernel owns the Environment, stored OUTSIDE the project folders under ~/.chariox (kernel state). An explicit Export option lets the user share it manually (devcontainer.json-compatible export where it fits); collaboration comes later. Cloud only displays/edits through the kernel (AGENTS.md: kernel is runtime authority).

Apply by default on the kernel the project belongs to. Project-scoped items apply automatically (variables, Vault secrets, connectors, Apps, tool versions installed into Chariox's own area under ~/.chariox). Conflicts with what the machine already has are DETECTED and REPORTED and the conflicting item is NOT applied — no replace/upgrade/downgrade handling. General-purpose programs install through the platform package manager — Homebrew formulae/casks on macOS, apt and Flatpak on Linux — opt-in per item by the user.

Transfer V1: an exported project arrives as a NEW project on the receiving kernel; if the receiving kernel holds a project of the same lineage (stable project/environment ID), offer "Update from this export" (replace after showing a diff); an independently created project is only replaced manually after a diff; never an automatic merge. Kernels stay independent (no sync).

Secrets keep today's Vault rules (values never in specs, logs or model context; target-sealed transfer). Provider logins only through official provider flows surfaced as authorization links.

What this changes

Unify the saved setup recipe and the environment manifest into the Project Environment. Preserve recipe attestation, deterministic Vault resolution, export refresh and kernel-owned operation recovery. Add folder scopes, typed requirements, direct editing, revision history, machine observations and Check. Fold accounts, connectors and Apps into the requirements view without moving their authority out of their existing kernel services.

Apply is an explicit lifecycle action on a reviewed revision. Within that action, eligible project-scoped items need no separate installation toggle. General-purpose programs still need an individual opt-in. Imported requirements are reviewed before application. A review or import does not execute a script or broaden a grant.

MP-08 keeps one runtime contract across ordinary kernels, slices and managed machines. MP-10 proves that behavior with exact-source real drills. MP-11 follows the narrowed 5 October scope: behavioral parity plus current semantic review of security-critical anchors. This plan does not require exact-blob review of unrelated source.

3. Concepts and requirement kinds — MP-08 / MP-10

Project is the work container. Environment is its single set of reviewed requirements. Folder is a scoped source/data root; Git is optional. Machine target is where requirements are checked or applied. Observation is a measured result on that target. A managed slice is a parent-owned execution target; an independent managed kernel owns its imported Project.

Project-wide requirements apply across its folders. A folder section adds requirements for that folder. Avoid implicit last-writer-wins overrides. Two incompatible requirements for the same effective variable, tool, service, mount or capability are a Conflict until the user edits the specification. Distinct folder-local tools or variables may coexist when the kernel can enforce distinct launch scopes.

The lineage IDs are generated through normal kernel paths once and carried by exports. Local Project and Workspace identities remain target-owned. Portable folder IDs survive transfer; local absolute paths and worktree bindings do not. Revision numbers are local to each kernel; a content digest and recorded parent/export digest identify differences across kernels. Matching a display name or Git URL never establishes lineage.

VaultSecretRef has only a logical name and Vault location. AccountRef has only linked-account metadata; transient authorization URLs are issued at use time, never exported as durable credentials. AppRef and ConnectorRef point to existing registries. Export includes only approved portable definitions/packages and requests for grants, never an already authorized target grant.

Versions and transactions

  • Specification revision: each saved edit or accepted detection diff creates a new immutable revision. Require expected_revision for mutation. Reject concurrent stale edits with a safe diff; never silently overwrite them.
  • Observation revision: Check updates target observations, not requirements. Evidence changes invalidate applicable receipts. “Checked on revision A” cannot certify revision B.
  • Operation identity: apply retries bind operation, attempt, revision, selected items, opt-ins and target generation. Idempotent replay returns the same receipt. The kernel checks authorization and target identity again before each mutation.
  • Schema version: independently version the durable aggregate and portable export. Migrate legacy recipe + manifest transactionally; preserve evidence, reviewed state and setup history. Unproven legacy readiness becomes an old observation needing Check. Keep recovery until migration commits, then remove obsolete duplicate authority and compatibility glue when clients no longer need it.
  • Import transaction: stage verified metadata and selected files, show a diff, commit one new/replaced Project atomically, then require target Check/Apply. No imported status or source grant becomes Ready locally.

Storage

Reuse the private kernel state root and existing project-environments store. Proposed layout: ~/.chariox/state/project-environments/<hashed-project-key>/ with revision records, evidence index, observations and operation journal. The implementation must resolve the configured CHARIOX_HOME, not hardcode a user's home. Store mutable files outside every Project folder, with private directory/file modes. Use existing atomic writes and store transactions rather than a second database.

Tool versions, connector packages and runtime preparation state belong in Chariox's own project/target-specific area. Files the user is working on remain in their selected folders. An explicit export writes only to the user's chosen destination. Generated logs, temporary scripts, service state and check output never appear as automatic workspace .chariox folders.

6. Apply, installs and execution boundary — MP-08 / MP-10 / MP-11

Apply plan

Default target: the kernel that owns the Project. The user may choose a managed slice or managed machine through the existing target selection. Show the exact machine, OS, target generation, folder mapping, accepted revision and per-item effects. A managed machine that is an independent kernel imports its own Project; a managed slice keeps its home kernel's session and Environment authority.

  1. Measure target machine needs and inventory through allowlisted probes. Resolve dependencies and incompatible scope declarations. Recheck freshness and target identity at mutation time.
  2. Build a plan for the reviewed revision. Separate eligible automatic project-scoped work from general-purpose items awaiting individual opt-in. List conflicts and blocked dependents. Do not block unrelated items just because one item conflicts.
  3. Apply eligible scoped items in dependency order. Use private, target-local tool homes under CHARIOX_HOME; materialize only scoped variables and authorized Vault bindings. Install/activate connectors and Apps through their existing kernel admission and grant services.
  4. Execute opted-in general-purpose installations through the platform package manager. Keep a durable item receipt. Do not invoke a free-form model-generated system install command as an adapter.
  5. Run permitted bounded checks on the actual target. Persist outcomes, last-checked times and safe failure details. A downloaded package, connected provider or live relay never substitutes for validation.

Conflict rules

  • A system/global version that fails the requirement is a Conflict, even when a private side-by-side install would be technically possible. Do not use scoped PATH to hide the deliberate system-version conflict. Apply leaves that requirement untouched. The user may edit the requirement or fix the machine manually, then Check.
  • A compatible existing program may satisfy the requirement if provenance and bounded checks pass. An older Chariox-owned tool is Outdated; this version does not upgrade it. A conflicting occupied private install path is Conflict. Missing tools can be installed into unused private paths.
  • Different folder-local versions can coexist only with distinct target homes and launches. Incompatible project-wide and folder assignments, duplicate service ports, conflicting font identities, nonempty folder collisions, mismatched connector names/digests or incompatible App grants block the affected item.
  • Probe failures or lost authorization never become Ready. Show a safe reason and retain the last known receipt as stale. A revoked/expired account becomes Needs your input; a missing executable becomes Missing; a version mismatch needing replacement remains unapplied.
  • Re-probe before installation and before final receipt. If the target changes after planning, stop that item with Conflict or a safe retryable failure. No installer force, replace, upgrade, downgrade or dependency resolution that mutates incompatible existing software is allowed.

Package managers may alter dependencies. Preview the actual dependency transaction where the manager supports it. If it would replace/upgrade/downgrade an existing incompatible package, report Conflict and do not run the transaction. Verify the executed transaction against the accepted item plan. A package source change or unavailable package becomes a bounded failure, never a substitute package chosen without review.

Setup and check execution

Reuse today's kernel setup lifecycle, worker confirmation, source/lockfile attestations, credential environment removal, durable project/worker preparation HOME, bounded command runner and cancellation settlement. The utility proposes definitions; only the kernel executes them. Reuse the confirmed disposable worker for opaque user/project setup, build and shell checks. This protects Chariox-supplied credentials by stripping their bindings; it does not prove arbitrary project scripts are sandboxed or that project-supplied credentials are safe.

An ordinary owning Mac/Linux kernel can directly run named, bounded inventory probes and typed scoped installers. It must not silently run opaque commands on the host merely because its general runtime role allows existing setup admission. Extend planning to require the disposable-worker boundary for those steps, or report Needs your input when that boundary is unavailable. A worker build receipt describes that worker; it does not certify host health. Direct host probes must independently verify the host's declared needs.

Scoped installs performed by an execution worker stay on that target. Installing into the Project kernel's ~/.chariox uses that kernel's typed installer; never copy a prepared executable back from another OS. If a step cannot meet its requested target and boundary together, explain the blocked item instead of claiming host Apply succeeded.

Setup receives only the values authorized for that step. Keep provider accounts, controller credentials and unrelated Vault entries out of opaque commands. Generic secret injection does not bypass setup's credential stripping; an account-dependent check uses the named authorized connector/account service. Structured validation retains exit codes, command digests and output byte counts; avoid retaining raw command output that may contain secrets.

Partial work and recovery

Cancellation settles owned child processes and service actions. Reject signal targets 0, 1, -1, undefined, NaN and unverified groups; verify exact process ownership. Persist successful item receipts before advancing. A resumed operation rechecks facts and skips verified completed work. It never blindly repeats an unconfirmed system install. Check the resulting target and report uncertainty. Preserve user data; rollback only an uncommitted scoped transaction this operation owns, never shared packages or unrelated project state.

It uses bounded named probes; opaque health scripts retain the worker boundary. Re-detection updates proposals, not the checked specification.

Before a target has been checked, the observation is absent: show “Not checked” and no last-checked time, rather than fabricate a sixth measured status or mark it Ready. During a check show kernel operation progress separately from the last observation. Offline/unavailable is target connectivity, not a requirement verdict. Stale observations stay visible as “Last checked …; check again,” with Ready suppressed from the current summary.

Check covers file existence/digests and folder access; effective executable identity and version; package/font availability; live service health; safe variable binding; Vault reference authorization without echoing a value; required account capability; connector registry/runtime; App admission/grants; setup receipts; and machine capacity. Stop read probes from mutating or billing real services. An explicit write/send workflow is a separate user action.

Manual changes create drift: removed files, changed versions, stopped services, revoked grants, expired accounts, edited values or changed machine capacity.
