External Provider Live Parity Drill Plan

Validate live external-turn tracking for codex, claude, and opencode through the product web terminal and TUI. Each provider drill creates a fresh provider-owned session outside Arroba, imports it as an unattached agent, then verifies badge lifecycle, transcript parity, scroll behavior, and turn collapse behavior while the external turn is still running.

Drill Shape

Providers

  • codex: external Codex session, current configured Codex model.
  • claude: Claude Code with Sonnet 4.6.
  • opencode: OpenCode with Kimi K2.6.

Observers

  • Product web terminal driven through browser automation.
  • TUI driven through the existing automation socket and snapshots.
  • Provider-native session transcript retained as the source of truth.

Prompt

  • One external prompt per provider.
  • Exactly 20 assistant progress messages, marked ASSISTANT_STEP_01 through ASSISTANT_STEP_20.
  • Exactly 20 observable tool calls against a temporary drill workspace.

Provider Prompt Contract

The drill prompt must force enough activity to prove Arroba keeps a single turn active across many provider updates. The prompt should ask the provider to:

  1. Create temporary drill files under the chosen workspace. Prefer a temporary drill directory when the provider allows it; use a unique workspace-root scratch-file prefix when a provider blocks subdirectory writes, and report that as a provider limitation.
  2. Run 20 small tool actions, each with a visible marker TOOL_STEP_01 through TOOL_STEP_20.
  3. Emit 20 separate assistant progress messages, each with one marker ASSISTANT_STEP_01 through ASSISTANT_STEP_20.
  4. Use file operations that are easy to verify: create, append, read, list, inspect metadata, and delete.
  5. End with a final summary marker FINAL_EXTERNAL_PARITY_SUMMARY.

The drill should keep all scratch files under a generated provider-specific path or filename prefix and remove them before completion.

Execution Flow

  1. Preflight the local dev kernel on 44120, the product frontend, provider auth, and provider CLI availability.
  2. For each provider, launch the external session outside Arroba and submit the provider prompt.
  3. Refresh Arroba's unattached-agent inventory until the new provider session appears.
  4. Import the unattached provider session into a new Arroba session.
  5. Open that Arroba session in the web terminal and in TUI automation.
  6. Poll provider transcript, Arroba operational history, web DOM state, and TUI automation snapshots until final completion.
  7. Capture before, during, and after evidence for every provider and observer.

Required Assertions

Area Assertion
Badge lifecycle Badge starts as IDLE, changes to WORKING after the external prompt/first observed update, remains WORKING across all 20 assistant messages and 20 tool calls, and returns to IDLE only after provider completion.
Transcript parity Provider transcript, web transcript, and TUI transcript all contain the single external prompt, all ASSISTANT_STEP_01..20 markers, all TOOL_STEP_01..20 markers or equivalent provider tool metadata, and the final summary marker.
Prompt dedupe Arroba shows the external prompt once. It must not repeat the prompt as new blobs arrive.
Live updates New assistant/tool blobs appear in web and TUI while the provider-native session is still generating, not only after joining or after provider completion.
Scroll behavior Web and TUI stay pinned to the bottom during live updates unless the drill intentionally scrolls away. No output update should jump the viewport upward.
Turn expansion The active turn must not collapse before provider completion. After the final assistant summary and IDLE transition, the completed turn should collapse according to the normal transcript rules.

Artifacts

  • One artifact directory per provider under the existing live-drill artifact convention.
  • Provider-native raw transcript/session file snapshot.
  • Arroba operational-history excerpt for the imported session and agent.
  • Web screenshots before, during, after, and after expanding the completed turn.
  • TUI automation snapshots before, during, after, and after expanding the completed turn.
  • Badge transition timeline with timestamps and source events.
  • Transcript parity report showing matched and missing markers for provider, web, and TUI.
  • Scroll/collapse timeline report showing viewport bottom distance and expanded/collapsed state over time.

Implementation Notes

  • Add a new live matrix script rather than overloading the fixture-based external import drill.
  • Run providers sequentially by default to avoid provider auth, CPU, and model-output contention.
  • Keep the provider-native session open and observable until Arroba has verified the final idle state.
  • Use existing kernel IPC helpers for unattached-agent refresh/import and session history reads.
  • Use existing TUI automation socket helpers for snapshots and badge assertions.
  • Use product frontend browser automation for DOM, screenshot, scroll, and collapse assertions.
  • Fail the provider drill when transcript parity or badge lifecycle fails; preserve artifacts on failure.

Success Criteria

  • Pass: all three providers satisfy badge lifecycle, transcript parity, live-update, scroll, and collapse assertions in both web terminal and TUI.
  • Investigate: any provider that lacks optional metadata must still pass visible transcript and tool-call parity, but the missing metadata must be explicitly documented.
  • Fail: duplicated prompts, stale history after joining, premature IDLE, premature collapse, missing final collapse, missing tool/assistant markers, or scroll jumps while pinned to bottom.

Final Provider Limitations Report

Every completed drill run must end with a provider-by-provider limitations section. This is part of the acceptance criteria, not an optional appendix. The report must be the final section of the drill result and must clarify what each provider persists and exposes live, what Arroba can display from that data, and what is unavailable because the provider does not write it to its session files or event stream.

  • For each provider, list available live metadata: status/running state, assistant text, tool calls, tool results, reasoning/thinking summaries, timestamps, token usage, model identity, and final completion/error state.
  • For each missing metadata category, state whether it is an Arroba bug, a provider persistence limitation, or a drill-observation limitation.
  • Do not imply parity for traces or hidden reasoning that the provider does not expose.
  • Include exact provider session IDs and Arroba session/agent IDs so limitations can be reproduced.
  • When a provider falls short, record the product impact and the expected Arroba behavior, such as showing an explicit unavailable metadata state rather than leaving the UI blank or implying the turn is still active.

Final Result Template

The drill report should use this order so the last thing the reader sees is the clarified provider limitation matrix:

  1. Overall pass/fail result.
  2. Provider matrix for codex, claude, and opencode.
  3. Web terminal evidence: badge lifecycle, transcript parity, scroll behavior, and turn collapse behavior.
  4. TUI evidence: badge lifecycle, transcript parity, scroll behavior, and turn collapse behavior.
  5. Artifact links or paths for screenshots, snapshots, raw provider transcripts, and Arroba history excerpts.
  6. Provider limitations and clarifications. This must be the final section and must explicitly distinguish Arroba bugs from provider-native metadata limitations.
