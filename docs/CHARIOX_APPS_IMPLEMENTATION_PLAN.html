Chariox Apps

Apps as first-class programs in the agent OS

This plan turns the existing notification path and Slack-specific kernel behavior into a general App system. Each App has a Node backend in an operating-system sandbox and a frontend Tab in the Room's kernel-managed Chromium Environment. Apps keep private data, expose tools through the single Chariox runtime MCP, and activate agents only through workflow triggers. Every terminal presents the same frontend Tab.

Definition of done

Required outcome

The project is implemented only when a third-party-style App can be packaged, installed, run, updated, bound to an agent, used by that agent through the runtime MCP, opened by a person, and connected to a workflow trigger without privileged App-specific kernel code.

  • No privileged reference Apps.Slack, Todo, and Documents use the same package, SDK, supervisor, file, UI, event, and binding paths available to a local developer App.
  • Every conforming App runs.Chariox ships and tests the App sandbox on every supported kernel OS. App developers target one package and capability contract rather than platform-specific containment APIs.
  • No legacy Slack exception.The temporary Slack logic leaves the kernel. Slack notification ingress and Slack actions run through the installed Slack App.
  • One MCP.Models see one Chariox runtime MCP. Bound App tools appear as namespaced functions inside it. Apps never expose a second MCP server to the model.
  • One trigger authority.Only workflow triggers activate agents without a user prompt. App bindings select tool discovery and cannot start an agent or arbitrary workflow node.
  • A bad App cannot stall Chariox.A hung, crashing, memory-hungry, malformed, or non-acknowledging App remains isolated. The kernel, other Apps, workflows, terminals, and event queues continue.
  • Every applicable matrix cell passes.Each feature declares its surfaces. Every applicable cell has automated or drill evidence. A blank cell, unexplained exclusion, placeholder or unsupported assertion blocks completion. Dated human accessibility and authentication drills count where the acceptance criterion requires them.

What does not count as implemented

A demo that runs one trusted App in the web client is not Phase 1. Neither is a package installer without updates, stock Node started outside the App supervisor, a client that executes a second copy of the App frontend, a viewer without authenticated input, or an event callback that bypasses workflow queues.

Agreed shape

Product and architecture decisions

Runtime
A maintained Node LTS release embedded in a signed Chariox App worker. A versioned, tested Node API subset is the developer contract; embedding alone is not containment. The security boundary is a separate operating-system sandbox. Phase 1 ships Seatbelt on macOS plus namespaces and seccomp on Linux. Phase 2 adds restricted tokens, AppContainer or LPAC, Job objects, and process mitigations on Windows.
Conforming backend
Phase 1 accepts JavaScript and TypeScript plus pure-JavaScript or portable WebAssembly npm dependencies. It supports standard Node APIs that remain inside the installation and brokered service access. The compatibility table below names the APIs that require adaptation or later platform packages.
Package
A deterministic .cxapp archive containing a manifest, bundled Node backend with a locked pure-JavaScript dependency graph, responsive web UI bundle, assets, integrity records, and migrations when needed. Chariox supplies the pinned Node runtime.
UI
One HTML, CSS, and TypeScript implementation executes in an installation-scoped origin inside the Room's kernel-managed Chromium Environment. Web, TUI, desktop, and mobile terminals embed or open an authenticated projection of that same Tab.
Styling
Chariox does not require React, a design system, or a visual style. Apps may use plain HTML or any browser framework. The SDK provides capability access and host information.
Files
Standard Node filesystem APIs work inside read-only package and writable installation data and temporary directories. Chariox sets the data directory as the working directory and the OS sandbox denies unrelated host paths. A narrow documented read-only allowlist covers trusted runtime support files required by Node and the OS. A provisioned quota-capable private volume or equivalent enforced storage bounds direct writes. chariox.files adds atomic single-file replacement, import, export, snapshots, and user-selected external grants. chariox.state supplies structured transactions. General multi-file transactions are deferred beyond the committed releases.
Timers
Scheduled App work uses kernel-owned wakes. An App registers durable wake requests (ID, due time, schedule revision) through chariox.schedule; the kernel persists them, starts the App worker when one falls due and delivers the wake at least once. Overdue wakes after sleep, shutdown or restart are delivered on recovery and marked overdue. The release defines a lateness budget while the kernel runs. Standard Node timers remain available for short in-process work while the worker is running, but no App worker stays running only to wait for a due time.
Network
Apps declare destinations and reasons. The App sandbox blocks raw sockets. A fetch-compatible kernel broker enforces approved hosts, ports, redirects, DNS resolution, TLS policy, and opaque connection credentials.
Agent access
Humans and authorized Room agents can use the same App operations through its view or tools. One binding mechanism supports explicit user selection, automatic binding when an installed App is foregrounded, and agent self-grant through the existing extension request path. The existing effective permission mode governs routine access; binding does not restrict the interaction medium or increase authority beyond that policy. Critical operations pause for kernel-owned human validation regardless of who initiated them.
Notifications
The kernel retains durable delivery, deduplication, retry, ordering, and workflow queue authority. The installed App receives the event and emits an App event through its configured automation.
App automation
One App automation points to one workflow endpoint and queue. The App holds an opaque automation ID, not a workflow ID. Automatic fan-out is out of scope.
Freeform
Binding Apps or Extensions to a Freeform agent creates no workflow. Adding a trigger or deploying that agent creates a visible one-node workflow with origin metadata and completes the requested flow directly.
Publish
There is no separate user-facing Publish action. HTTP, schedule, and notification are workflow triggers. Deploy remains a separate direct action.
Distribution
Phase 1 is an independently shippable release for built-in and local developer Apps, including local .cxapp installation and file associations on macOS and Linux. Phase 2 is a later release adding the public Library, publisher management, review and distribution, Windows kernel support, and native terminal integration. Phase 1 has no dependency on an unfinished Phase 2 capability.

App supervisor module

A trusted kernel module owns installation policy and worker lifecycle. It creates one signed App worker for each installation, applies the platform sandbox, and verifies lockdown before allowing the worker to load App code. The worker embeds pinned Node and receives only package, data, temporary, IPC, and resource handles granted to that installation. Callers request an operation and receive a typed result. They never manage a process directly.

App event module

This module owns inbox persistence, acknowledgement, replay, deduplication, occurrence identity, App delivery, automation resolution, broken-binding state, and workflow queue insertion. A slow App cannot hold the event ingestion request open.

App tool module

This module projects bound tools into the runtime MCP, resolves calls to the correct installation, validates schemas, applies permissions and deadlines, and returns structured errors. App IPC remains an internal adapter.

App view bridge module

This module loads each App view in its installation-scoped origin inside the Room's kernel-managed Chromium, authenticates its SDK messages, and binds it to its App backend. Each terminal uses the normal Environment viewer and input protocols to present the same Tab.

Phase 1 dependency: sandboxed Chromium with persistent sessions

The existing Linux slice launch and recovery paths use --no-sandbox. Replace them with a production configuration that keeps renderer isolation active, including inside supported containers. Investigate the reported relationship between sandbox flags and lost Google sessions as a hypothesis; do not assume a Chromium defect without reproducing it. Trace profile persistence, cookie encryption, keyring/password-store availability, browser shutdown and save/restore generations.

Run a deterministic authenticated fixture and a real Google-session regression through save, full container and home-volume removal, restore, browser restart and fallback launch. Preserve the required profile and key material securely. Distinguish Chariox state loss from provider-driven reauthentication. A repeatable Chariox-caused login loss or disabled renderer sandbox blocks Phase 1. Keep any unsafe launch exception restricted to explicit development diagnostics; it cannot host production App views.

Resource implementation and release budgets

P1.03 must name the supported OS/distribution floor, installer-provisioned privileges and delegation, actual storage quota mechanism, and total-resource enforcement for each platform. Record numeric limits on named reference machines before validation: total memory including external buffers and browser work, CPU, threads, descriptors, queued bytes, logs, disk, broker concurrency, startup, event lateness and input latency. Distinguish hard limits from monitored thresholds and bound reaction delay and overshoot. Aggregate admission preserves host and kernel reserves across many Apps. Browser sandboxing alone does not promise these resource ceilings. Each supported installation provisions the required facilities for developers automatically. On Linux this is one privileged step when Chariox itself is installed (package post-install or a single sudo prompt); installing, updating and running Apps never requires root or a new prompt.

Durable event contract

The kernel durably records an incoming occurrence before acknowledging receipt. App handler delivery is at least once. chariox.state can commit App state and an outgoing occurrence record together; raw-file Apps implement the documented durable outbox pattern. The kernel atomically records the dedupe key and workflow enqueue. Keys include installation, automation, event version and stable occurrence identity; scheduled occurrences include schedule revision. Receipt retention covers the advertised replay window. Expired or poison events receive a visible terminal classification; queues and retries are bounded.

Receipts and delivered-occurrence tombstones survive App-data rollback. A timeout after a remote mutation may have an unknown result; cancellation cannot undo an accepted service operation. Use provider idempotency and reconciliation where supported, and do not automatically retry an ambiguous non-idempotent mutation. Pending human validation has its own durable operation state and cannot hold a kernel request handler open.

Versioned AEGS/AEDS cutover

Define the new generic contract before migrating Slack: installation-scoped connection grants, source-interest subscriptions, normalized occurrences and artifact references, installation inbox routes, automation targets, acknowledgements and generation fencing. The App transforms source content into the existing canonical workflow prompt/artifact model. An automation has one endpoint; separate automations may intentionally receive the same source occurrence. Version every changed event, management and client wire contract.

Each connection declares where its service credentials are held and which actions the App can request. Existing AEGS-held credentials remain usable during migration without exporting tokens; the new contract may retain or deliberately replace that mechanism after validation. Opaque handles are scoped to installation, connection, destination and operation. Chariox agent-provider harness credentials never enter this facility.

Slack is the first third-party-style implementation of the new contract, with no privileged exception. Keep current behavior operational until new clean-install and upgrade flows pass live and fault-injection verification. Migrate connection, route and dedupe identities with one active route generation, then remove obsolete Slack-specific code, adapters and configuration. Phase 1 cannot ship with a permanent dual execution path.

Mandatory sandbox rule

Chariox does not load third-party JavaScript into the kernel or App supervisor. Every App backend starts in its own App worker process. No App code runs before the supervisor proves that the default-deny OS policy is active. Runtime permission flags add diagnostics and defense but never replace the OS boundary. Phase 1 must pass on macOS and Linux. Windows joins the same contract in Phase 2.

Package, installation, updates and migrations

Compiled proprietary backends (Phase 2)

Phase 1 packages ship a bundled JavaScript backend; the compiled format below is Phase 2 work delivered with the Library. Phase 2 supports distributing a proprietary App backend without its JavaScript or TypeScript source text. Developers keep using the supported Node SDK and libraries; Chariox release tooling compiles before distribution and signing. Development mode can execute source. Open-source packages may deliberately include source. Minification, obfuscation, archive packing, encryption and a single-executable wrapper alone do not satisfy the proprietary compiled-backend contract. Compiled instructions can still be reverse-engineered; source confidentiality from a determined machine owner is not promised.

Evaluate a Chariox-owned V8 bytecode compiler/loader inside the existing sandboxed Node worker first. Select and version the production format only after proving supported ESM/CJS dependencies, SDK callbacks, asynchronous execution and all supported macOS/Linux targets. Do not treat Bytenode or a V8 code cache as an already-approved drop-in solution. Record unsupported source-introspection or dynamic-loading behavior explicitly. Compiled loading must begin after containment, use the same bounded IPC and grants, and must not enable arbitrary native executables, FFI, subprocesses or a second per-App Node runtime.

The signed manifest binds backend artifact format, compiler/runtime build identity, supported target variants and their exact digests. The loader rejects incompatible or malformed artifacts before App execution. The build tool produces required variants from one developer source project. Include backend dependencies and migration code in source-exclusion checks; source maps, source-bearing caches, inline sources, private symbols, development files and secrets must not leak into proprietary packages. Keep publisher debugging material private and preserve required third-party notices. UI HTML/CSS/JavaScript remains a web bundle and may be minified or obfuscated without a compiled-UI requirement.

Before shipping this format, prove a runtime security-update path: compatible artifacts remain usable, or the publisher rebuilds and signs replacements against the new runtime through the same release tooling. Installation never compiles supplied source or runs npm hooks; never silently ship a source fallback or retain a vulnerable runtime indefinitely to accommodate old bytecode. State the supported compatibility window and recovery policy, including offline upgrades. This compiler/loader decision and its tests are a Phase 2 release gate. Phase 1 JavaScript packages remain valid after the compiled format ships.

Background and sources: Node bytecode compatibility, Node executable packaging, and JavaScript compilation in Hermes. These establish candidate mechanisms; Chariox must validate its own loader.

Update completion rule (Phase 1 local replacement)

An update is complete only after its durable installation generation agrees across worker, data schema, capability decision, tool catalog, and views. Old workers, bridge sessions and cached UI generations cannot issue operations. Events resume with deduplicated enqueue. Fault injection proves pre-commit rollback; post-commit recovery preserves newly accepted writes and external-effect history.

The kernel runs an App only while there is work for it

Running an App is a kernel decision, independent of whether its view is visible. Human use and agent use keep the App worker running. An enabled notification integration does not keep it running: the kernel owns the waiting. When an inbound event for the installation arrives or a registered wake falls due, the kernel starts the worker if needed and delivers the event or wake; the App then emits App events, which trigger the configured workflow through the existing queue. The App needs no visible view and no separate background-job permission. This follows the operating-system model: the kernel owns timers and event delivery, the program runs when there is work.

Closing a view or detaching a terminal does not stop an agent's work or disable an integration. The kernel persists enabled integrations and registered wakes, and restores them after restart using the existing durable delivery rules. Disabling an integration prevents new triggers through it and does not silently cancel already accepted workflow work or delete the workflow. When no human, agent, event or wake work remains, the kernel stops the App backend through its bounded lifecycle after a short idle period. Installation alone, an unused tool binding or an App's own in-process timer cannot keep it running.

Humans and agents use the same App operations. Agents retain their existing, potentially narrower permissions, and opening an App grants no additional authority. App events can activate agents only through configured workflow triggers. A closed App cannot run unsolicited jobs or invoke agents. Phase 2 Library delivery can download and stage updates for a closed App through trusted Chariox services without starting the App or calling an agent; any App migration runs only in the sandboxed update lifecycle.

One App release, two distribution routes

Keep backend and view architecturally separate but publish one signed App release, with one developer-facing version and one coherent activation record. The view's executable assets, backend artifacts, migrations, capabilities and backend/view API compatibility are identified by that release. A UI-code change is a new release even if it reuses the same backend artifact. Separate frontend release channels are not required. Phase 1 implements this boundary, local package replacement, migration and recovery. Phase 2 adds automatic discovery, delivery, channels and rollout for both distribution routes; it does not defer safe local replacement out of Phase 1.

Library route: the publisher uploads each release without supplying source code, Chariox automatically checks its artifacts for detectable security vulnerabilities and critical failures, and the Library distributes approved releases to enrolled installations on the user's kernels. The Library offers discoverability, managed delivery and auto-updates for users who enable them, plus optional beta channels. It has one publishing and review flow, with no source-based review tiers. The Library owns release discovery and delivery; the kernel owns local signature/integrity/compatibility verification, accepted permissions, staging and activation. This distribution service is separate from the encrypted runtime relay and receives no authority over sessions, agents or conversations.

Direct route: the publisher hosts a signed release feed and packages. A declared publisher channel supplies updates on App opening and through resource-bounded checks while the App remains open, including agent-only or notification-integration use. A closed App does not run a publisher update job. Chariox provides the shared updater and installer, so developers do not write their own signature verifier, self-modifying worker or recovery process. Direct packages do not require Library review and must not display a Library review attestation they do not possess. Channel changes and signing-key rotation preserve publisher identity and require the appropriate authenticated trust transition.

Phase 2 uses the same local update contract for both routes: fetch/stage in the background, retain a working offline release, respect user update policy, and activate at a safe point that preserves drafts and accepted human/agent work. Unchanged permissions do not cause repeated prompts; expanded permissions use existing consent rules. Retain the conservative Phase 1 fenced replacement as the default. A view-only optimization may leave the backend running only when artifact, API, schema, grants and tool catalog are unchanged; define backend generation and view revision separately, invalidate stale view bridges, and test operation continuity before enabling that optimization.

Live content and App-view delivery

The sandboxed App backend serves the view through a kernel-owned, authenticated installation route. It supplies packaged web assets and typed dynamic responses without binding an arbitrary listening port. The view executes once in the Room's managed Chromium; Web/TUI/native terminals project it. JavaScript execution in Chromium is distinct from the developer's release build and backend compilation.

Campaign text, images, schedules, service data and configuration for already-shipped behavior can refresh through the backend's approved network access without a code release or a new Library review. Support opening-time refresh, bounded refresh while the App is in use and enabled notification integrations; update an open view without discarding edits. Give cached content explicit expiry/offline behavior. Executable JavaScript, backend logic and migrations are release artifacts, including when described as templates or configuration: do not intentionally bypass release review by replacing executable code at a mutable URL. Review and sandboxing remain complementary; data-driven behavior cannot be assumed harmless and the runtime boundary applies to all execution.

TypeScript interface

SDK, private files and capabilities

The SDK hides kernel topology, MCP, workflow IDs, relay connections, host paths, and terminal transport. App backends use normal Node APIs inside their private directories and Chariox APIs for operations that cross the sandbox.

chariox.files

Add atomic single-file replacement, snapshots with a declared consistency level, import, export, and user-selected external grants. Ordinary private file I/O uses node:fs. General multi-file transactions are deferred.

chariox.state

Structured values with compare-and-set, multi-record transactions and schema version, backed by kernel-owned transactional persistence. State changes and outgoing occurrence records can commit together. These guarantees do not cover independent node:fs writes. Browser IndexedDB retains its normal transactions for view-local state.

chariox.events

Emit an occurrence through an opaque automation ID, inspect delivery status and retry only when the kernel classifies a failure as retryable.

chariox.schedule

Register, replace and cancel durable kernel-owned wakes with an ID, due time and revision. The kernel starts the worker when a wake falls due and delivers it at least once, marking overdue wakes. Registration can commit with chariox.state changes.

chariox.tools

Register implementations for package-declared tools and receive validated calls with cancellation, deadline and invoking-agent context.

chariox.http

Back the App's global fetch and explicit SDK calls under the installation's approved destination policy. A connection handle names one explicit credential authority and permitted service operations. The broker enforces that authority; AEGS-held credentials are never silently exported into a local token store.

chariox.paths

Expose the package, data, and temporary roots using normal platform paths. The data root is the worker's initial working directory.

chariox.host

View lifecycle, surface dimensions, safe areas, color scheme, input mode, links, clipboard, notifications and system file pickers.

chariox.log

Structured App logs with levels, fields, redaction and bounded retention. Apps cannot write kernel logs directly.

chariox.lifecycle

Startup, suspend, resume, shutdown, update preparation and configuration-change notifications with strict deadlines.

One App operation model for humans and agents

Agents can operate App views and tools at the same functional level as humans under the Room's policy. Bindings choose tool availability through explicit selection, foreground activation or self-grant under the existing permission mode; they do not create a privileged tool lane or prohibit UI operation. Kernel-issued context identifies the installation, Room, actor or background caller, operation and active generation. The App cannot supply an authoritative actor identity or infer human approval from a page click.

chariox.validation.request is the proposed SDK entry for a kernel-owned human-validation interaction. An App may require validation for a declared critical action; kernel policy may require it independently and cannot be weakened by the App. The operation remains durably pending until an authorized human approves. Waiting returns a pending operation ID and releases kernel/worker request capacity; a human reply resumes through the same operation state without replaying earlier effects. Denial, expiry or revocation prevents execution. All callers, including humans using the App view, go through the same rule.

The trusted terminal shows the actual action and canonical parameters outside App-controlled content and outside the agent-operated Environment. Bind the decision to operation ID, installation and release generation, requester, connection, parameter digest, expiry and a single use. Changing an amount, recipient, account or relevant parameter requires new validation. Reuse the kernel's RuntimeInteraction machinery through a versioned extension where needed; all terminals project one pending interaction and concurrent replies settle it once.

Phase 1 confirmation uses the authenticated human terminal channel through kernel approvals, outside App content and the agent-operated Environment. Phase 2 adds step-up user verification for policy-selected high-risk actions, preferably a passkey verified against a trusted Chariox relying-party origin and fresh challenge, together with third-party Library Apps; a TUI can open the trusted confirmation page in the user's browser. Do not introduce an App-visible root password or deliver secrets to App JavaScript. Agent actions and synthetic App messages cannot satisfy human validation.

The trusted action executor or credential/network broker checks and consumes the exact approval receipt before a protected effect. An equivalent unchecked route using the same authority must not exist. App-defined business semantics still need correct App integration: arbitrary allowed HTTP cannot be classified automatically as a payment. The manifest declares protected actions and their effect routes so kernel enforcement has a concrete boundary. Kernel-enforced critical effects use managed handlers or scoped service credentials. Declaring an action cannot make arbitrary direct private-file mutations approval-enforced. After an ambiguous external effect, receipt consumption prevents blind retries and the operation enters reconciliation.

UI SDK contract

  • No required React package, CSS, typography, spacing, colors or component appearance.
  • Apps may use plain HTML, React, Vue, Svelte, Lit or any build tool that emits static browser assets.
  • The managed App origin uses a strict CSP. It cannot read Chariox pages, viewer pages, another installation, or arbitrary network destinations. Service calls go through the authenticated App bridge to the sandboxed backend.
  • Browser storage is partitioned by App installation. Cookies, IndexedDB, Cache Storage, and service workers cannot cross into Chariox, another App installation, or a terminal viewer origin.

Core App experience

The App presents the user's work with Chariox

An App gives humans another presentation of their kernel-owned work. Users bring their focus agent, conversation and automations into the App. The kernel supplies generic execution, permission, state and delivery mechanisms; App functions supply all App-specific meaning. There is one Chariox prompt area, addressing the zero-or-one focus agent, regardless of which App is foregrounded.

One binding mechanism, existing permission modes

The user can bind an installed App explicitly, opening it in the foreground can bind it to the focus agent, and an agent can request the same binding through the existing MCP/extension self-grant path extended to Apps. These are three entry points to one kernel mechanism. The user does not configure separate interactive, tool-selection, automation and service permission systems. Workflows retain the bindings they need for unattended execution.

Use the current effective agent/session permission mode. YOLO allows routine self-grants and operations within the user's existing authority; Ask uses the existing kernel permission interaction when approval is required. An explicit foreground user action is binding intent, so do not ask a redundant binding question when existing policy already authorizes it. An App cannot foreground itself to mint authority. Installation sandbox limits and mandatory human validation remain enforced under YOLO. A possible Sandbox YOLO mode would be one additional global policy, not an App-specific permission matrix; it is not required for Phase 1.

At request submission, capture the focus agent, App installation, Room, task/turn and active generation. Focus changes do not redirect an accepted operation. With no focus agent, use normal Chariox agent selection/creation. Closing a view does not cancel work or strip bindings needed by an in-flight task. Explicit revocation is respected and must not trigger an automatic regrant loop. Catalog changes follow existing provider-adapter refresh semantics while preserving the agent's conversation; pending refresh is visible rather than silently claiming tools are ready.

One private conversation panel

The trusted Chariox terminal renders the normal human-facing conversation/progress panel in a fixed terminal-owned region beside the App view; the App view receives the remaining viewport. Phase 1 starts with this fixed region; App-chosen placement may be revisited if it proves too rigid. This is the only conversation integration. There is no transcript API, App-rendered message subscription or App-configurable workflow-style message-level system. The sole prompt area remains in Chariox terminal chrome; the App does not create its own chat or provider session.

Because the App view runs in remote managed Chromium, the terminal renders this panel outside App-controlled DOM, canvas, browser storage and the App's display stream. The App receives only its own viewport size, not message text, selection, accessible text or conversation-dependent measurements. Input and accessibility for this region belong to the trusted terminal. App CSS, scripts, nested frames, screenshot/export calls and browser observations cannot read the panel or route its input to the App. The panel uses kernel history and authorization directly, and the same isolation applies to Web, TUI browser viewers and Phase 2 native terminals.

The panel follows the normal Chariox focus-agent conversation and history navigation through trusted terminal controls. Switching agents uses their existing distinct histories rather than merging them into an App-owned conversation. It reconnects from kernel-owned durable history. Showing the conversation next to the App does not grant the App access to it. The App sees its own kernel-routed function calls/results and ordinary App state changes, not the surrounding conversation.

Functions are sufficient for App semantics

Use ordinary declared functions such as app.linear.list_issues, get_selected_issues, create_project, get_task_state or validate_project. The kernel does not need a universal issue/project/object taxonomy or an App-specific semantic checker. Current selection is App data accessible through an ordinary function. Task templates and resume state may be returned by functions too.

The additional generic contracts are limited to what ordinary data functions cannot establish themselves: the trusted conversation panel and policy-controlled bindings. The kernel does not interpret App business meaning.

Bind an App or Extension

The user may bind an installed App in agent configuration. Chariox creates a visible one-node workflow using the current agent configuration, adds origin metadata, opens trigger configuration and completes it. HTTP, schedule and notification are the available trigger classes.

Chariox creates the visible one-node workflow and immediately runs the complete deployment walkthrough. The user does not have to find or click the generated workflow first.

Automation lifecycle

  • One automation resolves to one workflow endpoint and queue. Enabling its notification integration opens the App and keeps it open while waiting for events, without requiring a visible App view.
  • The App emits the opaque automation ID and its own stable occurrence ID.
  • Deleting or changing the workflow does not let the App choose a replacement. The kernel marks the automation broken and reports it to the App and user.
  • Deleting an App disables its automations but does not delete workflows.
  • Deleting an agent follows existing workflow lifecycle rules. Chariox warns about generated workflows that remain triggered or deployed.
  • A Todo App reuses one configured workflow for many Todo occurrences. It never creates one workflow per Todo.

Phase 2

Distribution and native clients

Phase 2 adds public discovery, publishing, trust signals, side installation and native hosts. It builds on the Phase 1 package and runtime contract rather than creating a separate marketplace runtime.

P2.01

Chariox App Library

Build browse, search, categories, App detail, publisher identity, requested capabilities, compatibility, release history, review attestations, install, update, uninstall, rating or report intake, region availability and revocation state.

Exit: a user can discover and install a reviewed App without visiting the Developer Center or handling a package file.

P2.02

Developer Center

Provide publisher onboarding, App ID registration, team roles, signing keys, release upload, preflight, review runs, findings, version management, staged rollout, withdrawal, telemetry policy, support metadata and developer AEGS registration.

Exit: an external developer can manage an App from first identity through a reviewed release without Chariox staff editing production records.

P2.03

Automatic security review for every Library release

Provide an LLM-led security service on initial publication and every update, including UI-only releases. Scope blocking findings to security vulnerabilities and critical failures such as data loss, broken installation or unusable startup. Use deterministic package/signature checks, dependency vulnerability analysis and targeted sandboxed probes to support the model. Design preferences, cosmetic/accessibility suggestions, product choices and noncritical quality findings are advisory rather than release vetoes. There is no routine human approval queue or editorial gate.

Exit: each distributed Library digest has a matching automatic security-review attestation; actionable findings arrive through the publishing flow with measured near-immediate latency and explicit failure/retry states, without claiming that an LLM proves the absence of vulnerabilities.

Immediate-feedback security service

Instant publishing feedback is the product goal. Measure upload-to-verdict p50/p95 latency against numeric budgets fixed before Phase 2 validation, with separate cold and unchanged-artifact paths; do not promise literal zero execution time. Reuse digest-bound results for unchanged components but assess every new release and changed integration. Queue pressure, scanner/model failure or timeout yields a visible pending/retry result, never an unreviewed automatic pass or a hidden human queue. Only blocking security or critical findings hold publication; developers receive evidence, a repair path and automatic resubmission. Optional support for disputed findings is not a routine release dependency.

Bind attestations to the final signed package and component digests, reviewer/policy versions, vulnerability-data freshness, scope, date and result. The trusted review coordinator validates structured findings and required checks before signing; package text and model output cannot directly issue attestations. Review runs in disposable environments, treating source, assets, comments and instructions as untrusted. Review the exact compiled artifacts, manifest and dependency inventory, with isolated execution probes and LLM-assisted interpretation. Publishing requires neither public nor private source disclosure. One review flow applies to every Library release. Dependency declarations may be incomplete; artifact checks and probes cannot establish the absence of vulnerabilities or replace the runtime sandbox. Reports state what was checked and what remains unknown, without implying a source-code audit. Reassess affected releases when new critical vulnerabilities become known.

P2.04

Side installation and autoinstaller

Associate .cxapp with Chariox on desktop and supported mobile share/open flows. Show publisher, digest, review state and capabilities, then complete installation. Allow policy to prohibit or warn on unreviewed packages.

Exit: opening a downloaded package results in an active, visible App or a precise rejection, with no terminal steps.

P2.05

Shared automatic updates, channels and revocation

Add Library-managed delivery and publisher-hosted signed feeds using one kernel updater. Provide automatic/manual policy, stable/preview channels, staged rollout, compatibility holds, safe activation, TUF-based trust metadata, signing-key rotation, withdrawal, revocation and offline catch-up. Library releases require their own automatic security review before distribution; direct releases retain their distinct review status.

Exit: publishers can deliver a joint backend/view release through either route without implementing installation or recovery; routine updates need no repeated consent, and bad releases stop or recover without lost writes or silently expanded access.

P2.06

Native Environment viewers

Embed the Phase 1 Environment viewer and input protocol in macOS, Windows, Linux, iOS, and Android clients. Match App Tab lifecycle, file picker, clipboard, links, safe areas, accessibility, downloads, viewer authentication, human takeover, reconnect, and crash recovery.

Exit: every native client presents and controls the same managed App Tab without executing another copy of its UI.

P2.07

Kernel App-set inheritance

Let users create a clean kernel or copy another kernel's App set. Offer packages and configuration only, or packages, configuration and App data. Remap installation and automation identities, preserve capability decisions explicitly and exclude machine credentials.

Exit: clean and inherited kernels remain independent after creation, and changing one never mutates another.

P2.08

Remaining notification Apps

Move every current notification generator into a Chariox-developed App and remove the generic notification-service-without-an-App concept from user configuration. Keep the existing durable infrastructure underneath.

Exit: every notification source visible to users corresponds to an installed App and one of its declared event types.

P2.09

Windows App backend sandbox

Port the Phase 1 App supervisor and worker contract to Windows using restricted tokens, AppContainer or LPAC identity, Job objects, process mitigations, installation-specific ACLs, and bounded private storage. Reuse the same package envelope, IPC, HTTP broker, lifecycle, and hostile-package corpus. Compiled-backend release tooling also generates and signs Windows variants from the same supported App source.

Exit: every portable JavaScript App accepted on macOS and Linux runs unchanged on Windows, compiled Apps run through a compatible signed Windows variant, and the complete containment suite passes on the signed Windows release build.

P2.10

Tracked work across Apps

Compose normal App functions through existing kernel agents/workflows, with operation correlation, scoped binding, recipient consent and transfer provenance. Cover partial completion, cancellation, duplicate delivery and recovery across App boundaries.

Exit: one task can coordinate issue, code, document and calendar/notification functions through multiple Apps. It retains one prompt/conversation authority and exposes only approved structured data to each App.

P2.11

Compiled proprietary backends

Implement the compiled-backend build/loader contract above, including target/runtime binding, compiled dependencies/migrations, private debugging material and source-exclusion checks. Select the compiler only after conformance and runtime-upgrade validation.

Exit: a locally built proprietary package runs on supported targets without backend source text or installation-time compilation, JavaScript packages keep working, and ordinary source development remains available.

P2.12

App outputs, agent continuation and App-created assets (to revisit)

Postponed from Phase 1 on 2026-09-24 and to be revisited before implementation: structured agent outputs delivered to Apps, resuming an App task with a second agent through App-owned state, and policy-checked workflow/agent asset operations requested by Apps. Information sets were removed as redundant with ordinary App functions and existing permissions.

Exit: defined when the contract is revisited.

P2.13

Step-up authentication for high-risk actions

Moved from Phase 1 on 2026-09-24. Add step-up user verification to kernel human validation for policy-selected high-risk actions, preferably a passkey against a trusted Chariox relying-party origin. Define that origin for Cloud-connected, local-only and remote-TUI kernels, plus enrollment and recovery. Do not introduce an App-visible secret.
