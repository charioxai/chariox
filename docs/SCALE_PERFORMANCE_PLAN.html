00Operating protocol

Mandatory first action

Create two isolated worktrees before changing code

Do not implement this plan in the user's active checkouts. Start both worktrees from fresh origin/main and perform all code changes, builds, drills, and commits inside them.

git -C /Users/miguel/chariox fetch origin
git -C /Users/miguel/chariox worktree add \
  -b codex/scale-efficiency-500 \
  /Users/miguel/chariox-scale-efficiency origin/main

git -C /Users/miguel/chariox-cloud fetch origin
git -C /Users/miguel/chariox-cloud worktree add \
  -b codex/scale-efficiency-500 \
  /Users/miguel/chariox-cloud-scale-efficiency origin/main

Own every process and every port used by the work

  • Launch a dedicated relay, home kernel, worker kernels, Cloud API, and web server for these drills. Never attach the scale work to the user's existing development or staging processes.
  • Choose empty ports at runtime. Check every candidate with lsof -nP -iTCP:<port> before binding, reserve the complete port band for the run, and record the resolved ports in the run manifest.
  • Use a unique temporary CHARIOX_HOME, kernel state directory, database, relay token, browser profile, artifact directory, and port offset for every run.
  • Track the process group and every child PID. Install EXIT, INT, and TERM traps before launching the first service. Never use broad pkill patterns that could terminate user processes.

Clean up after every drill, including failures

  • Stop only the owned browser, servers, relay, kernels, provider stubs, screen/tmux sessions, and child process groups. Wait for exit, then force-kill only owned PIDs that fail the grace period.
  • Delete temporary kernel homes, SQLite/WAL files, browser profiles, sockets, logs, and intermediate artifacts. Preserve only the compact final manifest, summary, and profiles required as evidence.
  • Verify cleanup with ps and lsof. A drill is not complete while an owned listener, child process, or temporary state directory remains.
  • At final handoff, confirm both worktrees are committed and clean, push their branches, then remove the worktrees and prune worktree metadata. Keep the branches until the changes are merged.
Resource rule: do not start a new scale run until the previous run's process group and temporary state have been removed. Failed drills count too.

01Current assessment

The actor/projection direction is correct, and the browser already bounds visible terminal panes. The unfinished ownership migration still leaves several costs proportional to total sessions, total agents, subscribers, or historical output.

Serialized session reads

Session lists and projections still deep-clone state behind exclusive mutexes. Prior measurements reached roughly 1.1 ms per session for a read-only list.

Global output sweep

The transport pump still scans all sessions and enters the global DaemonApp lock to find work that is already identifiable by provider-run readiness.

Shared storage locks

Terminal output, durable state, and operational history serialize through process-wide mutexes and synchronous SQLite work.

Repeated inventory work

Each local or relay inventory subscriber can rebuild and compare the same waiting-room snapshot independently.

Sequential browser hydration

Initial history hydration is configured as one agent per request and renders each agent repeatedly, which turns a 500-agent reload into a request/render train.

Coarse relay registry

Routes, presence, pending requests, and subscriptions share one relay registry lock even though they have different write patterns.

02Performance contract

Phase 1

Instrument before restructuring

  • Add interval histograms and high-water marks for command latency, projection builds, app-lock wait/hold time, terminal queue records and bytes, SQLite batches/fsync, relay queues, and browser event/render/hydration work.
  • Record projection builds per logical revision and browser history requests per visible agent. Diagnostics remain sampled and off by default.
  • Run release-build baselines at 10, 100, 200, and 500 agents plus 20×50, 50×20, and 100×10 session layouts before changing behavior.

03Kernel efficiency

Phase 2

Make reads immutable and constant-cost

  • Replace the global session-service mutex with a small create/delete/index registry plus actor-owned mutable state per session.
  • Publish versioned Arc session snapshots, lightweight session-directory summaries, and a shared waiting-room projection after canonical mutations.
  • Serve ListSessions, GetSessionState, waiting-room reads, and every subscriber from those immutable projections. Readers clone handles, not full runtime graphs.
  • Build waiting-room state once per coalesced revision. Local and relay subscribers use the same projection and existing row-delta contract.
  • Add an architecture test forbidding owner-store reads, full session-list cloning, or DaemonApp locking in hot transport, output, waiting-room, and subscription modules.
Phase 3

Process only ready provider runs

  • Replace the all-session pump with a deduplicated ready-run queue fed by PTY readers and structured-provider callbacks. Use a deadline heap for first-output, inactivity, and cleanup timers.
  • Use async FIFO mailboxes per provider run and one bounded blocking executor for unavoidable synchronous adapter work.
  • Keep required PTY readers bounded, with explicit small thread stacks and byte queues.
  • Shard terminal stream ownership by session, store output bytes once as shared immutable buffers, and track recipient cursors separately.
  • Replace the global eight-request semaphore with a process limit of min(256, max(32, CPU_COUNT × 8)), a 32-request per-connection limit, bounded session/agent lanes, and reserved capacity for prompt, cancel, approval, and reconnect commands.

04Persistence off the stream path

Phase 4
  • Give durable state and operational history independent bounded writer actors. Group up to 256 records or five milliseconds of work into one transaction.
  • Backpressure writers instead of dropping. Preserve sequence assignment, return acknowledgements where durability is part of command acceptance, and flush on graceful shutdown.
  • Use dedicated read-only WAL connections so history hydration never waits on the writer mutex.
  • Store and index history merge keys by (session_id, agent_id, merge_key, sequence); remove scan-and-decode replacement lookups.
  • Replace full-state JSON checkpoints with incremental entity checkpoints and an atomic manifest sequence. Read old snapshots as a migration fallback, then compact asynchronously after a successful new-format checkpoint.
  • Test crash recovery before, during, and after every batch/checkpoint boundary.

05Browser and Cloud efficiency

Phase 5
  • Hydrate history initially only for the current desk's mounted agents, in one existing multi-agent outline request. Background agents remain summary-only until focused or explicitly opened.
  • For unmounted completion events, mark history stale without reading it. Replay gaps recover visible agents first; ordinary transport resume stays read-free.
  • Virtualize expanded agent/workflow trees beyond 100 rows, memoize rows by revision, and keep at most six terminal panes mounted.
  • Use mounted-pane and sidebar-row registries instead of repeated document-wide selector scans on event paths.
  • Persist structural inventory changes immediately, but debounce activity-only Cloud cache writes for five seconds. Allow one request in flight and retain only the latest pending version.
  • Make unchanged inventory-version writes a no-op, add the relay-target lookup/order composite index, and page dashboard machine/client/target reads in batches of 100 selected fields.

06Relay routing isolation

Phase 6
  • Split peer routes, presence, pending requests, subscriptions, and display tunnels into independently synchronized stores.
  • Use sharded hash maps for route and request lookups. Heartbeat and registration writes must never take the packet-routing lock.
  • Give peers separate bounded control and event queues with byte accounting and weighted draining.
  • Preserve existing backpressure behavior: request overload returns target_backpressure; a slow subscription closes only its own client lane.
  • Keep the relay transport-only. It must not inspect, retain, or become authoritative for encrypted runtime payloads.

07Interfaces and compatibility

  • Reuse waiting-room row deltas, history cursors, SpawnAgents, LaunchProviderRuns, SubmitPrompts, and batched terminal output.
  • Increment the shared daemon protocol version only if serialized health fields or another wire shape changes. Update protocol hashes, minimum client version, and the focused protocol drill in the same commit.
  • Keep the Cloud inventory-cache request shape unchanged. Change only write coalescing, idempotence, selected fields, pagination, and indexes.
  • Preserve prompt ordering, durable history, permissions, workspace claims, reconnect behavior, and source-gated external-provider observation.
  • Do not add a background provider transcript observer that mutates active prompt state.
  • Temporary drill-only switches are allowed for parity testing, but no permanent dual path or feature flag remains after cutover.

08Validation sequence

  1. Capture current release baselines and profiles in the isolated worktrees.
  2. Land immutable read projections and require flat read latency as session count grows.
  3. Land ready-run output and terminal-store sharding; require zero hot-path app-lock acquisitions.
  4. Land grouped persistence and incremental checkpoints; run restart and retention tests.
  5. Land lazy browser hydration, virtualization, and Cloud write coalescing.
  6. Land relay-store separation and distributed execution.
  7. Run each final gate three consecutive times, cleaning all owned resources between runs.

09Definition of done

The work is complete only when the full matrix passes three times in release mode, all correctness and resource budgets hold, and no hot-path operation scales with total inactive sessions, total subscribers, or full retained history.

Handoff requirement: report benchmark deltas, remaining risks, commit and branch references, preserved evidence paths, and a cleanup audit proving no owned listeners, processes, worktrees, or temporary runtime state were left behind.

Assumptions

  • The guaranteed target is 500 concurrently active Chariox agents distributed across kernels, coordinated by one home kernel and browser.
  • A single kernel must also model and render 500 synthetic agents efficiently.
  • Provider quotas and provider child-process memory are reported separately from Chariox orchestration overhead.
  • The user's existing checkouts, relay, kernels, development server, staging services, and browser state are out of bounds.
