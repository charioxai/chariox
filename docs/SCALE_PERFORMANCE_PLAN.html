Scale & Performance Plan

A measured, root-caused assessment of what stops Arroba from supporting hundreds of sessions and agents across many terminals and multiple machines, with a prioritized set of changes. Findings come from live benchmarks against a debug kernel plus source analysis of arroba (kernel, relay) and arroba-cloud.

Drafted: 2026-07-07 Method: live load benchmarks + code root-cause Target: 100s of sessions/agents, many terminals, multi-machine

The headline: reads are O(n) full-clones behind one exclusive lock

The single most important result. A read-only ListSessions — the call the web waiting room and session lists poll — scales linearly with the number of sessions, at roughly 1.1 ms per session, on a single client with no concurrency:

sessions 2 → ListSessions median 2.7 ms sessions 52 → ListSessions median 68.9 ms sessions 102 → ListSessions median 125.4 ms sessions 152 → ListSessions median 168.0 ms

At 300 sessions a single list read is ~330 ms. Now add concurrency. Throughput of the same read across N parallel clients plateaus at ~300 req/s and per-request latency grows linearly with N — the textbook signature of a single lock serializing everything:

N=1 clients → p50 3 ms 165 req/s N=4 clients → p50 18 ms 134 req/s N=8 clients → p50 29 ms 274 req/s N=16 clients → p50 57 ms 276 req/s N=24 clients → p50 75 ms 301 req/s (throughput flat)
Effective concurrency is ~1 despite an 8-permit admission semaphore: the reads serialize on an exclusive mutex before the semaphore can help. Fix the lock and the clone first; the semaphore is the next ceiling, not the current one.

Root causes (kernel)

1. Session store is a single exclusive mutex; list reads clone every session P1

session/owner.rs (SessionStateStore { inner: Arc<Mutex<SessionService>> }); runtime/state/session_lookup_state.rs (list_session_snapshots)
  • SessionStateStore guards all session state behind one std::sync::Mutex. Both read() and write() take the same exclusive lock, so reads cannot run concurrently — with each other or with writes.
  • list_session_snapshots() calls list_sessions() (clones every RuntimeSession) and then session_snapshot(id) per session — O(n) full clones plus per-session lookups, on every call, under the lock. This is the ~1.1 ms/session measured above.
  • The session-state projection (runtime/projection/session_state_projection.rs) is also an exclusive std::sync::Mutex, so warmed-list reads serialize too.
Fix: serve list/read views from a warmed projection that stores an Arc-shared, pre-rendered snapshot updated on change, handed out by cloning an Arc (O(1)) rather than deep-cloning n sessions per call. Move the projection and session-store read paths to RwLock (or parking_lot::RwLock) so reads are concurrent. Return lightweight list summaries (id, title, agent count, status, revision) for list endpoints; keep full snapshots for single-session reads only.

2. Provider-output streaming pumps through the global app lock P1

runtime/state/provider_output_runtime.rs (repeated with_app_side_effect per pump cycle); Arc<Mutex<DaemonApp>>
  • Every provider-run output pump acquires the one global DaemonApp mutex multiple times per cycle (drain PTY, process bridge, settle prompts). With hundreds of agents streaming, every pump contends on the same lock — the streaming hot path serializes against all commands and all other agents.
  • This is the same global lock the earlier remediation plan (B1–B3) instrumented and began unblocking; at scale it is the dominant steady-state contention point, not just a tail-latency one.
Fix: give each provider run / session actor ownership of its own output state so pumping does not touch the global app lock (continue the M4.5 ownership migration for the output path specifically). Where shared state must be read, use per-session/per-agent locks or lock-free projections, not the daemon-wide mutex. Batch the per-cycle lock acquisitions into one short critical section.

3. Global 8-command admission cap P2

runtime_transport.rs: INBOUND_REQUEST_LIMIT = 8
  • A single process-wide semaphore caps the kernel to 8 concurrent in-flight commands across all connections, terminals, and machines. Once findings 1–2 are fixed this becomes the next throughput ceiling.
Fix: raise the cap and make it scale with cores / configurable; consider per-connection or per-session fairness limits instead of one global cap, so one busy terminal cannot starve others. Admission control should shed load gracefully (it already returns kernel_request_overloaded), but the steady-state ceiling must be far above 8.

4. Coarse pump cadence and O(all-sessions) sweeps P2

runtime_transport.rs: PUMP_INTERVAL_MS=500, WATCH_INTERVAL_MS=100; pump_active_prompt_outputs iterates every session
  • The runtime pump wakes on change signals (good) but falls back to a 500 ms poll, and several reap/pump passes iterate all sessions each cycle. At hundreds of sessions these O(n) sweeps run repeatedly regardless of which sessions are active.
  • The external-provider discovery poller (already trimmed once this session) and the git observer are similar periodic O(n) scans.
Fix: drive pumps from a per-session ready-set / work queue so only sessions with pending output or due timers are visited, instead of sweeping all sessions. Keep the change-signal fast path; make the fallback poll a safety net, not the primary cadence.

5. Per-read allocations and projection clone cost P3

kernel projections and read models (~5,000 .clone() sites)
  • Beyond the session list, many read/projection paths deep-clone their models per request. With the B1 app_lock instrumentation now live, the top clone hotspots can be measured and converted to Arc-shared read models.
Fix: wrap warmed read models in Arc so handlers share rather than copy; measure with the daemon-health app_lock data under real load to pick the top three by cost.

Multi-machine & relay path

6. Relay routing is already RwLock-based; watch registration write contention P3

relay/src/server/connection.rs, relay/src/registry.rs
  • Good news: the relay registry is an Arc<RwLock> — packet routing takes read locks and can run concurrently across peers (the live relay was healthy at 22 peers).
  • At scale, watch two things: registration/heartbeat writes briefly block all routing (write lock), and per-message routing does a registry lookup under the read lock for every relayed packet. With many machines × many sessions, packet routing volume is the relay's scaling axis.
Fix: keep heartbeat/registration writes tiny and off the hot routing path (e.g., sharded or lock-free presence updates); consider sharding the registry by realm/target so a hot realm's writes don't block another's routing. Benchmark relay packet throughput separately (fan-out of provider output across machines is the real multi-machine load).

7. Cloud API read endpoints and DB query shape P3

arroba-cloud/apps/api (Prisma over Postgres)
  • The cloud control plane is off the runtime hot path (it issues tokens, tracks presence, lists targets), so it is not the session-scale bottleneck. But at many machines the waiting-room / relay-target and presence queries run often.
  • Verify these list endpoints are indexed (realm + status), paginated, and cached where possible (the waiting-room inventory cache exists — confirm it is used on the hot path), and that presence upserts are cheap. Add the CI-run Postgres so query regressions are caught (CI was added this session but without a DB service).
Fix: add DB indexes for the relay-target/presence/revocation queries by realm+status; ensure list endpoints paginate; load-test the relay-target and presence endpoints with a seeded DB.

Recommended sequence

Items 1 and 2 together should turn the flat ~300 req/s / O(n)-per-read curve into something that scales with cores and stays roughly constant per read as sessions grow — the prerequisite for hundreds of sessions. Item 3 is the prerequisite for hundreds of concurrently streaming agents. Verify each against the live benchmark harness (create-N-sessions latency curve + N-client throughput) that produced the numbers above.

How these numbers were produced

  • Launched a debug arroba-kernel on an isolated port/state; drove it over the kernel WebSocket with a Node client.
  • Session-count curve: created sessions in batches of 50, measuring median ListSessions latency at each step (single client).
  • Concurrency curve: N parallel WebSocket clients each issuing sequential ListSessions, recording p50/p90/p99 and aggregate req/s.
  • Root causes traced in source: SessionStateStore/SessionStateProjectionStore lock types, list_session_snapshots clone shape, INBOUND_REQUEST_LIMIT, and the provider-output pump's with_app_side_effect usage.
  • The harness is trivial to re-run after each change to confirm the curve flattens; keep the before/after numbers next to this plan.
