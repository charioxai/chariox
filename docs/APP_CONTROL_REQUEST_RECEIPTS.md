# App restart and uninstall request receipts

The kernel uses the existing command-result journal implementation in the shared App control service. `ControlAppWorker` and `UninstallApp` remain excluded from transport caches so every attempt reaches authenticated owner authorization. A new identity must also pass an owner-scoped installation lookup before it consumes a receipt slot; nonexistent and cross-owner targets leave no receipt. Existing receipts retain their original installation authority, while replay still checks the current authenticated caller and exact input. The service then uses the existing `KernelCommand.command_id`, scoped to that owner. Clients must preserve that identity on retry. Local WebSocket frames without `command_id` use their `request_id`; a relay command without an identity is a new request.

A receipt binds the authenticated caller, command source, and SHA-256 of the exact request. Reusing the identity for different input or a different caller returns the existing `AppRequestFailed {code: conflict}`. Different owners have separate identities. An identical pending request waits for the original result. An identical completed request returns that result, including failures. A new identity executes normally against current installation state.

The service writes and syncs a reservation before executing a receipted lifecycle effect. Execution and settlement continue if the caller disconnects or cancels. The final response is appended and synced before either the original call or any pending duplicate receives it. If final append or sync fails, current callers receive `storage_unavailable` and the accepted identity remains reserved; a retry never executes the effect again. Receipt data is stored beside the kernel state database as `<state stem>.app-command-results.jsonl`; it contains App control input digests and results, with no credentials.

A crash after durable acceptance but before execution can leave the operation unexecuted. A crash during execution or before durable settlement can leave a partial effect or a completed effect with no final receipt. In all three cases the same identity returns `AppRequestFailed {code: storage_unavailable}` after recovery and never executes again. This is an unknown outcome, not proof that nothing happened. Check `app worker` or `app status` before submitting a deliberate new request with a new identity. A completed durable receipt survives a kernel restart and returns its original response. There is no automatic recovery execution.

Receipts never expire or evict, because discarding them would permit an old identity to execute again. The service retains the existing 512-entry command-cache bound, across all owners and both request kinds. Once full, new Start/Restart identities fail closed with `limit_exceeded`; existing identities still replay. The cap is global across owners: after an overflow Stop, a new Start or Restart cannot re-enable that App (or any other stopped App) until an owner-approved capacity/identity-retirement design exists. Automatic recovery also respects manual-stop intent. This fix keeps safety controls available; it does not restore normal start admission or provide an operator journal reset.

A new Stop or Uninstall rejected with the dedicated receipt-capacity error executes without a new receipt after owner/installation authorization. Existing receipt matches and conflicts are resolved before this exception, so no previously accepted identity can execute again. Stop persists manual-stop intent and drains/reaps the worker; repeating an overflow stop reasserts that state. Uninstall checks its expected generation before stopping and advances the generation atomically; repeating a completed overflow uninstall conflicts before further side effects. Internal quarantine persists worker-failure state without command receipts and is unaffected by this capacity. Overflow controls still continue after caller cancellation, but have no historical response receipt: after a lost reply, inspect current state. An interrupted uninstall can leave the App stopped or uninstalled with retained data; a deliberate new request using the current generation can finish deletion. No new lane or journal entries are needed, so repeated safety controls cannot exhaust another finite control capacity.

Journal corruption or unavailable storage also fails closed. Do not delete this journal to recover capacity: doing so discards the guarantee. A future receipt archival or identity-retirement policy needs an explicit owner decision.

There are no serialized protocol shape changes. Restart returns the original accepted worker summary; it does not wait for the worker to become healthy. A receipted uninstall returns the original installation summary even if later requests changed it.
