Cross-Repo Review Remediation Plan

A phased plan to carry out the July 2026 cross-repo review of arroba and arroba-cloud: eliminate blocking work under the kernel's global lock, close the security gaps in relay and cloud token handling, restore fail-closed startup behavior in the hosted control plane, add missing CI, and pay down the largest structural debts.

Drafted: 2026-07-06 Repos: arroba, arroba-cloud Source: full-repo review (kernel, relay, cloud API, relay-tokens, web terminal) Status: proposed

Workstream overview

Phase Workstream Repo Priority Effort Risk of change User-visible impact
0 A. Fail-closed security fixes + cloud CI arroba-cloud, arroba P0 1–2 days Low (small, isolated diffs) Closes impersonation/forgery windows
1 B. Unblock the kernel: no blocking work under the app lock arroba P0 1–2 weeks Medium (touches hot paths) Daemon-wide latency stalls disappear
2 C. Token model hardening (TTL caps, revocation, single format) both P1 3–5 days Medium (wire compatibility) Long-lived stolen tokens become containable
3 D. Rust workspace + shared claim model arroba P1 2–3 days Low Faster CI, no dependency drift
4 E. Structural refactors (monster files, flat api dir) both P2 ongoing, sliced Medium (mechanical, test-guarded) Review velocity, onboarding
5 F. Hygiene and small performance items arroba P2 <1 day Trivial Clean clone, smaller repo
Phases 0 and 1 are independent and can start in parallel. Phase 2 (token hardening) should land before any hosted relay realm is opened to external users. Phases 3–5 are sequenced after the P0 work only to keep review bandwidth focused; nothing blocks them technically.

Phase 1 — Unblock the kernel P0

The daemon serializes all command handling behind one Arc<Mutex<DaemonApp>> (114 lock().await sites), and blocking work runs while the lock is held: hard sleeps, blocking relay network round trips, ~139 sync filesystem calls, blocking ureq HTTP, and a sync rusqlite connection. Any one of these stalls every session, agent, and terminal in the daemon. This phase removes the blocking work from under the lock without waiting for the full M4.5 actor-ownership migration; it is compatible with it and reduces its risk.

Order of attack

  1. B1 — instrument first, so improvements are measurable.
  2. B2 — remove hard sleeps (worst latency per byte of diff).
  3. B3 — move relay round trips outside the lock (worst tail latency).
  4. B4 — wrap sync SQLite and filesystem I/O (steady-state jitter).
  5. B5 — swap the blocking HTTP client in the credential service.

B1. Instrument lock hold times and command latency

apps/kernel/src/runtime/command_latency.rs (extend), runtime_transport.rs:136
  • Wrap the app mutex in a helper that records hold duration per call site (feature-gated or debug-level tracing spans; a histogram in daemon health is enough).
  • Expose p50/p95/max lock-hold and per-command latency in the existing daemon health projection so regressions are visible in the smoke harness.
  • Capture a baseline run (multi-agent session with active provider output) before B2–B5 land.
Accept: daemon health reports lock-hold percentiles; baseline numbers recorded in this document's follow-up notes.

B2. Remove hard sleeps from event processing

apps/kernel/src/app/provider_output_claude_native.rs:810, 1225, 1450, 1457; transport/relay_client/display_tunnel.rs:665
  • The 300ms std::thread::sleep on Stop/SessionEnd guesses when the claude-headless transcript has flushed. Replace with an event-driven wait: schedule a follow-up drain command (via the existing command router) after the delay instead of sleeping inline, or poll the transcript file for size stabilization on a background task.
  • Same treatment for the 100–250ms sleeps in the retry/drain loops: convert the containing operations to spawned provider-operation dispatch (the pattern already exists for prompt dispatch writes per the M4.5 notes) so the wait happens off-lock with tokio::time::sleep.
  • This is also a correctness fix: fixed sleeps silently drop output on slow machines. The stabilization check must be deterministic (size unchanged across two polls, or provider-signaled completion), not a bigger sleep.
Accept: no std::thread::sleep remains in async-reachable kernel code (grep-clean, excluding tests); the claude-native suites pass; a Stop event during an active second session no longer stalls that session's echo (verify with B1 metrics).

B3. Move relay round trips outside the app lock

apps/kernel/src/app/relay_runtime.rs:56 (block_on_relay_future), ~20 call sites in app/remote_agent_binding.rs, app/remote_workspace_live_sync_fanout.rs
  • Adopt a two-step pattern per call site: (1) under the lock, snapshot the inputs the request needs and enqueue the intent; (2) release the lock, run the relay future on the runtime (tokio::spawn or the provider-operation dispatch lane), then (3) re-enter via a kernel command that applies the result to state. The router and mailbox infrastructure for step 3 already exists.
  • Prioritize call sites on interactive paths (agent binding, prompt relay) over startup-only ones (registration).
  • Once the last call site is converted, delete block_on_relay_future and its block_in_place escape hatch so the pattern cannot return.
  • Sequencing note: coordinate with the in-flight M4.5 ownership work — convert call sites in the same order that their owning modules are migrated, to avoid churning files twice.
Accept: block_on_relay_future no longer exists; no block_in_place in the kernel; remote-binding tests and the relay smoke harness pass; B1 metrics show relay operations no longer appear in lock-hold tails.

B4. Isolate sync SQLite and filesystem I/O

apps/kernel/src/history.rs:462 (Arc<Mutex<Connection>>), runtime/history_executor.rs, runtime/history_requests.rs, ~139 std::fs call sites under app/
  • History store: route all rusqlite access through a dedicated blocking lane — either spawn_blocking at the executor boundary or a single-threaded worker owning the Connection with an mpsc request channel (preferred: removes the mutex entirely and serializes writes naturally).
  • Filesystem: triage the std::fs sites under app/. Config reads at startup are fine; anything on the command path while the app lock is held (session history appends, workspace scans, provider auth inspection in relay_registration) moves behind spawn_blocking or into the same follow-up-command pattern as B3.
  • Cache inspect_home_provider_auth results with a short TTL so heartbeats don't re-scan the home directory.
Accept: history executor paths contain no direct sync DB calls on the runtime; history suites pass; heartbeat processing does no home-dir I/O (verified by tracing).

B5. Replace blocking HTTP in the credential service

apps/kernel/src/secret.rs:267–292 (ureq)
  • http_request_with_credential runs a blocking ureq call. Either wrap the whole call in spawn_blocking at its dispatch boundary (cheapest, keeps ureq), or move to the async client already in the dependency tree (hyper) — decide based on how many call sites exist after B3.
  • While here: return secrets as Zeroizing<String> from resolve_secret and adjust the few consumers, so plaintext secrets don't linger in caller memory.
  • Micro-cleanup: replace the per-byte format! in hex_bytes (secret.rs:737) with a single-buffer writer.
Accept: credential HTTP tests pass; no blocking HTTP call reachable from a tokio worker without spawn_blocking; resolve_secret signature returns Zeroizing.

B6. Panic and lock-poisoning policy

apps/kernel/src/provider/run_actor/runtime_slots.rs, slice/store.rs, ~267 prod unwrap/expect sites
  • Most prod expects are std-mutex poisoning guards; one panic while holding a slot mutex cascades into daemon-wide panics on every later access.
  • Adopt parking_lot::Mutex for the runtime slot registries (no poisoning, smaller/faster), or standardize on a recover-and-log helper (lock().unwrap_or_else(PoisonError::into_inner)) with a tracing error.
  • Audit the remaining non-poisoning unwraps in slice/store.rs and provider/ for ones reachable from user input; convert those to DaemonError returns. Leave genuine invariants as expects with messages.
Accept: a deliberately injected panic in one provider-run task no longer breaks unrelated sessions (add a test); prod unwrap count reduced and the remainder documented as invariants.

Phase 2 — Token model hardening P1

Must land before hosted relay realms are opened beyond trusted testers. These changes touch the wire format contract between arroba-cloud (issuer) and the arroba relay (verifier), so they ship as coordinated pairs with shared test vectors.

C1. Cap client-supplied TTLs server-side arroba-cloud

apps/api/src/runtime-token-service.ts:39, pairing-service.ts:61, device-login-service.ts:54, pairing-token-repository.ts:21
  • Every issuance path does input.ttlMs ?? default with no ceiling, and routes accept ttlMs from request bodies — an authenticated client can mint effectively immortal relay tokens.
  • Add per-token-type maxima in one shared module (suggested starting points: runtime relay tokens 1h, pairing tokens 15m, device-login 10m, session invites 7d) and clamp with Math.min; reject rather than clamp if the request exceeds the max by more than 10× (likely a bug or abuse).
  • Make the maxima configurable via entitlements later; hardcode sane values now.
Accept: unit tests per issuance path prove a 10-year requested TTL produces a token capped at the type maximum; route schema documents the cap.

C2. Relay-side revocation for scoped tokens arroba

apps/relay/src/auth.rs (ScopedTokenVerifier), relay server state
  • The relay verifies scoped tokens purely by signature + expiry; jti (token_id) is carried but never checked, and arroba-cloud already has revocation bookkeeping (account-admin-revocations) with nowhere to enforce it.
  • Add an in-memory denylist to ScopedTokenVerifier keyed by token_id (and a coarser one by account_id for account deactivation), checked in validate_claims.
  • Feed it from cloud: a periodic pull of active revocations for the realm (simple, works with current architecture) — entries expire from the denylist when the underlying token would have expired anyway, keeping it bounded.
  • With C1's short TTLs, a small propagation delay is acceptable; document the bound (revocation effective within one sync interval).
Accept: revoking a token in cloud causes the relay to reject it within the sync interval in an integration drill; denylist size is bounded by outstanding-token count.

C3. Single token format + shared claim model both

arroba/apps/relay/src/auth.rs (dual arroba-scoped-v1/JWT parsing), arroba-cloud/packages/relay-tokens
  • The relay accepts two formats with duplicated claim parsing; the TS and Rust claim models are hand-synchronized and already drifting (TS emits session_id, Rust silently drops it).
  • Standardize on the JWT form (cloud already issues it), deprecate arroba-scoped-v1: keep accepting it for one release with a warning metric, then delete decode_scoped_token_parts and encode_scoped_hmac_token or move them to test-only.
  • Create a shared conformance fixture: a JSON file of valid/invalid token test vectors (claims, secret, expected verdict) checked into both repos (or one repo, vendored by script into the other) and consumed by both test suites. Add session_id to the Rust claim struct while doing this.
  • Add nbf/future-iat tolerance checks (small clock-skew window, e.g. 60s) on the Rust verifier.
Accept: both suites run the same vector file green; Rust and TS claim structs field-for-field identical; only one non-deprecated wire format remains.

C4. Enable a real CSP on the hosted web app arroba-cloud

apps/api/src/server.ts:89 (contentSecurityPolicy: false), apps/web
  • The browser terminal handles relay tokens and session data; XSS there is token theft. Define a strict policy (default-src 'self'; explicit connect-src for relay websocket origins; no unsafe-inline scripts) and enumerate what currently violates it.
  • The styles-as-TS-modules pattern likely means injected <style> tags — allow style-src 'unsafe-inline' initially if needed, but keep script-src strict; tighten styles when Phase 4 splits them out.
  • Roll out with Content-Security-Policy-Report-Only first, watch reports in the worker, then enforce.
Accept: enforced CSP with strict script-src in production; terminal, workflows, and admin shells function; a regression test asserts the header.

Phase 3 — Rust workspace and build unification P1

D1. Root Cargo workspace arroba

new root Cargo.toml; apps/kernel, apps/relay, adapters/rust (currently three crates, three lockfiles)
  • Create a virtual workspace with the three members; delete the per-crate Cargo.lock files in favor of one root lock. This removes version drift between kernel and relay — which share the auth types via a path dependency today.
  • Hoist common dependency versions into [workspace.dependencies]; add [workspace.lints] (clippy: unwrap_used/expect_used as warn in lib targets to hold the line from B6).
  • Update CI to build/test from the workspace root — Swatinem/rust-cache then caches one target dir instead of three, cutting Rust CI time.
  • Check scripts/ and the compatibility launcher for hardcoded per-crate paths.
Accept: cargo test --workspace green from root; one lockfile; CI wall-clock for the Rust job measurably down; cargo tree -d shows no internally-duplicated majors.

Verification strategy

  • Every security fix (A*, C*) ships with a regression test that encodes the attack: dev-secret startup, prod identity header, tampered signature timing path (behavioral), oversized TTL, revoked jti, expired-token-with-broken-clock.
  • Phase 1 is measured, not asserted: B1's lock-hold and command-latency histograms are the acceptance instrument for B2–B5; keep the baseline and after numbers in a short appendix committed next to this plan.
  • Refactors are move-only: Phase 4 slices separate mechanical moves from behavior changes into distinct commits, relying on the existing (large) suites; no refactor PR may change a test expectation.
  • Cross-repo token changes (C1–C3) land behind compatibility: relay keeps accepting the old format for one release; the shared vector file is the contract test preventing drift from returning.
  • Existing harnesses to lean on: the local daemon smoke harness (kernel), relay smoke drills, arroba-cloud's route/service suites, and the visual-validation fixtures for the web terminal.
